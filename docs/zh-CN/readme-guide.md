# 给工程写 README

你的工程根目录可以放一份 `README.md`——写给**演出现场的人**看的一页纸。读者有两拨：**侧栏前的准备者**（操作者、场地技术员）与**开演前坐在场地屏幕前的观众**（v1.5.0 起投影窗口的简介页显示同一份文件，见「场地屏上的简介」）。App 会在主界面选中工程卡片时把它渲染成一张**封面页**：巨大标题、作者胶囊、四点 logo 配色与封面图、小节文字的排版全部由 App 完成，你只负责按格式填内容（见「封面页格式」）。演出文件夹的自述（App 内表单写的那份简介）是另一个物种，不要混淆。这份指南讲的就是工程侧这份文件怎么写。

## 为什么值得写

演出当晚的操作者面对的是一列工程卡。选中卡片后，App 主界面显示的就是这张封面页——不用翻工程目录、不用问作者。一份交代清楚「这是什么、怎么演奏、要注意什么」的 README，能让替补操作者、场地技术员和未来的你自己在一分钟内进入状态。

它不是合规条件：没有 README 只显示空态，preflight 不检查它。但既然 App 给了这块屏幕，把它用起来。

## 它出现在哪里

- **App 主界面**：选中工程卡片时，右侧 README 面板渲染工程根的 `README.md`（v1.5.0 起）；改了文件想刷新，把选中切走再切回来即可（再点一次当前卡片即取消选中）；
- **投影窗口的简介页**（v1.5.0 起）：「投影开演」（▶ / ⌘⏎）之前，面向场地屏幕的投影窗口显示同一份 README——观众入场后看到的第一屏就是它，写法见「场地屏上的简介」；
- **`.pnds` 里**：打包排除清单从不裁掉它，装到别的机器上看到的就是同一份；
- **演出文件夹导出目录**：那里的 `README.md` 是**文件夹自述**（App 内表单的简介合成的），不是工程这份——两者同名但不同源。

## 封面页格式

README 分两段：`---` 之前是进 App 封面页的内容，之后（可选）是给 GitHub 读者的固定样板。完整骨架：

```markdown
# 失语 III

**中文** | [English](README.md)

title: 失语 III
composer: @肖翔
composer_url: https://…
github_url: https://github.com/…
color_palette: [#000000, #C9D8B6, #F1ECC3, #57837B]

## 作品简介：

<一节自由撰写的正文——封面页横带里的文字>

---

## 关于作品

<固定的 PNDS 样板，见下文，可直接复制>
```

元数据行写在文件顶部的正文之前——它们不是 markdown 语法，按 `key: value` 原样一行一条：

| 键              | 用途                                       | 缺失时的行为                                   |
| --------------- | ------------------------------------------ | ---------------------------------------------- |
| `title`         | 封面页大标题                               | 回退到 README 的一级标题                       |
| `composer`      | 右上角作者胶囊（如 `@肖翔`）               | 不显示胶囊                                     |
| `composer_url`  | 作者胶囊变按钮，点击用默认浏览器打开       | 胶囊照常显示但不可点                           |
| `github_url`    | 头部新增 `github` 按钮，打开仓库           | 不显示按钮                                     |
| `color_palette` | 四点菱形 logo 的配色，顺序＝左、上、右、下 | 合法 `#hex` 色值不足 4 个时，回退 App 品牌四色 |

两个 URL 键只接受 `http(s)://` 地址——其他写法（`ftp:`、随手敲的字符串）一律按缺失处理，不会交给浏览器。

规则：

- **只有第一节进封面页**：小节标题由你定（「作品简介：」「演奏说明：」都行），正文随你写；面板内容止于第一个 `---`；
- **`---` 之后不进面板**：那是给 GitHub 读者的部分，官方工程用下面这段样板——

```markdown
## 关于作品

本作品为 PNDS 工程。PNDS（Platform for Networked Digital Score）是一个面向网络化数字音乐演出的开放平台，用于创建、运行和组织多人参与的数字乐谱作品：创作者将一份数字乐谱、一套声音引擎和一组网络交互规则组织成一个独立的演出工程，再由 [PNDS App](https://github.com/xO-xN/PNDS-App)（macOS 桌面应用）在演出现场将它变成一个可运行的本地多人数字音乐演奏系统。
```

- **语言切换行**留在顶部（写法见「双语 README」的示例）：它是给 GitHub 读者的；App 按界面语言自动选择变体，这类相对链接在 App 内点击无副作用；
- **旧格式不受影响**：没有元数据块的 README 按普通文档渲染，老工程无需改动。

## 封面图 cover.png

封面页下方横带的左侧是一张方形封面图——创作者对工程的截图。封面放在工程根目录，命名 `cover.png`（App 依序探测 `cover.png` → `cover.jpg` → `cover.jpeg` → `cover.webp`，先到先得）：

- **建议 1:1 正方形**：面板按方形展示，1:1 在任何窗口宽度下都不被裁切；
- **选最能代表作品的画面**：monitor 页的生成图形、演奏中的 performer 页，都比目录截图更像「这部作品」；
- **体积克制**：建议压到 2 MB 以内——演出机器不该为一张图等待（硬上限 4 MB，超过会被拒绝显示）；
- **语言无关**：封面不做 locale 变体，一份图服务所有语言；
- 没有封面时横带只显示文字，其余行为不变；它与 `README.md` 一样随 `.pnds` 原样旅行。

## 双语 README

演出可能跨语言，官方工程必须给出双语 README：`README.md`（默认语言）+ `README.<locale>.md`（如 `README.zh-CN.md`）。**App 会按界面语言自适应打开对应变体**（界面是中文就优先 `README.zh-CN.md`），没有对应变体或只有单一 README 时回落到 `README.md`，行为不变。两份 README 都按上面的封面页格式写，元数据各随其语言。

在 GitHub 上阅读时给读者一行语言切换链接（App 内这类相对链接不会导航，点击无副作用）：

```markdown
[中文](README.zh-CN.md) | **English**
```

两份 README 保持同一结构；翻译滞后时以默认语言那份为准更新。

## 场地屏上的简介

「投影开演」（▶ / ⌘⏎）之前，投影窗口停在**简介**——显示的就是这份 README：封面格式显示封面页（大标题、封面带），普通格式显示全文的静态文档视图。观众入场后看到的第一屏是你写的，这给上屏的那部分内容加了一条纪律：

- **不提前暴露乐谱画面、结构与关键交互**。悬念是演出的一部分：monitor 会长什么样、乐谱如何翻动、哪个手势触发什么，留给开演后的观众现场经历。上屏的内容写「作品是什么」——编制、时长、气质；「怎么玩」留给操作者（见下）。
- **篇幅按「站着扫读」写**。封面带的文字超出时虽会自动缓速滚动，但一段站着就读得完的文字远胜一段滚个不停的长文；普通格式的文档视图**不会**自动滚动，上屏的只有打开时的首屏——长的内容要么压缩，要么放进封面格式的 `---` 之后（那里不上屏）。
- **操作者向的内容挡在上屏区之外**。封面格式天然挡得住：首节之后的「演奏方式」「技术需求」不上投影；普通格式则是**整份文件上屏**——含操作细节的 README 请改用封面格式，或把观众不宜先看的部分移到 `---` 之后。
- **双语变体跟随 App 界面语言**。投影简介与主窗口面板打开同一变体——操作者把 App 界面设成哪种语言，观众就看到哪份。演出场地的语言应该决定你确认哪份变体上屏（见「双语 README」）。

首节示例（观众视角、可上大屏）：

```markdown
## 作品简介：

《失语 III》为五名演奏者与实时声场而作，长约 14 分钟。人声、
打击乐与三件乐器在网络乐谱的调度下彼此应答，声场随演奏者的
走位缓慢变形——一场关于「说不出口」的合唱。
```

## 写作要点

- **元数据行写在顶部、别包进代码块或列表**——App 靠它们认出封面页格式；包住了格式就失效，按普通文档渲染；
- **正文纯 markdown**：GFM 表格、围栏代码块都正常渲染；裸 HTML 一律不渲染，写了也白写；
- **克制篇幅**：进面板的只有第一节，但整份文件也别失控。超大的 README 会被 App 拒绝渲染并提示；
- **上屏的部分先自查一遍**：封面格式的首节会投给入场观众——能过「不提前暴露乐谱」这一关再定稿（见「场地屏上的简介」）；
- **用读者的语言**：演出在哪国就用哪国话写；App 界面语言决定打开哪个变体，不改动内容本身；
- **别把运维细节写进来**：端口、协议字段这类契约在参考手册里（如 [structure.md](./reference/structure.md)），README 只管「人怎么把它演下来」。

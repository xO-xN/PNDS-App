# 给工程写 README

你的工程根目录可以放一份 `README.md`——写给**演出现场的人**看的一页纸。App 会在主界面选中工程卡片时直接渲染它；演出文件夹的自述（App 内表单写的那份简介）是另一个物种，不要混淆。这份指南讲的就是工程侧这份文件怎么写。

## 为什么值得写

演出当晚的操作者面对的是一列工程卡。选中卡片后，App 主界面显示的就是这份 README——不用翻工程目录、不用问作者。一份交代清楚「这是什么、怎么演奏、要注意什么」的 README，能让替补操作者、场地技术员和未来的你自己在一分钟内进入状态。

它不是合规条件：没有 README 只显示空态，preflight 不检查它。但既然 App 给了这块屏幕，把它用起来。

## 它出现在哪里

- **App 主界面**：选中工程卡片时，右侧 README 面板渲染工程根的 `README.md`（v1.5.0 起）；改了文件想刷新，把选中切走再切回来即可（再点一次当前卡片即取消选中）；
- **`.pnds` 里**：打包排除清单从不裁掉它，装到别的机器上看到的就是同一份；
- **演出文件夹导出目录**：那里的 `README.md` 是**文件夹自述**（App 内表单的简介合成的），不是工程这份——两者同名但不同源。

## 推荐大纲

五个部分，前四个建议都要，最后一个按需：

```markdown
# <作品名称>

**作者**：<姓名 / 团队>

## 简介

这个作品是什么、编制、时长——写给演出操作者的一段话。

## 演奏方式

如何启动与操作：页面怎么分（谁看 performer、谁看 monitor）、
交互手势、每个阶段的推进方式、注意事项。

## 技术需求（可选）

音频模式、外接设备、网络要求——场地需要提前准备的东西。
```

「演奏方式」是现场最有价值的一段：写清楚操作顺序和容易踩的坑，别假设读者看过彩排。

## 双语 README

演出可能跨语言，官方工程必须给出双语 README：`README.md`（默认语言）+ `README.<locale>.md`（如 `README.zh-CN.md`）。**App 会按界面语言自适应打开对应变体**（界面是中文就优先 `README.zh-CN.md`），没有对应变体或只有单一 README 时回落到 `README.md`，行为不变。

在 GitHub 上阅读时给读者一行语言切换链接（App 内这类相对链接不会导航，点击无副作用）：

```markdown
[中文](README.zh-CN.md) | **English**
```

两份 README 保持同一大纲；翻译滞后时以默认语言那份为准更新。

## 写作要点

- **纯 markdown**：GFM 表格、围栏代码块都正常渲染；裸 HTML 一律不渲染，写了也白写；
- **克制篇幅**：这是墙上的一页纸，不是技术文档。超大的 README 会被 App 拒绝渲染并提示；
- **用读者的语言**：演出在哪国就用哪国话写；App 界面语言不影响 README 的显示；
- **别把运维细节写进来**：端口、协议字段这类契约在参考手册里（如 [structure.md](./reference/structure.md)），README 只管「人怎么把它演下来」。

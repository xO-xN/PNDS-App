# 运行期健康监督

本机工程进入 `ready` 后，进程仍存在不代表工程仍可用。工程可能已经在 health 中报告音频错误，而 Node 与 scsynth 都没有退出。运行期监督继续核对工程报告及 Internal 音频服务器响应；启动期就绪校验仍遵循[运行契约 §5](../zh-CN/reference/runtime-contract.md#5-health-contract)。

## 归属与频率

监督复用 `SessionManager` 的运行 watchdog，不创建额外常驻进程。每代本机 session 复用一个 HTTP Agent 和适用的 UDP socket；请求串行执行、单次有界，不为错过的时间点堆积请求。探测在 session 锁外执行，返回后重新核对 generation、运行状态和当次已应用配置。停止、重启、切换工程后的迟到结果不得更新新演出、清除新告警或关停新进程。

| 探测                                    | 频率    | 适用范围                                            | 证明的事实                         |
| --------------------------------------- | ------- | --------------------------------------------------- | ---------------------------------- |
| loopback performer `GET /__pnds/health` | 每 3 秒 | 有本机工程进程的 Internal / External / None session | 当前工程报告及身份、配置仍匹配     |
| OSC `/status`                           | 每 5 秒 | App 托管 scsynth 的 Internal session                | 当前 OSC target 能返回有效状态回复 |

HTTP 先核对 `projectId`、`audioMode`、实际 performer / monitor 端口、适用的 runtime `runId` 和 OSC target，再解释错误字段。运行端口工程采用当次实际分配，不能退回 manifest 首选端口。HTTP 200、另一个工程的 `error` 或结构不完整的 JSON 均不能独立触发当前工程的致命故障。

App 自身读取的 HTTP health 响应体上限为 256 KiB，禁用重定向及环境代理，始终直连回环目标；此边界同时用于启动与运行期读取。超限、重定向与其他读取失败按所在阶段处理，不跟随新的目标地址。

External 只读取工程自己的 health，不向用户指定的外部音频服务器探测；None 不发送 OSC。池客没有本机工程进程时不运行这套监督。HTTPS、池客入口与 DNS 的故障仍沿各自状态和恢复规则处理，不与本机工程健康合并。

## 告警与失败

| 观察结果                                                                                                                     | 处理                                                                |
| ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| HTTP 超时／不可达、结构错误、身份或配置不匹配，以及未明确报错的非 ready 状态                                                 | 工程通道累计连续失败；第 3 次起保持告警，保留可能仍在发声的 session |
| Internal `/status` 超时、错误来源或无效回复                                                                                  | 音频通道累计连续失败；第 3 次起保持告警，不仅凭无回复拆除音频       |
| 通道取得有效成功结果                                                                                                         | 清除该通道连续失败及告警，另一通道的故障独立保留                    |
| 身份和配置匹配的 health 明确报告 `status: "error"`、`audio.status: "error"` 或非 null 的 `audio.error` / `scoreServer.error` | 立即按当前 generation 执行既有 `fail_generation`，不等待 3 次       |
| Node 或受管 scsynth 已退出                                                                                                   | 沿用既有子进程退出失败路径                                          |

明确错误保留原始故障 health 与采样时间，先收尾该代次的工程、音频及演奏记录，再发布 error 快照。错误页沿用手动 Retry；监督不自动重启音频、不重开工程，也不重放演奏输入。告警与错误区分的原因是：网络或调度短暂停顿不能证明声音已经停止；经归属核验的工程明确错误则是工程报告的实际失败。

`runtimeHealth.project` 与可选的 `runtimeHealth.audio` 各自包含 `status`（`healthy / unresponsive / failed`）、`checkedAt`、`lastSuccessAt`、`firstFailureAt`、`consecutiveFailures` 与 `error`；三个时间字段为 Unix 毫秒。前两次未确认失败只累计证据，第 3 次才进入 `unresponsive`；明确故障直接进入 `failed`。明确故障的原始 payload 保留在 session 的 `health` 中，不由后续回复覆盖。

正常检查只在后端更新证据，不发 UI 事件、不追加日志、不弹 toast。每轮连续失败的首次失败及恢复各记录一次诊断日志；第 3 次的告警状态变化才发 UI 事件，告警恢复和明确故障也按语义状态变化通知。重复失败不反复 emit 或记录日志。故障详情与日志继续归属于原 generation；告警保持至该通道成功或本次运行结束，不因此写入用户偏好。

## 性能与验收边界

稳定运行时每 3 秒一次 HTTP、Internal 另每 5 秒一次小型 OSC 请求；连接与 socket 按代次复用，HTTP 有 256 KiB 响应上限，没有高频音乐消息采集、逐 poll 磁盘写入或额外 UI 刷新。这些是实现约束，不是 CPU 或内存占用的实测结论。增加探测前应先说明它能区分哪一种故障，不能把更高轮询频率当作声音可靠性的证据。

自动化需通过真实本机 HTTP／UDP fixture 验证：ready 后才开始监督；正确归属的明确错误立即收尾并保留 payload／时间；超时、畸形、其他工程及普通非 ready 回复连续 3 次才告警；成功恢复、两个通道独立计数；停止／重启交错和迟到结果不影响新代次；None／External／池客的范围限制；正常轮询不产生重复事件或日志。子进程退出、录制退役及错误页手动 Retry 仍使用原有回归入口。

原生验收在用户启动的 App 中比较相同工程、设备和负载下的正常运行及多人叠录，记录 CPU／内存、日志增长与 UI 更新次数；用可控的工程错误和暂时不可达分别观察 error 与告警，再确认手动 Retry。自动化通过不代替这组测量，也不能证明实际扬声器有声。本阶段不检查 master 节点存活、音频电平、NaN 或硬件输出；`/status` 成功只能证明服务器响应。

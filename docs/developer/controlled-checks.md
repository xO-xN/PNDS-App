# Controlled saved-copy checks (#194)

The App and `pnds check --run` adapt the same `run_controlled_check` service.
The service owns a saved temporary project, copied shared resources, input
inventory, child registry, output tail, cancellation and structured report.
It never starts a second GUI manager, changes preferences, updates the main
session generation or publishes session snapshots. Relative cache and compile
writes stay in the copy; no artifacts are adopted automatically. This is a
saved-file execution workflow, not an operating-system sandbox for hostile code.

The workbench does not expose a manual saved-copy check action, issue-count
launcher or report panel. Its right pane is preview-only. Assistant tools, CLI
execution, native commands and the shared frontend runner retain their existing
authorization, runtime exclusion and cleanup behavior.

## Desktop page observation

The desktop adapter uses `run_controlled_check_observed` to inspect the live
saved-copy HTTP pages before child cleanup. Hidden incognito WebKit windows
capture script exceptions, resource load failures, unhandled Promise rejections,
console errors and local-resource CSP violations. Each page gets a bounded load
wait and a 1.5-second post-load observation. Reports add `browserScripts` evidence;
a failure makes the check fail and is available to the edit assistant's repair
loop. Windows are destroyed after observation/cancellation. Visual appearance,
later interactions and sound remain explicitly unverified. `notification_plugin.rs` delegates the
notification plugin lifecycle and command routing, but skips its Web API
bootstrap in `check-page-*` windows. These windows receive no additional native
permissions. Without that scope, the plugin eagerly calls
`is_permission_granted`, producing a denied IPC Promise that is unrelated to
the score. A regression executes the actual installed plugin initialization
script: Host pages invoke it; check pages do not. The browser observer still
reports all project Promise failures. CLI uses the same
service without a browser observer and does not claim this evidence.

The edit assistant projects this report into bounded diagnostic JSON rather
than sending complete file/dependency inventories to the model. The original
report and native freshness checks are unchanged. Within one logical assistant
task, a previous check is reused only after native content freshness validation;
new writes invalidate the cached receipt. Stale/unverifiable input requires a new
check. See [creation-assistant.md](./creation-assistant.md) for pause and receipt
ownership.

The edit tool runs `diagnoseCreationProject` before requesting the runtime lease.
Saved-file static diagnostics are read-only and remain available during an
active performance. A blocked runtime is separate from static pass/failure;
`runtimeBusy` is a typed command error rather than a generic validation failure.
For a ready session owned by the current workspace, the assistant now uses
`inspectCreationRuntime(identity, true)` instead of requesting a second lease.
This bounded read-only observation GETs the existing local health endpoint and
HEADs both existing page roots. It checks project identity, audio mode/target and
ports against the ready session. It creates no webviews, sockets that join music
protocols, processes or audio services. The native adapter fences both creation
identity and runtime generation after I/O. Starting/stopping and another
controlled check still remain blockers; unchanged occupancy is not retried.

Live observations are explicitly `kind: liveObservation` with
`savedChangesVerified: false`. They are neither saved-copy receipts nor proof
that modified server/JS files have loaded. Static diagnostics still verify saved
contracts; browser execution, sound and fidelity remain outside this observation.
Server changes require a creator restart to load. The assistant reports that
scope once and finishes rather than repeatedly requesting an exclusive run.
Pause/restart cannot reuse this observation as fresh saved-input evidence; old
`activeSession` blockers are also invalidated once ready observations are possible.
The explicit static-only tool still makes no browser, sound or execution claim.

## Ownership and lifecycle

### Task-owned compilation and Node tests

Assistant compilation uses `prepare_assistant_synthdefs` / unlocked compiler /
`finish_assistant_synthdefs`. The current edit grant, unresolved task questions,
protected editor drafts and saved input versions are checked before execution
and again before publication. Every manifest reference must be generated by that
run and pass binary symbol validation. Existing files are not evidence that a
new compile succeeded. The task journal records original and pending binary
bytes before publishing; interrupted publication and undo reconcile against
actual bytes. Whole-task undo preflights binary conflicts before restoring text.
External changes prevent replacement and undo. New artifact directories remain
task-owned and are removed only when empty and still owned.

`getAssistantBuildState` is read-only. It requests compilation when the task
changed standard SCD sources, when a non-document task has missing/invalid
declared artifacts, or when an existing successful receipt no longer matches
all saved inputs and artifact bytes. A new document-only task does not trigger
a whole-project build audit. `compileAssistantSynthdefs` reuses a receipt only
after those native comparisons. Failed/missing compiler results do not become
reusable build evidence. No build operation restarts a live performance.
The optional `projectCheck` flag permits a read-only missing-reference check for
an untouched task before an explicitly requested project check. Ordinary final
validation leaves this flag false; tasks with only document changes still skip
compilation. No remaining SCD sources and no references mean no build is needed.

`startAssistantTests` runs supported saved `*.test.js`, `*.test.mjs` and
`*.test.cjs` files outside `node_modules` with bundled Node and fixed arguments
`--test --test-reporter=tap --test-concurrency=1`. It accepts no command, shell,
package installation or custom runner arguments. No supported entry returns
`notExecuted` before a runtime lease or temporary copy is requested. Otherwise
the same exclusive runtime lease, saved copy, process group, durable ownership,
bounded output and cleanup service apply. A project test is executable project
code; the temporary copy is not an OS sandbox. Live performance blocks this
execution. Node test reports add actual `nodeTests.entries` and `exitCode`, retain
input evidence/freshness, and do not claim sound or page execution. Dependency
resolution failures are test failures and do not install packages.

Compiler and Node-test operations are tied to one assistant task. Cancellation,
ending the task, workspace close/replacement and application exit revoke active
operations. Compiler publication is fenced after the unlocked process returns;
Node test cleanup is confirmed before its lease is released. A late result
does not grant a new task permission to publish.

The controlled eight-pad NRT acceptance is test-only and separate from project
test execution. It compiles actual artifacts through the task journal and
measures output from `scsynth -N` with a known gate protocol. It makes no claim
about arbitrary project OSC protocols or live device sound. Commands, thresholds
and observed results are in the
[native build/NRT acceptance record](../acceptance/assistant-native-build-and-nrt.md).

### Shared frontend scheduling

`CreationCheckRunner` is the frontend module used by assistant tools and retained
isolated report fixtures. Its interface owns submission, 300 ms progress polling,
task/workspace reply validation, cancellation and native freshness queries.
The standalone component tests also exercise its 10-second/focus freshness
watcher; assistant completion and receipt reuse request a single verification.
Failed or superseded verification is `unknown`, never fresh. A failed query
retains its error and can retry without submitting another check.

Each runner belongs to one creation identity and one caller lifetime. Duplicate
submission cannot start another native task. Cancellation during option
preparation prevents submission; cancellation during native submission waits for
the returned task ID and cancels that exact task. Explicit cancellation keeps
collecting the cleanup report even after its caller hides its report. Disposal
revokes publication and requests cancellation even if startup returns later.
Workspace replacement fences late progress, reports and freshness replies.
None of these frontend facts imply confirmed native cleanup.

The retained standalone adapter captures explicit audio/compile choices and the
current preference snapshot, submits `startCreationCheck` and tolerates transient
polling errors; isolated tests mount it directly, with no App navigation entry.
The assistant retains draft protection, static-first diagnostics,
occupied-runtime suppression, bounded report projection and receipt reuse;
it submits `startAssistantCheck` with the current authorized task ID and returns
polling failures to the model loop. Assistant submissions never fall back to the
manual command after an authorization or runtime refusal. Native task grants,
runtime leases, source evidence and cleanup remain authoritative and unchanged.
The task-scoped [assistant check policy](./creation-assistant.md#assistant-check-policy)
owns those assistant-specific decisions; the shared runner remains independent
of pending check obligations and checkpoint formats.

Tests cross the runner's interface for late startup cancellation, owner changes,
reply mismatch, cancellation cleanup, unknown freshness and detached watchers.
The dialog and assistant tests retain their distinct policy and presentation
assertions; native checks still test real temporary files and process ownership.

### Native runtime ownership

`RuntimeLease` uses a nonblocking exclusive OS file lock at the user's
`Library/Application Support/com.xo-xn.pnds-app/runtime.lock`. Both App runtime
startup and controlled-check submission acquire it before resource preparation.
The Host retains its lease across starting, ready, stopping, teardown and
unconfirmed cleanup. Controlled-check adapters call `begin_check(task_id)` before
starting the service and `finish_check(confirmed, unresolved_groups)` before
releasing the lease. These append a durable journal to the same locked inode;
confirmed process cleanup clears it. Unconfirmed cleanup records group IDs,
captured leader birth identities and task markers, so ending either front end
does not unlock new App or CLI runs. A dead leader does not prove its descendants
released their resources. Acquisition probes only whole-group absence (`ESRCH`),
never sends a termination signal, and clears complete ownership records only
when all recorded groups are absent. A recorded boot-session change also proves
previous processes are gone. The CLI can exit boundedly while this blocker persists. Journal finalization
errors are appended to the completed report's cleanup errors; a passed task
becomes failed, while an existing cancellation or failure keeps its original
outcome and evidence. A journal-start I/O failure returns a not-executed
operational JSON report (exit 1), rather than an argument error with empty stdout.
Do not unlink this lock file: replacement would create two independent owners.
Saved-file static diagnostics and static CLI checks acquire no runtime lease.

An interrupted run with incomplete ownership evidence remains blocked. Restart
the Mac before retrying; a boot-session change clears valid old records. A
malformed/truncated journal cannot supply a trustworthy boot identity and is
never silently discarded. If it still blocks after a reboot, quit every PNDS App
and CLI first, then truncate the existing `runtime.lock` file to zero bytes
(without deleting or replacing its inode). This maintenance recovery is safe
only after the reboot has removed every former process and no new runtime owner
is active. Never use this step to bypass an active or unconfirmed live task.

The App accepts only the backend-issued creation identity. It registers the task
while holding the creation access lock, returns a task ID and exposes progress,
report and cancellation by that task ID. Workspace replacement or close cancels
the former owner's task. UI requests and stale checks fence task and workspace
ownership; a late result cannot replace a newer report. Actual App exit requests
cancellation and waits for bounded cleanup before exiting.

Results lead with outcome, the actual error, failed/skipped check reasons and
repair actions. Confirmed checks, task/project/checker metadata, cleanup facts,
environment, input evidence, unverified items and output tails expand under Full
check report. Unconfirmed cleanup and cleanup errors remain visible outside it.
Settings are open before a report, then collapsed below results; changing their
visibility never starts a check. Copy report still includes the complete original
envelope, independent of disclosure state.

The dialog stays mounted for the current creation identity while hidden. Closing
an active check still requests cancellation and collects its final cleanup
report; reopening shows the same result or submission error until an explicit
new check. Workspace replacement unmounts that state and fences late replies.
Copy report writes the full report/error envelope, task ID and creation identity
to the clipboard; clipboard failure never overwrites the original diagnostic.

CLI supervision starts a separate worker with a private stdin control pipe.
The worker holds the lease and runs the same service. SIGINT/SIGTERM request
cancellation; unexpected front-end exit closes the pipe and cancels the worker.
The worker cleans its own process groups before writing its final result. This
covers the CLI front end disappearing; forced termination of every process or
machine power loss cannot produce a successful cleanup report.

None is the default and requires the saved manifest to support None. Internal
requires explicit selection and resolves the actual output device/sample rate,
channel plan, scsynth readiness and master stage with existing audio primitives.
External remains a manual App workflow. Explicit compilation uses the existing
compiler/validated artifact publication on the copy, with cancellation. A missing
compiler or required resource remains a failure; no installation is attempted.

Node and audio have independent owned process groups and registries. Readiness
checks the live child, project ID, audio mode/target/state, both declared ports,
health errors and HTTP 200 at both roots. Cleanup stops Node before audio, using
bounded escalation. Cleanup facts remain separate from task outcome. Unconfirmed
process cleanup retains ownership information and is never a pass.

While both overall and audio state are `starting`, a null audio target is an
unfinished startup fact and polling continues. Identity, mode, ports and explicit
errors are still validated on every payload; a non-null wrong target fails.
Ready payloads must have the exact task target and mode-appropriate audio state
before HTTP/master-stage verification. A project that never becomes ready still
times out. Starting-to-ready transition tests must include the initial null
target so fast fixture startup cannot conceal this boundary.

## Input evidence and report

Report schema 1 records task/project identity, checker version, explicit mode,
static and runtime outcomes, health, actual environment, output tail, cleanup,
input evidence and source freshness. JSON stdout contains only the report.
Each copied file has its content SHA-256, path, size and permissions; directory
entries and dependency/lockfile contents also affect the tree fingerprint.
Production declarations, installed package versions and exact shared references
are separate facts. Git HEAD and dirty status are auxiliary observations; Git
absence does not prevent checking uncommitted input.

Copies exclude the root `.git`, include saved sources, assets and `node_modules`,
materialize contained file links, reject escaping links and do not claim an
instantaneous whole-project snapshot. Reads are descriptor-relative, nonblocking
and limited to regular files. Limits are 100000 entries, 2 GiB per file and 8 GiB
per tree. Cancellation is checked while reading/copying. Preparation changes,
incomplete reads, root replacement and later source/shared changes remain
explicit. App stale rechecks rehash actual content; watcher revision only adds a
conservative stale hint. A new report requires an explicit new check.

HTTP readiness does not validate rendered pages, phone connections, model
inference, actual sound, artistic quality, external audio, trusted HTTPS or the
telematic hub. Physical audio and dual-architecture installed App acceptance are
tracked in [the v1.6.5 acceptance record](../acceptance/194-v1.6.5-controlled-checks.md).

## CLI

```sh
/Applications/PNDS.app/Contents/MacOS/pnds check /path/to/project --run --json
/Applications/PNDS.app/Contents/MacOS/pnds check /path/to/project --run --mode internal
/Applications/PNDS.app/Contents/MacOS/pnds check /path/to/project --run --compile
```

`--timeout-ms` selects the readiness budget (100–120000, default 30000).
`--sample-rate` and `--output-device` are per-task Internal options. Accepted
rates are the same shared Host policy: 44100, 48000, 88200 and 96000 Hz; invalid
rates fail argument parsing with exit 2. Resources
come from the installed executable layout, or an explicit `--app-root PNDS.app`;
there is no maintainer-checkout or global Node fallback. `--resources-root` still
means the shared-library directory containing `catalog.json`. Options precede
`--` when the project name starts with a dash. Without `--run`, the existing
static-only behavior and resource discovery are unchanged.

Runtime exit codes: 0 passed including confirmed cleanup; 1 failed or not
executed; 130 cancelled; 2 invalid arguments or output failure. Read the complete
cleanup and unverified fields even when a report is returned. Single-file review
and recovery are independent and described in [single-file-changes.md](./single-file-changes.md).

Manual check entries, including the discussion's independent check button and
the right debug-panel menu, have been removed. `CreationDebugPanel` only offers
preview expansion and hiding; it does not mount `CreationDoctor` or
`CreationControlledCheck`. The report-only `debugView`/`debugVisited` state and
`setDebugView` action are gone, so navigation cannot reveal a hidden report.
Preview layout changes preserve the same iframe and URL, bottom transport and
console.

Standalone report components remain isolated test adapters for saved-input,
freshness, report retention, cancellation, guarded undo and repair-handoff
behavior. They provide no creator-facing entry. The internal assistant still
checks through its authorized tool flow, and the CLI/runner/native report
contracts are unchanged; failure does not grant additional execution authority.

## 每次调用的共同要求

- 复用同一个 App 整合分支，例如 `codex/v1.7.0-beta.3-performance-entry`；各实现票使用自己的分支和隔离 worktree。每组开始核对当前整合分支与已完成票，结束把成果合回同一个分支。
- implement-spec 默认目标是实施整个规格，因此每次必须明确写“本次仅处理以下 issue”。分组完成不代表父 #294 已全部完成；父规格只在全部实施与最终验收满足后处理。
- 当前 App 与多个维护源都有既存修改。建立 worktree 前记录并保留已确认的 staged、unstaged 和 untracked 输入，建立可核对的工作基线；仅从旧 HEAD 派生会漏掉本轮已确认输入。不要提交无关修改。
- 九个维护源实际属于九个独立 Git 仓库，部分维护目录本身是 linked worktree。App 的隔离 worktree 不会隔离这些源；各源在自己的真实仓库建配套分支／worktree，依据指定维护树和输入快照工作。App 整合分支记录源提交、包版本与内容哈希，不把 App 合并当作已收录外部源码。
- ASBS 两票复用同一源仓库的连续成果，接入票必须基于完整预取票。原 #304 已完成 Template／Classic 核验冻结，其记录保持；#315 撤下 Classic 新建，后续验收唯一 Blank 和既有 Classic 兼容。Template 仍按维护清单的明确来源维护，不猜测新 App worktree 的父目录。
- 四工具源可并行；App 工具注册信息、固定包与哈希由同一整合者顺序合入。共享真实端口的检查也统一调度，避免多个整合者竞争同一 App 工作区和夹具。
- 每票按 tdd 工作，完成后先并入整合分支最新状态，再由整合者合入；各组运行适用检查与 code-review，最终仍需完整 App 检查和跨仓库资源验收。
- 第 7 组需要真实设备、签名 App、最低 macOS／双架构及双机结果；自动化、API 可见或健康响应各自只证明相应范围。开发服务器由用户启动并回报，缺设备结果保持待验。
- 工具的本地构建与远端固定发行物分别核对；提交、标签、推送和发布以明确授权为准。后续若获准本地提交，不自动扩展为打标签或正式发布授权。

# v1.7.0-beta.2 演奏记录与叠加排练实施规格

状态：2026-11-03 用户确认纳入 v1.7.0-beta.2；首版及 2026-11-04 轮次修订已在工作区实现，原生声音与发行验收仍须分别核对。本规格覆盖先前设计文档中“评估中／待完整方案确认”的状态，不将原型模拟结果视为功能证据。

2026-11-04 用户实测后确认[录制轮次修订](./2026-11-04-performance-recording-debug.md)及 [ADR-0016](../adr/0016-recording-pass-as-management-unit.md)：每轮可多人，整轮重录，列表／详情与两层删除；旧记录保留并视作一轮“已有内容”。下文对应条款已按新决定修订，原生声音验收仍须用户执行。

## Problem Statement

演出结束后，演奏者与创作者无法在 App 中恢复一场演出的演奏信息、乐谱及指挥过程。创作者独自修改作品时，也无法用自己的设备逐遍扮演不同演奏者，在已有演奏的基础上加入新输入，体验多人相互作用与声音的大致效果。

直接保存画面快照不足以重新驱动作品，记录音频也不能让同一份演奏信息试听修改后的工程。作品可能随机生成乐谱、允许多位演奏者选择同一序号，并通过 START、暂停或定位改变乐谱进度；若把设备、序号、乐谱进度和记录时间混为一谈，各遍就会错位、覆盖彼此或产生错误声音。

## Solution

在 App 共用底栏提供“演奏记录”入口，轻量面板分记录列表与详情：列表新建、删除、导入／导出整份记录，详情回放、叠加及管理轮次。底栏持续显示当前状态与经过时间，返回列表或收起面板后操作继续。池主的演出模式支持整场记录与回放；创作模式另支持叠加新轮次和整轮重录，每轮可一人或多人。池客仍只参与工程，不因此获得全场记录控制。

记录保存足以恢复作品行为的演奏、乐谱与指挥信息，回放时由兼容工程实时生成声音。第一遍确定总时长与共同指挥过程。之后每遍恢复同一初态，自动重放已有演奏和 START／暂停／定位，在共同时间轴上录入新增或重录对象；到末尾自动保存。记录演奏者独立于物理设备和乐谱选择序号。

用户在作品页面自行选择编号、准备和决定起录时机。App 不监控编号是否选择完成，不增加准备确认或起录门槛。首版以 Inarticulate III 验证完整叠加互动，以 runes 验证随机乐谱和同序号多演奏者。未适配工程继续按原方式运行，不宣称可录制回放。

## User Stories

1. As a host, I want to record the performers accepted by my running score project, so that I can replay the actual performance later.
2. As a creator, I want to record and replay within creation mode, so that I can evaluate my score while developing it.
3. As a creator, I want to reuse my device or record with other people in each overdub pass, so that I can experience a work intended for multiple performers.
4. As a performer, I want to choose my score selection number in the project page, so that the score retains its own participation workflow.
5. As a creator, I want to start recording when I decide I am ready, so that App readiness checks do not interrupt rehearsal.
6. As a host, I want recording to begin without automatically pressing the score START control, so that I retain control of the live performance.
7. As a host, I want to start recording after a performance has already begun, so that its current score and necessary state become the recording's initial state.
8. As a host, I want stopping a recording to leave the live performance running, so that saving a recording does not end the event.
9. As a listener, I want playback to generate sound through the score project, so that the recorded performance remains usable with its musical behavior.
10. As a creator, I want the actual randomly generated score to be saved, so that ordinary playback restores the score that was performed.
11. As a creator, I want new overdub input to affect the score according to the project, so that interactive behavior remains audible and visible.
12. As a creator, I want every overdub to restore a common initial state, so that residual touches or sound control from the previous pass do not contaminate the next pass.
13. As a creator, I want later passes to replay the recorded START automatically, so that I do not introduce timing differences by pressing it again.
14. As a conductor, I want effective START, pause, and seek changes captured during the first recording, so that playback follows my actual conducting.
15. As a creator, I want new manual conducting disabled during playback and overdubbing, so that every pass shares the same conducting timeline.
16. As a creator, I want preparation waits and score pauses included in recording elapsed time, so that later passes preserve their timing.
17. As a creator, I want score seeking to leave recording elapsed time moving forward, so that events remain ordered even when the score moves backward.
18. As a creator, I want the first pass to determine the recording duration, so that subsequent passes have a consistent end.
19. As a creator, I want overdubbing and playback to end automatically at the recorded duration, so that later input does not silently extend the recording.
20. As a creator, I want existing performers inherited once during an overdub, so that replayed input is not recorded a second time.
21. As a creator, I want a new overdub to create a pass with independent identities for its live sources, so that reusing physical devices does not overwrite an earlier pass.
22. As a creator, I want multiple recorded performers to share a score selection number when the project allows it, so that rehearsal matches the work's actual ensemble possibilities.
23. As a creator, I want to manage recording passes without tracking performer identities, so that a pass can contain one or several performers.
24. As a creator, I want to rerecord an explicitly selected whole pass, so that I can improve it while retaining the other passes.
25. As a creator, I want all old performers from the replaced pass excluded during rerecording, so that a smaller new ensemble does not leave their old input behind.
26. As a creator, I want rerecording one pass to preserve other passes using the same score selection numbers, so that shared numbering does not merge their identities.
27. As a creator, I want replacement published only after a successful save, so that cancellation or failure preserves the previous completed recording.
28. As a creator, I want to stop and save an overdub early, so that the recorded portion remains usable without completing the full duration.
29. As a creator, I want an early saved pass to leave its remaining duration unperformed, so that old input does not return in the second half of a replacement.
30. As a creator, I want to discard the current pass explicitly, so that I can keep the previous recording unchanged.
31. As a performer, I want playback and overdub sources released when their pass ends while ordinary recording stop leaves live performance running, so that recorded sources do not sustain unintentionally or interrupt ongoing live input.
32. As a viewer, I want live input excluded from pure playback, so that watching devices do not alter the recorded result.
33. As a creator, I want every project-accepted live source admitted to the current overdub pass, including late arrivals, so that multi-person rehearsal does not depend on window registration order.
34. As a host, I want actual joins, departures, and reconnects represented in a live recording, so that playback preserves accepted performer activity.
35. As a creator, I want recording time to continue through a device disconnection, so that the common timeline does not shift automatically.
36. As a performer, I want reconnecting during the same pass to recover the appropriate recorded identity when the project supports it, so that a network interruption is not mistaken for another overdub.
37. As a creator, I want records saved automatically by project and visible after restarting App, so that I can return to rehearsal later.
38. As a creator, I want an independent recording file that I can export and open, so that I can share it together with a separately supplied compatible project.
39. As a creator, I want recording and project compatibility checked before playback, so that incompatible data cannot silently produce a misleading result.
40. As a creator, I want changed project content disclosed before I reuse a recording, so that I can explicitly choose to hear the performance interpreted by the current compatible project.
41. As a creator, I want the recording's original project provenance retained, so that trying a modified project does not misrepresent where its performance originated.
42. As a creator, I want interrupted data marked incomplete while completed records remain intact, so that a crash does not turn partial work into a false success.
43. As a creator, I want a new attempt after an interruption to start from the beginning, so that the first release does not imply unsupported recording resumption.
44. As a host, I want operations that end the current run to save the current pass through the existing workflow, so that recording does not add another confirmation step.
45. As a creator, I want a mode change that preserves the same running project to preserve the recording, so that the existing mode transition remains uninterrupted.
46. As a creator, I want hiding the window or collapsing the recording panel to keep recording active, so that I can focus on the score.
47. As a creator, I want recording status and elapsed time visible in the bottom bar, so that I can understand the current operation without covering the score.
48. As a user of an unsupported project, I want an honest explanation of missing recording support, so that ordinary project operation is not confused with verified replay capability.
49. As a creator, I want playback tested with real score behavior and sound, so that a working interface alone is not treated as proof of musical correctness.
50. As a creator, I want to delete a whole recording or a selected pass, so that I can manage rehearsal results without changing other passes or common conducting.
51. As a creator, I want old recordings preserved as one legacy pass, so that I can continue overdubbing without guessing their former pass boundaries.

## Implementation Decisions

1. **职责与范围**：App 提供记录操作、共同时间驱动、持久化、文件打开／导出、兼容检查和可见状态；工程通过明确的适配接口提供乐谱、来源、有效演奏与指挥信息，并恢复、接纳或释放回放来源。沿用 App 不解释作品高频业务消息的边界，不以通用抓包、读取谱面 DOM 或 session 快照代替适配。
2. **运行所有权**：全场记录由池主运行的工程或创作模式本机运行承担。池客、手机及其他演奏端的输入可由该工程记录；池客不启动本机工程服务或 App 托管的 scsynth，也不隐式增加全场记录管理。一次运行不同时执行相互竞争的录制、纯回放或叠加时间驱动，重复点击与迟到结果不得创建第二份活动操作。
3. **能力与兼容**：工程须声明并实际满足录制适配能力与协议版本；具备普通入口、health 或名册不等于具备记录能力。未适配工程提供可理解的状态，保留原运行功能。III 与 runes 的适配、工程侧测试及必要的随包分发验证属于本规格交付范围。
4. **记录对象**：保存初态、实际乐谱生成结果、记录演奏者身份与属性变化、按记录时间和确定顺序组织的有效演奏与指挥变化、总时长、完整性状态及工程来源。接口需携带足以重新驱动声音与显示的信息，不能仅采用 monitor 显示摘要，也不能用粗间隔轮询漏掉已经生效的指挥变化。
5. **声音取舍**：回放经工程实时产生声音，不保存音频轨或纯音频合成内部随机状态，不承诺逐样本一致。影响乐谱的随机生成保存实际结果，不以单一 seed 替代未经证明可还原的内容。持续输入、重复保持和释放若影响声音或存活，必须保留其语义，不能按数值相同随意去重。
6. **首次起录**：用户手动开始时捕获当时乐谱、参与者及必要初态，建立记录时间零点；作品正在演奏时捕获当前状态，不替用户 START、归零或重启工程。停止普通录制确定首遍时长并保存，演出本身继续。记录按钮和作品指挥是不同操作。
7. **共同时间**：记录时间持续前进，包含 START 前等待、乐谱暂停和网络中断；乐谱定位只改变乐谱进度，不倒退记录时间。首次有效的 START／暂停／定位及其顺序保存到同一记录时间轴。回放及叠加恢复初态并自动执行它们，锁定新的手动指挥；控制权必须在工程生效入口落实，不能仅禁用一个可见按钮。
8. **初态与恢复**：每遍从共同零点恢复作品需要的触点、乐谱、控制及声音状态，再同步开始已有回放与新输入。原有页面、服务器或音频的自主推进不能覆盖回放主权；保持同步所需的传输或存活消息不作为新演奏重复写入。回放开始、停止、失败和换记录均释放旧回放来源，避免残留声音及双重时间驱动。
9. **固定长度**：第一遍正常停止确定总时长，后续回放／叠加到同一末尾自动结束，叠加自动保存；新增或重录不延长记录。需要改变总时长或共同指挥过程时新建记录，不在原记录中隐式调整。
10. **身份分离**：记录演奏者身份独立于乐谱选择序号、物理设备和瞬时连接标识。真实录制按工程接纳的独立来源建模，序号及其变化是工程属性；不越过作品自身的编号／入场规则。每遍新增叠加生成新的记录身份，回放为各记录演奏者建立独立工程运行来源。
11. **来源准入**：普通录制与叠加接收全体实际获工程接纳的现场演奏者，叠加不按最近注册的单一来源锁定；起录后加入同样有效。每轮逐源建立独立记录身份，纯回放只由记录驱动。App 不检查编号是否符合用户预期，不轮询选择完成，也不新增强制设备选择、准备向导或自动切号。工程须确认多人轮次协议，不向旧适配器静默降级。
12. **继承与替换**：新增叠加继承已有演奏信息一次并加入新轮次；既有回放不经现场录制路径再次追加。整轮重录排除目标轮全部旧演奏者及其初始触点，其他轮原样保留。合并结果成功保存后才发布；放弃、失败或异常不能提前修改已有完成记录。同序号不构成替换依据。
13. **提前结束**：叠加或重录的“停止并保存本遍”保留已录部分，剩余区间视为未演奏，总时长不变；整轮重录不接回被替换轮的后半段旧输入。该结束边界释放本轮全部叠加或回放来源仍按住的控制；普通真实演出停止录制不释放其正在演奏的现场来源。“放弃本遍”丢弃本次新增／替换内容，保留原记录。
14. **断线**：普通演出记录实际加入、离开与重连。叠加断线不暂停共同时间，也不自动重做本遍；工程按自身释放和恢复规则处理。重连依据工程明确的恢复信息归回本遍身份，不能把瞬时连接变化当作新增叠加。用户自行决定停止保存或放弃。
15. **持久化与携带**：App 按工程自动保存并在重启后呈现记录；独立记录文件支持导出与打开，工程另行提供，默认不混入演出工程包。保存格式带版本、完整性及工程／适配协议来源，不以相同显示名或相同 manifest 标识静默合并不同来源。移动至另一设备后重新核对所提供工程及兼容性，不携带旧运行权限或本机绝对路径依赖。
16. **工程内容变化**：记录关联当时实际运行的工程内容，保留原始来源，不能只依赖当前未保存草稿或版本显示名。工程内容变化时明确提示，由用户选择以当前兼容工程回放或叠加，声音与新结果按当前工程解释；后续结果的解释来源与原始演奏来源应能区分。协议不兼容必须拒绝，不能强行降级；App 不自动备份整工程或切换工程版本。
17. **异常与发布**：尽量保留已经耐久写入的信息，并明确标记未完成；已有完成记录保持完整。本遍只能从头重录，不从断点续录。保存失败显示真实失败并保留可恢复信息，不伪装成功或把部分结果发布为完成替换。未完成数据须可识别，不把原型中“回放已保存部分”的建议当成已批准的完整功能。
18. **运行收尾**：用户主动关闭、重启、切换工程或退出等确实结束当前运行的动作，先按停止并保存收尾，复用原有确认与关停流程，不叠加录制确认。保存失败遵守上一条，不能以关停成功掩盖记录失败。隐藏窗口／面板不收尾；模式切换按既有非对称接续规则，保留同一运行时继续记录，实际结束才收尾。
19. **界面**：共用底栏入口和轻量面板在创作／池主演出及展开 monitor 时可用，底栏持续显示状态与记录经过时间，乐谱进度另表达。列表进入详情后按录制轮次管理，不要求追踪记录演奏者 ID 或序号；演出模式不提供叠加操作。沿用系统字体、四主题、键盘可达焦点、既有 i18n 和逻辑方向布局，不新增独立工作台或轨道编辑器。
20. **首版控件**：提供录制、停止、从头回放及创作模式叠加／整轮重录、保存或放弃本轮，列表提供导入／导出及删除整份记录，详情可删除单轮。录制停止或正常完成自动保存。删除轮次保留公共初态／指挥／总时长，最后一轮删除后允许空记录；活动记录及其轮次不可删除。App 不新增暂停续播、任意定位、变速或循环控件；工程已有指挥在首次录制时保留，在回放／叠加时受共同记录自动驱动，二者范围不能混淆。
21. **工程核验**：III 必须恢复触点互动及影响声音的派生控制，不能只播放可见点；runes 必须装载保存的实际 composition 和指挥初态，保持同序号多来源独立发声、持续保持和释放。以实施时现行的服务器管理乐谱／进度接口为依据，不照搬早期 monitor 自主生成和 POST 的历史接线，也不隐式改变工程原有声音节点资源政策。
22. **旧记录兼容**：旧格式全部内容按一轮“已有内容”展示，原文件完整保留；之后新增轮次明确保存归属。不能按编号或事件时间猜测旧轮次，未采集触点不能伪造恢复。

## Testing Decisions

用户已在本轮确认以下测试边界：以 App 公开操作／命令为主入口，观察真实工程、持久文件与受管进程／网络结果；界面补测可见工作流，媒体与声音保留实机验收。

- **优先一条最高行为接缝**：通过 App 对外的记录控制操作，连接真实工程适配、临时持久化与回放驱动，观察保存文件的公开内容／状态、工程实际接纳的来源、有效指挥和可观察演奏结果。用可控共同时间推进首遍、叠加、停止与恢复；不依赖私有 reducer、线程调用顺序、内部缓存或类的形状。桌面 UI 不必参与每个时间轴用例，但接缝必须覆盖正式控制和持久化行为，不能用两个互不相连的模拟器替代闭环。
- **复用现有先例**：沿用 session／创作测试流程的运行归属、重复操作与迟到回执测试模式，以及原生本地 Node 集成 fixture 的真实进程、HTTP 就绪、临时目录和有界清理。涉及端口时复用现有 fixture 设施，不靠固定等待、重复重跑失败测试或降低全局并发“证明”通过。只有时间来源及输入可控，适配器、保存和回放业务路径使用正式实现。
- **共同时间验收**：记录第 0 秒起录、第 5 秒 START，再暂停、定位倒退和继续；第二遍不手动 START，在同一记录时刻自动重现，准备等待与暂停时长均保留。起录时已经演奏的状态可恢复；末尾只触发一次结束和保存；晚到输入不延长时长或污染下一遍。
- **身份与来源验收**：同一设备先录一轮→3，再录一轮→3，第三轮→5，来源独立；另测两人同轮、起录后新窗口加入和已有窗口复用。重录第一轮时只播放其他轮，放弃或失败保持旧版；重录多人轮改为一人时不接回其他人的旧内容。同序号离线释放与重连不影响另一位。纯回放拒绝现场音乐输入，叠加接纳全体实际有效来源，回放不会再次录入。删除首轮须排除其初始按住触点而保留公共乐谱与指挥；删除最后一轮不丢失共同时间框架。
- **保存与故障验收**：正常完成、自动末尾、提前保存、明确放弃、写失败、工程异常退出和 App 再次启动，验证完整记录不被损坏、未完成状态诚实、替换只在成功发布后生效。提前结束的重录后半段为空且释放控制；未完成记录不具备断点续录能力。关闭／重启／换工程／模式接续覆盖真实运行路径，隐藏界面继续记录。
- **兼容与携带验收**：独立记录导出后在另一工程位置／设备环境打开；分别覆盖正确工程、内容变化后的明确选择、不同物理来源、缺失适配、记录格式损坏与版本不兼容。不能凭导出按钮回执或 manifest 标识相同判定可回放；导入失败保留已有记录，当前工程重新解释不抹掉原始来源。
- **可见界面验证**：用既有组件测试体系检查列表／详情、整份及单轮删除、整轮重录、自动保存后详情接续、底栏状态／计时、返回列表／收起接续、模式权限、错误和明确选择。测试用户可见行为，不写仅镜像内部实现的断言，不把 HTML 内存样例当成业务验收。
- **真实作品与声音验收**：III 完成至少三遍互动并验证距离控制与发声，runes 验证实际随机乐谱还原、首次 START 延迟、暂停／定位、同序号多来源与释放。自动化可检查工程控制输出，真实声效仍须用户在实际 App、设备和声音链路上验证；不要求纯音频随机逐样本一致，也不能以无声音异常日志代替听觉验收。
- 新业务逻辑随实现带有上述行为测试，工程侧执行各自要求的检查；App 实施完成必须默认并发运行 `npm run check:all` 全绿。开发服务器由用户启动并回报结果，真实平台及发行验证独立记录，不能把本次规格或仓库检查视为已实现。

## Out of Scope

- 音频录音、音频轨导出、保存纯音频合成随机状态或逐样本一致的声音恢复。
- 演出分支、多个候选录次管理、局部补录、轨道编辑、剪切拼接、冻结前遍乐谱、编辑已有指挥过程。
- App 的暂停续播、任意定位、变速与循环回放控件；不因此删减作品已有的指挥能力。
- 断点续录、把未完成数据自动修复成完整记录、未经完整性验证的片段回放承诺。
- 编号监控、准备向导、就绪检查、按编号自动匹配重录对象或强制选择输入设备。
- 为任意未适配工程自动推导记录协议、通用抓包回放、按谱面 DOM 猜测音乐状态。
- 自动备份整个工程、自动切换工程版本、把记录默认打入演出工程包、云同步或跨互联网记录管理。
- 给池客增加本机工程服务、App 托管的 scsynth 或全场记录控制；重命名、局部片段及单人轨道编辑。

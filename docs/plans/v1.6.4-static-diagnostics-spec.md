# v1.6.4：静态工程诊断与 CLI

状态：代码与自动验证完成，用户 App 验收通过；Intel CLI 与装机验收待回报。

GitHub Issue：[193](https://github.com/xO-xN/PNDS-App/issues/193)，标签 `ready-for-agent`。

## Problem Statement

创作者和外部 agent 需要在不启动或改变演出的情况下，了解工程声明、资源、依赖和共享引用的问题。现有启动预检包含遗留进程清理，不能直接当作只读诊断；分散的错误也不便于机器理解或定位多个独立问题。

## Solution

提供同一确定性的静态工程诊断能力，供 App 和 `pnds check` 类 CLI 使用。结果明确检查范围、问题、严重性、原因与未验证内容，输出可读与结构化报告。检查不启动工程、不占用运行资源或清理进程，未完成工程也能获得实际可检查的事实。

## User Stories

1. As an 创作者, I want 不启动工程即可检查, so that 不影响当前演出。
2. As an 外部编程 agent, I want 在命令行得到静态结果, so that 修改后能自主取得工程反馈。
3. As an 创作者, I want App 与 CLI 使用相同规则, so that 两个入口不会报告相反结果。
4. As an 创作者, I want manifest 格式与约束问题明确定位, so that 我知道需调整的声明。
5. As an 创作者, I want 入口和工作目录按工程范围检查, so that 非法路径不会被当成有效工程。
6. As an 创作者, I want 声明引用的资源缺失被指出, so that 我能补齐运行资产。
7. As an 创作者, I want 生产依赖与共享引用分别检查, so that 能辨认缺失的来源。
8. As an 创作者, I want 共享版本不匹配有可读原因, so that 我能更新引用或工程。
9. As an 创作者, I want 未完成工程也获得可检查结果, so that 创作初版不会只有一个笼统拒绝。
10. As an 创作者, I want 多个独立问题共同报告, so that 不必修一个再发现另一个。
11. As an 创作者, I want 依赖前提不足时显示未执行原因, so that 不把跳过误当通过。
12. As an 创作者, I want 区分阻断、提示与未验证, so that 能安排下一步工作。
13. As an 外部编程 agent, I want 稳定的结果结构与退出状态, so that 可以读取实际失败而非猜测日志。
14. As an 创作者, I want 报告说明检查对象与版本, so that 不把旧结果当当前工程。
15. As an 创作者, I want 工程变化后旧结果被标明过期, so that 修改后知道需要重检。
16. As an 创作者, I want 静态通过不被称为运行通过, so that 真实声音和页面仍有明确验收。
17. As an 创作者, I want 检查不保存草稿或修改工程, so that 读取动作不会写入内容。
18. As an 创作者, I want 检查不清理或终止进程, so that 候选工程诊断不会停止演出。
19. As an 创作者, I want 静态检查在 App 活动运行时仍可用, so that 可以准备下一工程。
20. As an 创作者, I want 大文件、不可读内容或未知条件有说明, so that 不完整信息不会被隐瞒。
21. As an 创作者, I want 诊断不联网安装依赖, so that 离线与现有运行环境保持稳定。
22. As an 维护者, I want 复用既有契约校验, so that 不维护第二套 manifest 或打包标准。
23. As an 维护者, I want 在干净环境复现 CLI 检查, so that 工具不依赖维护者电脑路径。
24. As an 创作者, I want 中英和键盘操作下结果清晰, so that 诊断与工作台一致。

## Implementation Decisions

- 优先在现有 manifest、路径、资源、生产依赖与打包静态校验之上形成一个高层诊断入口，供 UI／CLI 复用；不以组件为边界复制校验。
- 静态入口与含清理副作用的运行预检分开，不能直接包装旧 preflight 当只读服务。
- 结果记录工程身份、检查范围、所观察输入、问题代码／严重性、可读原因与未执行项；明确依赖前提，不编造动态协议关系。
- 涵盖 v1.6.2 的共享库引用与版本可用性，保留自带依赖及已批准运行契约；保存可编辑声明、创作打开、运行和可打包条件分别表达。
- 仅对确定性可得事实给出结论，依赖目录存在不等于所有运行行为正确，SynthDef 文件存在不等于声音已验证。
- CLI 提供机器可读结果及清楚退出含义，成功只代表所选静态检查；实现具体参数保持两个入口规则一致。
- 检查不保存、安装、启动、清理进程或替换 App 运行状态；App 活跃期间仍可读取并诊断。

## Testing Decisions

- 最高接缝是同一工程输入通过 App／CLI 诊断后得到的公开报告。复用既有 manifest、bundle、依赖与路径测试，比较行为与副作用，而非私有函数拆分。
- Rust 临时工程覆盖合法、未完成、无效声明、资源／依赖／共享缺失、路径逃逸、不可读和前提不足；报告多个独立问题并明确跳过项。
- 为无副作用提供正向证据：原文件不变，活动运行身份不变，没有启动／关停／清理调用。既有 session 流程与预检归属测试为 prior art。
- CLI 使用真实临时输入验证结构、退出状态和 App 同结果；不依赖开发服务器、维护者特定目录或外部网络。
- 静态通过与运行／声音未验证分别断言，不用 fixture 文件存在冒充作品完成。
- 新业务逻辑和文档随实现同步，App `npm run check:all` 全绿。

## Out of Scope

- 工程启动／关停、自动清理、音频设备测试、联网探测、依赖安装和自动修复。
- 全源码 AST 索引、推断任意动态音乐协议、资源播放器和作品完成度评价。
- CLI 与 App 分别维护两套规则，或静态检查执行工程代码。

## Further Notes

本版可独立提供静态反馈，无需等待运行检查；其结果是后续助手与临时副本流程的输入，不替代真实 App、手机或声音验收。

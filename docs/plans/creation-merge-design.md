# 工程版本合并与创作助手协助

状态：已按确认方案接入 App。2026-11-15。实现边界见[合并候选](../developer/merge-candidates.md)；自动化检查与实机验收分别记录。

创作者已确认 Q1–23 的最终决定，其中 Q10 的“合并后再试听”和 Q19 的逐文件确认已被后续决定替代。本文件保留完整需求与验收边界；后续已通过 HTML 核对并明确要求将整套合并方案接入 App。

领域语言见 [CONTEXT.md](../../CONTEXT.md)，核心边界见 [ADR-0021](../adr/0021-review-merge-candidates-before-publication.md)。本规划扩展 [ADR-0011](../adr/0011-creator-git-version-navigation.md) 原先排除通用合并的产品范围；工作区已接入，发布版本另行验收。

## 1. 创作者操作流程

**选择来源 → 准备合并候选 → 人工／助手处理 → 可选检查和测试 → 一次完成合并。**

1. 在版本树选中来源，右侧点“合并到当前版本”。目标始终是实际当前工程版本；仅浏览其他节点不改变目标。同一／已包含直接说明结果，结束操作。
2. 需要改变当前版本时，先保存为工程版本或明确放弃未记录修改，结束未完成的普通助手任务，再生成独立候选。实际工程在 App 内转为只读；分叉候选可编辑，快进候选只读。
3. 左栏查找变更及冲突，中间处理结果。可在现有助手页签主动启动“合并协助”，也可全程人工完成。模型未配置、离线、失败都不阻断人工路径。
4. 点击检查、测试或完成时，统一保存并核对当前候选。没有逐文件“标记已解决”步骤；二进制、删除／修改等仍需决定采用什么内容。需要新编译产物时明确采用，变化进入候选列表。
5. 可选点“测试合并结果”，从候选的确定保存快照启动乐谱服务器，使用现有预览、音频、演奏者窗口及设备／网络能力。原运行需先明确停止。继续修改后提示重新测试。
6. 对整个结果点一次“完成合并”。原生核对冲突、格式、路径、基线及运行清理后，快进到来源，或创建双父合并版本；完成后不自动开演。同步／备份失败单独重试。
7. 发布前可取消并丢弃候选，也可离开后回来“继续处理”。外部变化使候选失效时“重新准备”。正式应用一旦开始，其失败走“继续恢复”，不再提供暗示回滚的普通取消。

## 2. 首版范围与 Git 语义

### 来源范围

| 来源                                             | 首版行为                                                        |
| ------------------------------------------------ | --------------------------------------------------------------- |
| 当前工程版本树中可选择的本机提交                 | 可以作为来源，随后核对版本关系与准入条件。                      |
| 手动从 GitHub 取回、已作为本地路线进入树中的提交 | 可以使用；“本机”不限制提交最初来自何处。                        |
| 仅存在于远端跟踪引用的 fetch 结果                | 不保证在现有树中可选；首版不扩展远端枚举或提供自动 fetch。      |
| clone 到另一个目录                               | 另一个仓库；合入当前工程前，需在 App 外将来源提交引入当前仓库。 |
| GitHub ZIP、普通复制的文件                       | 不携带原提交历史，不作为首版真合并来源。                        |

不包含跨仓库导入、ZIP 内容整合、cherry-pick／仅吸收功能或自动连接无关历史。普通 GitHub 更新保持现有快进入口；本功能消费已在树中可选的提交。

### 关系与路线

| 关系                                     | 结果                                                                               | 候选编辑                                                       |
| ---------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 同一版本，或来源已包含在当前历史中       | 显示“已包含”，不改文件／index／HEAD／路线，不触发备份。                            | 不建立候选。                                                   |
| 当前位于来源历史中，可快进               | 精确前进到已有来源提交，不创建新提交。                                             | 只读，可审阅、检查和测试。进一步修改在快进后的普通创作中进行。 |
| 真正分叉，能构建受支持的可用共同基线     | 新版本的第一父为原当前版本，第二父为选定来源。最终树等于原当前树时仍创建合并版本。 | 可人工／助手调整。                                             |
| 没有共同历史，或无法构建受支持的共同基线 | 准备阶段说明原因，交外部 Git 处理。                                                | 不进入无法完成的冲突处理流程。                                 |

多共同基线等复杂历史须由原生能力验证；无法给出受支持三方结果时明确拒绝，不擅自挑一个祖先或线性化历史。

当前附着命名路线时推进该路线，来源路线不动。当前处于历史位置时，只要结果会改变当前版本，就自动建立新路线；快进也适用，但不新建提交。同一／已包含不建路线。

只读关系判定先于清理门槛：已包含时不要求保存／放弃改动、结束助手或停演。准备前若用户保存了新版本，实际 HEAD 已变，必须重新判定关系和准备目标，不能沿用旧预览。

## 3. 布局与文件处理

保留真实 App 的 226px 窄文件侧栏、上方横向版本树及其右侧操作区，下方仍以逐行差异和结果编辑为主。树的时间轴和真实父子关系沿用现有规则，切换或选中节点不重新排序。

| 区域               | 候选阶段内容                                                                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 左侧栏             | 候选相对目标的实际变更、仍需处理的冲突路径、状态及搜索。只列相关内容，不恢复“变更／全部”切换。结果等于目标的待处理冲突不能提前从列表消失。                       |
| 中间               | 逐行差异与结果编辑；按需折叠查看共同基线、当前及来源快照，避免默认铺开多栏。快进结果只读。                                                                       |
| 树右操作区         | 来源与目标、简洁进度、候选名称、助手入口、完成和取消。详情直接排布，不增设重复菜单层。                                                                           |
| 现有助手页签       | 明确显示本次“合并协助”作用域，不另建聊天侧栏；来回切换保留文件选择、手工草稿和滚动状态。                                                                         |
| 右侧现有预览与底栏 | 复用测试配置、monitor、演奏者测试、启动／停止与控制台；候选测试时常显“合并候选 · 未合并”，原工程仍运行时显示其真实归属。内部修订号和临时路径不作为主要用户信息。 |

候选状态放在操作区，不伪装为“未保存改动”虚线树节点。只有正式完成后才出现真实合并关系。纯历史合并没有文件变化时，显示关系说明，仍允许完成，不伪造变更文件。

### 文件策略

| 情况                                                       | 处理                                                                         |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 普通新增、修改、删除及可自动处理的重命名，无冲突           | 原生 Git 计算结果。                                                          |
| 支持的文本冲突                                             | 人工或助手编辑候选结果。保存及批量操作时更新原生冲突状态，不额外逐文件批准。 |
| 普通二进制双方修改                                         | 创作者整文件选择保留当前或采用来源。助手可解释影响，不任意改写二进制。       |
| 删除／修改                                                 | 创作者选择删除或保留修改结果。                                               |
| 复杂重命名、路径占用、文件／目录冲突                       | 准备时说明，首版转外部 Git；不等用户处理完其他文件后才拒绝。                 |
| 符号链接、子模块、保护／敏感路径、超限或不受支持的仓库形态 | 继续执行现有原生准入边界，助手不能绕过。                                     |

缺失文件与零字节文件分别表示。原生保留本次冲突对象、双方输入及当前结果，不以全仓搜索 `<<<<<<<` 判定冲突；合法原有字符串不应被误拒。AI 声称完成、删除标记、health ready 或有声音都不代替必要校验。点击“测试合并结果”或“完成合并”即统一提交当前处理结果供原生核对，没有额外的“标记已解决”动作。

## 4. 候选所有权与助手

合并候选与实际工程文件、真实 index 和已保存版本独立。准备与人工／助手编辑不改变实际工程历史；发布前取消只丢弃私有候选及其检查点。

准备前结束未完成的普通助手任务，保留聊天与已保存文件，退休旧执行检查点。候选期间禁止普通 Work、保存、版本切换／记录／恢复、真实工程编译产物发布等旁路写入；覆盖菜单、快捷键、控制台、其他窗口、模块与交接入口。不能只用版本页的 `gitBusy`。原生统一执行门禁，前端展示同一状态，并等待已开始的写入完成交接。

助手的每一轮工作由创作者明确启动：

- 可读取固定共同基线、当前、来源及最新候选中的必要受支持文本，遵守既有隐私、路径、尺寸及分页限制。
- 只在真正分叉的候选内修改本次合并需要的文本和关联文本，可按规则新增／删除。快进只解释，不写结果。
- 重要创作歧义先提问。问题及回复属于该候选任务，不因普通聊天切换而改变写入目标。
- 每轮开始前保存手工候选并建立检查点；保存失败不启动。该轮拥有候选写入权时人工只读，不能同时测试新快照、采用产物、撤回或完成合并；先“停止并编辑”并等在途原生操作结束。
- 暂停／等待提问仍可能持有本轮任务，不能用模型 `idle` 推断已交还人工。旧回复／工具结果必须核对会话、候选修订、任务及权限，不能晚到覆盖手改。
- 停止或模型失败保留已完成候选修改，不等于取消整个合并。完整展示本轮差异，支持撤回最近一轮实际触及的内容。
- 撤回预先核对受影响内容；若已存在后续手改，整次撤回拒绝并保留现状，不部分恢复或覆盖。未被该轮触及的手改始终保留。

助手没有实际工程写入、最终发布、Git／远端操作、任意 Shell 或自动停演权限。候选测试已运行旧修订时，助手可按明确任务修改独立候选，但不能自动替换正在运行的内容。

## 5. 检查、编译产物与交互测试

### 三类门槛分开

| 类别           | 规则                                                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 合并必要条件   | 所有冲突有完整结果、声明可解析且符合格式、路径／类型／大小等准入、Git 状态及来源／目标／候选有效，所需运行清理完成。不可跳过；必要校验无法完成也不能当作通过。       |
| 测试启动前提   | 依赖、所需已采用产物、设备、端口和运行资源等符合普通创作测试契约。缺少时可以无法测试，但不自动变为禁止 Git 合并。                                                    |
| 代码及运行报告 | 静态诊断必须运行并展示；编译、已有测试、受控检查和人工交互测试按需执行。通过、失败、未执行、不可用、取消、过期／未知分别显示。可选检查失败时允许创作者明确仍然合并。 |

现有静态诊断的失败多为 error，`staticPassed` 要求全部通过；普通保存却允许合法声明缺少待编译产物。因此不能直接以全部 error 或 `staticPassed` 作为合并开关。实施时按结构化诊断种类分类硬门槛与代码／环境问题，不靠文案匹配。候选变化使相关旧报告过期；必要最终校验必须针对确切当前结果。

### 编译产物

检查默认在私有副本验证，不悄悄修改候选。分叉候选可在成功编译后明确“采用编译产物”：核对当前输入与编译收据一致、输出为受支持产物且路径通过准入，再作为可见候选变更保存，形成新修订并使相关旧报告过期。模型可建议采用，不获得任意二进制写入权限。

快进检查的临时产物不进入结果，最终文件树始终等于来源提交。来源缺少产物时可以无法试听；需要修补时先在普通创作生成新来源版本，或快进后继续创作，不能在快进候选暗中修补。

### 测试合并结果

测试可选，无需额外点击“测试通过”。正常流程为处理结果后直接启动服务器，观察／试听／交互，再决定是否整体完成；环境不可用或测试失败时仍遵守前述可审阅失败规则。

- 保存并统一核对候选后，固定一个修订，从它建立可丢弃运行副本。运行的是该候选的已保存文件；若需新 SynthDef，先明确采用，再启动该修订，不能测试临时新产物却宣称验证了尚未采用它的候选。
- 沿用普通创作测试的受支持音频模式、monitor、演奏者测试窗口、手机／设备接入和工程通信；Internal 音频、External OSC、已配置 telematic 等不在实施时悄悄降为仅页面／None 模式。沿用当前明确配置，不因临时路径改写真实工程偏好，不安装依赖。
- 只复用一个主运行引擎和独占运行租约。若原工程仍运行，操作明确为“停止当前运行并测试合并结果”；需确认停止及清理后再启动，不由助手或后台自动停演。
- 预览普通／展开状态都标明“合并候选 · 未合并”。启动、停止、health、端口、音频、网络入口、页面刷新／重启、测试窗口、控制台、网页存储及参数预演都绑定候选运行归属与代次。临时目录不能成为实际工程或最近工程记录。
- 运行时可继续编辑独立候选。运行仍属于启动时的修订；新改动显示“正在试听修改前的内容”，显式重新测试，不静默热更新。旧原工程运行的只读观察不能充当候选验证。
- 相对路径日志、缓存及运行输出留在副本，不自动进入候选。副本不是操作系统沙箱；这里只保证 App 的输入／写入归属及正常相对产物隔离，最终仍核对真实工程基线。
- 完成、取消、候选失效、切换工程或退出前停止候选运行，确认所属进程组、页面、端口与音频资源清理。失败保留清理所有权，不宣称已释放。恢复候选不自动重启测试，完成后也不自动重启原工程。

## 6. 状态与新鲜度

候选生命周期、人工／助手所有权及运行子状态分开建模，避免一个 `busy` 覆盖所有含义。

| 候选状态               | 可操作范围                                                     | 下一步                                 |
| ---------------------- | -------------------------------------------------------------- | -------------------------------------- |
| 准备中                 | 只读计算、准入与保存固定输入。                                 | 进入候选或提前说明不支持。             |
| 处理中，人工持有       | 浏览实际工程，编辑分叉候选，检查／测试，启动助手，完成或取消。 | 动作均核对当前会话与修订。             |
| 处理中，助手持有       | 阅读候选、回复问题、停止该轮；已有旧修订运行可保留。           | 等写入交接后恢复人工。                 |
| 待继续                 | 展示已保存候选，真实工程门禁保留，不自动授予写入／执行。       | 重新核对后“继续处理”或丢弃。           |
| 失效，只读             | 停止助手及候选运行，保留候选与旧报告供参考，禁止应用。         | 丢弃或“重新准备”，不自动移植旧处理。   |
| 正式应用中             | 冻结结果，不提供取消；正常退出等待本次应用到可判定状态。       | 本地完成，或进入恢复。                 |
| 应用失败／中断，待恢复 | 候选冻结、实际工程继续只读；先核对现场。                       | 明确“继续恢复”，或保留现场转外部处理。 |
| 本地完成               | 解除本次候选编辑门禁，展示真实版本结果。                       | 附带步骤失败只重试对应步骤。           |

运行子状态为未运行、启动中、运行中、清理中、已清理／清理未确认，记录修订与 generation。候选本身存在时不长期占用全局运行租约；只在实际运行／检查／发布时持有。门禁按物理工程生效，其他工程不因待处理候选整体只读，资源争用仍按现有运行规则处理。

来源固定为选定提交并在私有候选中保留必要输入；来源路线后续前进不换源。目标固定为物理工程、实际 HEAD 与路线身份；即使新路线仍指向相同提交，也要重新核对归属。受保护的真实文件、index、HEAD、目标路线或影响准入的配置变化使候选失效。无关路线或版本管理范围外的日志变化不单独使其失效。

所有必要校验、检查报告、助手写入、撤回、测试和最终确认都绑定确切身份与内容修订。新鲜度不是仅靠轮询 UI，原生在每次敏感操作及最终发布前重新校验。

## 7. 持久化、发布与恢复

### 发布前

候选、固定输入、冲突账本、手改、最近一轮助手检查点和报告进入工程私有创作数据边界，继续从 Git、打包、普通文件工具和运行输入中排除；避免复制测试输入时递归带入候选自身。不得借普通工程草稿或真实 index 存储候选。

同工程切换页签保留进度与已明确启动的助手任务。切换工程／正常退出保存候选并暂停助手、停止测试；保存或清理失败保留可重试状态，不假称已安全完成。异常退出恢复最近成功保存的内容，不将半段流式输出当作完成。重新打开先核对，明确继续，不自动请求模型、检查、测试或发布。

发布前的取消丢弃候选，但先停止助手并完成运行／写入清理。清理未确认时仍处于取消处理中；不得提前放行发布或下一运行。

### 正式应用

最终确认固定操作 ID、来源／共同基线／旧目标、当前候选树、路线决定、作者及提交元数据，持久化发布意图后才开始真实副作用。真实仓库所需对象及内部保留引用在此阶段发布；准备阶段只使用私有候选保留，不新增可见版本或改变真实 HEAD／refs／index。

分叉合并只创建一个确定的结果提交，父顺序为原当前、选定来源；恢复始终复用其 OID。快进固定为来源 OID。发布记录覆盖对象与保留、文件、refs、index 和后续同步的意图／结果；文件步骤需能辨认每条路径的旧值、预期新值和外部第三种内容。结构上不承诺跨文件／ref／index 的整体原子回滚。

最终持有新鲜身份、原生写门禁、Git 锁及所需运行租约，再校验真实状态。用户双击、超时重试、前端重载不得创建第二个结果或再次推进路线。恢复也不能仅信任日志阶段标签，必须与实际文件／refs／index 对照。

### 三种恢复结果

| 实际状态                             | 行为                                                                                 |
| ------------------------------------ | ------------------------------------------------------------------------------------ |
| 本次结果已完整应用                   | 认定本地成功，只重试尚未完成的名称、刷新、编辑器同步或备份步骤。                     |
| 与本次操作的预期中间状态一致         | 展示可继续恢复；用户明确继续后，只补齐未完成步骤，复用同一结果。                     |
| 外部后续修改、引用冲突或无法可靠辨认 | 保留实际内容及候选，停止自动写入，给出可核对的外部处理指引。不强制重置、覆盖或回滚。 |

正式应用开始后即使失败，也不恢复普通“取消合并”按钮。外部处理完成后必须重新核对现场，明确结束或继续该恢复记录，不能靠清除 UI 标记解除原生保护。

## 8. 名称与 GitHub

分叉新版本默认显示名“合并〈来源版本〉”，按现有铅笔原位编辑。快进沿用来源版本名称；历史位置新路线沿用现有唯一命名规则。版本显示名仍是本机仓库标签，不承诺随 push／clone 传播。

合并完成沿用目标路线已开启的自动备份；新路线不继承开关，保持手动，来源路线不变。不自动 fetch、跨仓库导入或强推。远端将获得的全部新增历史继续执行既有保护检查，不能只检查最终树。

本地结果、备份排队、远端发送分别记录身份与结果。备份失败不撤销本地合并，也不重做合并；重试不得把旧结果排到已更新路线之前。名称元数据或刷新失败同样保留本地完成收据。

## 10. 验收矩阵

新增业务随改动带测试；使用临时真实 Git 仓库、可控故障和运行所有权夹具验证行为，避免只镜像实现或以 mock ready 代替实机音乐验收。

| 范围         | 必须通过的结果                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 关系         | 同一／已包含无副作用；快进无新提交；分叉的父顺序正确；相同文件树仍合并；无可用基线提前拒绝。                                   |
| 路线         | 当前路线推进、来源不动；历史位置快进／合并另建路线；无操作不建路线；准备前保存后重新分类。                                     |
| 文件         | 普通自动合并、文本、二进制双改、删除／修改、普通重命名；复杂路径／保护／超限提前拒绝；缺失不等于空文件。                       |
| 无逐文件确认 | 保存／测试／完成统一核对原生冲突结果；没有重复批准按钮；原有合法标记字符串不误判，未决选择不能因结果等于目标而消失。           |
| 隔离         | 准备、编辑、检查、测试、取消不提前改变真实文件／HEAD／refs／index；所有 App 写入口受统一门禁。                                 |
| 新鲜度       | 目标、索引、受保护真实输入或路线身份变化失效；无关日志不失效；来源路线前进不换源；晚到结果不能污染新候选或另一工程。           |
| 助手         | 无模型可完成；只写候选；提问、停止与在途写入交接；人工手改受保护；撤回遇后续改动整次拒绝；失败不自动发布。                     |
| 检查与产物   | 必要失败不可绕过；可选失败／不可用／未执行／过期如实显示；明确采用才改变候选；快进树不因编译改变；旧报告不冒充新结果。         |
| 候选测试     | 可见 monitor／声音来自确定候选；完整现有音频与设备／网络范围；停止旧运行、独占租约；修改后过期、显式重测；运行输出不自动采用。 |
| 生命周期     | 页签保留；切换／退出保存并暂停；失败不假称已清理；重启明确继续；不自动恢复模型、测试或发布。                                   |
| 发布恢复     | 每个对象／文件／ref／index 边界注入失败和崩溃；重复完成／恢复不重复提交；外部新内容不覆盖；取消不伪装回滚。                    |
| 附带步骤     | 名称、刷新、编辑器同步、备份排队／发送分别失败与重试，本地完成不撤销，旧结果不覆盖更新队列。                                   |
| 实机界面     | 保留窄侧栏与既有整体布局，中英文长标签、RTL、键盘及缩放可用；无假虚线版本；时间轴仍左旧右新，双父曲线正确。                    |
| 实机运行     | macOS 实测 Node、音频模式、monitor／演奏者窗口、设备／手机、停止清理及再次启动；记录实际覆盖与未覆盖范围。                     |

## 11. 实施顺序与完成标准

阶段是开发拆分，不把缺少隔离、人工路径或恢复保护的半成品作为最终交付。每个阶段随业务逻辑补测试，真实发布前就必须具备阶段恢复。

| 阶段                  | 内容                                                                                         | 阶段完成判据                                                               |
| --------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 1. 原生候选基础       | 关系／共同基线与冲突分类、固定输入保留、候选持久化／修订、新鲜度、统一写门禁。               | 未接 UI／模型也能可靠准备、失效、暂停和恢复候选；无操作无副作用。          |
| 2. 人工闭环与发布     | 窄侧栏、结果编辑、必要内容选择、无逐文件批准、路线／名称、确定结果及发布阶段恢复、附带收据。 | 无模型可完成支持范围的快进／合并；重复调用和中断不重复生成结果。           |
| 3. 候选检查与交互测试 | 门槛分类、编译／明确采用、受控检查、固定快照完整创作测试、运行归属／清理及过期提示。         | 真实候选可测试；快进精确保树；旧运行不冒充新候选；取消／离开无残留所有权。 |
| 4. 可选助手           | 固定三方上下文、候选专属工具、按轮交接、创作提问、完整差异与受保护撤回。                     | 模型停止／失败仅影响该轮，不破坏人工路径或自动发布。                       |
| 5. 整体验收与契约     | 跨阶段故障／重启、外部修改、晚结果、备份重试、实机 UI／声音／设备及文档。                    | 验收矩阵有证据，`npm run check:all` 全绿，实机覆盖如实记录。               |

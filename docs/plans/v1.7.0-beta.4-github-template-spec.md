# v1.7.0-beta.4 PNDS GitHub 模板、首次备份与公开工程目录

目标版本 **v1.7.0-beta.4**。本规格记录 2026-11-13 已确认的首版工作流。

跟踪票见 [#327](https://github.com/xO-xN/PNDS-App/issues/327)。首版流程的实机验收见 [#332 验收记录](../acceptance/332-github-template-release.md)。

> App 内的新建、建仓与首次上传以 [beta.4 创作工作台规格](./v1.7.0-beta.4-creator-project-versions-spec.md)（[#339](https://github.com/xO-xN/PNDS-App/issues/339)）为准。本文保留官方模板快照、来源核验、历史保留、外部初始化和公开工程目录的约定。

## Problem Statement

创作者可以在 PNDS App 里从 Blank 离线新建工程、保存本地版本，再绑定 GitHub 仓库。现有建仓入口打开普通 GitHub 建仓页，绑定接受空仓或共享历史的仓库。创作者若改用 GitHub 的模板建仓，远端会先有自己的初始提交，现有绑定会拒绝这个与本地工程没有共同历史的仓库。

官方 `PNDS-Template` 默认分支仍提供上一代创作模板。希望用外部编辑器或 agent 从 GitHub 开始的创作者，需要能取得与 App Blank 一致的工程骨架和独立工程身份。维护者和其他创作者也需要从官方模板页发现愿意公开展示的 PNDS 工程。GitHub 的模板来源记录能核对单个仓库的来源，公开目录需要自己的发现入口。

## Solution

沿用 `xO-xN/PNDS-Template`。新版默认分支提供由 App Blank 生成器导出的模板快照。作者可以从 App 离线新建后，把已保存版本首次备份到从官方模板建出的仓库。作者也可以先在 GitHub 从模板建仓，在本机终端或 Codespaces 初始化工程身份，再用外部工具创作。

首次模板备份连接本地 Git 历史和 GitHub 的模板初始提交，以普通快进推送保留两段历史。App 在确认时显示目标和要推送的版本，断网或退出后可继续同一次备份。模板 README 提供公开工程目录入口，由创作者自行添加 `pnds-project` topic 加入。

## User Stories

1. 作为 App 创作者，我希望继续离线新建空白工程，以便没有 GitHub 账号或网络时也能开始创作。
2. 作为已在本地保存多个版本的创作者，我希望以后再建立模板仓库绑定，以便已有的工程 ID、文件和 Git 提交一起保留。
3. 作为首次备份的创作者，我希望从 Git 版本页进入预选官方模板的 GitHub 建仓页，以便少做一次查找和选择。
4. 作为仓库所有者，我希望在 GitHub 选择所有者、仓库名称和公开性，以便用自己的账号或有权限的组织管理工程。
5. 作为已授权部分仓库的创作者，我希望能把新仓授权给现有 PNDS GitHub App 并刷新仓库列表，以便选中刚创建的仓库。
6. 作为已经备份过其他工程的创作者，我希望保留普通空仓或共享历史的绑定入口，以便继续用已有工作流。
7. 作为在实验分支工作的创作者，我希望 App 说明需要切到与远端默认分支同名的本地分支，以便我决定哪个工程版本先出现在 GitHub 首页。
8. 作为首次备份到公开仓的创作者，我希望确认仓库、分支和要公开的已提交历史，以便控制公开范围。
9. 作为有未保存草稿或外部暂存改动的创作者，我希望首次模板备份保留这些工作状态，以便稍后继续编辑。
10. 作为用了旧版 App 的创作者，我希望新版官方模板仓仍可接受我已保存的工程，以便保留本地 Blank 版本和创作内容。
11. 作为较早建好模板仓的创作者，我希望模板 `main` 更新后仍能完成首次备份，以便沿用原仓库。
12. 作为已经在 GitHub 编辑过远端默认分支的创作者，我希望 App 报告冲突并保留两边的内容，以便我决定怎样处理。
13. 作为首次推送中断的创作者，我希望重开 App 后继续原仓库和原提交，以便不用重新建仓或重复产生合并提交。
14. 作为没有收到推送结果的创作者，我希望 App 识别 GitHub 已经收到的提交，以便恢复准确的备份状态。
15. 作为中断期间继续创作的人，我希望新增的本地版本都保留，以便确认过的首次备份和后续保存可以各自继续。
16. 作为已绑定仓库的创作者，我希望原绑定、已排队备份和分支同步照常工作，以便无需迁移仓库。
17. 作为外部编辑器用户，我希望从官方 GitHub 模板直接建仓并初始化，以便用自己的工具开始 PNDS 创作。
18. 作为 Codespaces 用户，我希望在新仓的浏览器开发环境里运行同一个初始化命令，以便无需打开 PNDS App 就能开始编辑和做无声预览。
19. 作为初始化新工程的创作者，我希望名称、作者、简介和独立工程 ID 写入相关工程文件，以便同名工程也拥有独立身份。
20. 作为重复执行初始化命令的创作者，我希望保留已有的 ID 和作品文件，以便恢复操作时不会覆盖已经开始的创作。
21. 作为从 GitHub 开始的创作者，我希望以后能用 App 打开或克隆原工程，以便继续使用原仓库、工程身份和历史。
22. 作为公开工程的创作者，我希望在首次公开备份或初始化推送后看到怎样加入目录，以便自主选择是否展示。
23. 作为已经发布 PNDS 工程的创作者，我希望补加 `pnds-project` 即可加入目录，以便沿用原有公开仓库。
24. 作为只想私有备份的创作者，我希望仓库选择和目录参与分别由我决定，以便私有工程保持在授权范围内。
25. 作为浏览工程的人，我希望从官方模板 README 打开公开工程目录，以便发现其他创作者主动分享的 PNDS 工程。
26. 作为模板维护者，我希望延续现有官方仓地址，并能核对不同版本的快照，以便历史来源链接和新工程的初始状态都可以查证。

## Implementation Decisions

- **官方模板仓。** 复用 `xO-xN/PNDS-Template` 的仓库身份和公开模板设置。旧 `main` 保存到 `legacy`，现有标签和 Release 保留。用普通提交更新 `main`。公开创作指引更新为 App 新建与官方模板主页两条入口，旧模板下载归入历史资料。
- **共享的 Blank。** 首版只提供 Blank。GitHub 模板快照由 App 使用的同一 Blank 生成器导出，保留可初始化的完整工程骨架。每份发布快照都有稳定的版本标签。App 创建工程时继续使用当前安装版本内置的 Blank，工程来源版本随生成结果保存。
- **建仓与授权。** App 提供独立的官方模板首次备份入口，打开预选官方模板的 GitHub 建仓页并引导使用默认分支。创作者在浏览器完成建仓和仓库授权，再回到 App 选择目标。复用现有 GitHub App 授权、仓库选择和权限检查。
- **首次备份范围。** 由 App 的 Blank 生成且尚未绑定仓库的工程可采用新流程，包括已经保存多个工程版本的工程。创作者切到与远端默认分支同名的本地分支后再继续。已有仓库和普通空仓或共享历史的绑定走既有路径，后续分支操作沿用同名分支规则。
- **验证远端初始状态。** 核对 GitHub 返回的官方模板仓库身份，确认目标默认分支只有一个根提交，并把完整 Git 文件树与对应官方版本标签核对。两代模板共用仓库身份，版本标签区分新版快照。旧版官方快照在模板更新后仍可验证。本地与远端的 Blank 版本可以不同。
- **首次推送。** 用一个双亲合并提交连接两段 Git 历史，文件树等于已确认的本地保存版本。普通快进推送更新远端默认分支，保持两段历史的原提交 ID。沿用公开推送确认、授权和推送前复查。确认期间若目标、分支、版本或公开范围改变，提示重新核对。远端已出现额外提交或 GitHub 拒绝更新时保留两边历史并提示原因。
- **中断与恢复。** 保存足以继续原操作的目标仓库身份、分支、原远端初始提交与待推送合并提交。远端已收到待推送提交时补齐本地状态。远端仍处于原初始提交时允许创作者继续推送同一提交。远端处于其他状态时提示冲突。中断期间产生的本地工程版本保留，公开范围变化时重新确认。
- **外部初始化。** 模板提供一次显式初始化命令，在本机终端或该仓库的 Codespaces 可执行。生成独立工程 ID，并一致写入工程 manifest、npm 包元数据、演奏端配置和工程简介所需的对应信息。重复执行保留已初始化工程的 ID 和创作文件。初始化提交由作者使用正常 Git 工作流保存并推送。随后可用模板的 npm 依赖做无声预览，Internal 音频仍由 Host 提供运行环境。
- **公开工程目录。** 官方模板 README 链接到 `topic:pnds-project is:public` 的 GitHub 仓库搜索。App 在首次公开备份成功后说明如何加 topic，模板文档也说明外部初始化推送和已有公开工程的加标路径。是否加入由创作者决定，目录覆盖主动加标且处于公开状态的工程。

## Testing Decisions

- 从创作模式的新建工程、Git 版本页和原生同步命令观察外部结果。沿用现有 Blank 创建测试与 GitHub 同步界面测试，覆盖离线新建、模板建仓入口、回 App 选择仓库、默认分支提示、公开确认、中断反馈和加入目录指引。
- 复用现有原生 Git 同步测试的真实临时仓库。构造不同本地历史与远端快照，核对两边原提交均可达、最终文件树等于已确认的本地版本、默认分支被普通推送更新，以及既有空仓和共享历史流程仍通过。用版本不同、同仓旧版、模板身份不符、文件树不符和目标已有额外提交的样例验证远端判定。
- 在同步工作流上复现远端尚未收到推送、远端已收到但本地未记录、重启后远端有其他提交、期间本地另存版本以及公开性变动。断言最终仓库、分支和提交状态，并验证重试复用同一合并提交。
- 用同一发布快照初始化两个独立目录，覆盖同名工程得到不同 ID、相关文件保持一致、重复初始化保留已修改工程，并通过现有工程打开与无声预览路径验证产物。沿用 Blank 的工程验证和受控运行测试。
- 使用配置好的 PNDS GitHub App 和专用 GitHub 测试仓端到端验证浏览器模板建仓、授权、`Generated from`、首次推送及手动添加 topic 后的公开搜索。覆盖一个私有备份和一个公开工程，并验证外部初始化路径。GitHub 搜索索引可能稍后更新，验收记录区分已加标与已出现在搜索结果。
- 业务测试随实现交付。PNDS App 必须通过 `npm run check:all`，模板仓的导出、初始化和预览执行其适用检查。开发规则和双语创作说明随功能交付。

## Out of Scope

- p5.js Starter 与其他模板类型。
- 以 GitHub Actions 自动初始化、自动建仓、自动写入 topic 或扩大 GitHub App 授权权限。
- 自建工程目录服务、集中上报、完整模板衍生统计或通知系统。
- 批量迁移已有工程仓库、回填 GitHub 模板来源，以及 `.pnds` 打包或发行工作流变更。

## Further Notes

- ADR-0019 记录本设计，ADR-0018 记录常规 GitHub 绑定、备份和更新行为。
- GitHub 依据生成关系显示 `Generated from`，公开目录依据仓库的 topic 和公开性。工程自己的 Blank 来源版本继续记录实际生成基线。
- GitHub 若对目标分支启用线性历史等限制，可能拒绝合并提交，App 应显示拒绝结果并保留工程历史。

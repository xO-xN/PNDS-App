# 创作模式下一步调整：逐轮讨论

状态：产品范围已逐项及整体确认，设计访谈完成（2026-10-20）。随后用户调用 to-spec，要求纳入新的 1.7.0 任务并全部安排在收尾 #172 之前；已发布 #238–#243，完整规格见[1.7.0 调整规格](./v1.7.0-creation-refinements-spec.md)。本文不代表功能已经实现或本轮已开始实施。MCP 明确留到后续版本，不作为本轮前置。

讨论采用 grill-with-docs；已确认术语沿用根目录 [CONTEXT.md](../../CONTEXT.md)，当前实现核对见 [creation-assistant.md](../developer/creation-assistant.md)、[creation-workspace.md](../developer/creation-workspace.md) 与 [controlled-checks.md](../developer/controlled-checks.md)。

## 当前实现核对

- 主工作区已有“讨论”视图，但助手输入区仍显示 `handoff / edit`。默认 handoff 可按需直接写交接单，缺少专门的手动交接入口。
- edit 已支持工程多文件新建、保存、删除、本地资源接入、检查后同任务修复和撤回。旧文档及词汇表的“仅支持单文件修改”不能用于判断当前能力。
- SCD 已有编辑、保存、编译；尚无指定本机 SuperCollider 打开的入口。
- 当前附件是工程内文本选区快照；不支持外部文件暂存、二进制复制或图像／PDF 等多模态输入。助手新建文本仍要求父目录存在。
- 未发现 PNDS 专门的创作追问流程或整理工程入口。
- 外部 agent 已能读写工程、读取交接单与装机帮助，并用随包 CLI 运行检查。当前没有 MCP；CLI 不具备 App 桌面 WebKit 的页面错误观察能力。

以上为本次只读核对快照，不替代功能及实机验收记录。

## 第一轮已确认

### 讨论、编辑与交接

- 将助手的 handoff 模式改为“讨论”；讨论用于读取、分析及推敲方案，停止自动维护交接单。
- 用户修正初始清单中“两种模式都可手动交接”的设想：**交接入口只放在讨论中**，避免编辑模式下混淆实施与交接。
- 编辑继续用于实施明确任务。讨论中手动交接的草稿、正式记录及比较基线衔接方式，见第二轮确认。
- 此方向修订 [ADR-0008](../adr/0008-creator-handoff-as-agent-seam.md) 中 2026-10-17 的“默认 handoff 直接维护交接文档”产品决定；ADR 已记录本轮目标，实施时同步更新规格与对应规则，当前代码尚未改变。

### 使用本机 SuperCollider

SCD 提供用本机 SuperCollider 打开的入口，只打开工程内已保存源码；外部保存后沿用 App 的文件变化检测。用户明确不需要接入 App 当前音频环境。

### 创作资料

- 采用“创作资料”称呼，区分讨论参考、等待接入的文件和已正式采用的工程文件。
- 资料先与当前工程关联并暂存，再由明确的编辑任务决定复制、转换或接入。
- 格式范围、保存位置及保留规则见第二轮确认。“暂存”不代表自动删除。

### PNDS 深入讨论

- 目标是将创作意图推进到可验证的创作实验。
- 围绕实际工程和创作意图追问，例如演奏者行为、相互影响、时间变化及反馈如何被感知；允许保留艺术上的开放性。
- 收束为已确认的创作决定、尚未解决的问题及下一次可验证的实验。
- 用户强调 grill-me 的极简特点：保持简短、按实际缺口追问，不增加繁复的讨论系统。

### 整理工程

面向当前 PNDS 工程，依据 PNDS 契约及用户选择的规范整理结构、命名、重复代码、引用和废弃文件，保持已有声音、视觉、生成逻辑及演奏交互。先作为复用 edit 的专用工作流；性能优化、作品重设计分别指派，不默认把已有工程迁为统一模板目录。

### 外部 agent 与 MCP

先关注“外部 agent 修改工程 → 请求 App 检查 → 取得页面错误、运行状态与日志 → 继续修复”的验证闭环。用户明确 MCP 可以放到后续版本；本轮不选择协议、传输、工具清单或具体交付版本。

## 第二轮已确认

### 交接草稿与正式记录（Q7）

手动生成交接默认整理当前话题中已确认的方案，先提供可编辑草稿，将建议和疑问单独标明。创作者审阅并点击“记录交接”后，才写入交接单并采集比较基线，沿用已有记录与比较流程。

### 极简追问与逐题回答 UI（Q8 与用户补充）

用户接受将以下短规则直接融入普通讨论：

> 结合相关工程事实，只追问会改变方案的关键缺口，给出建议；能通过预演验证时，提出最小实验。用户要求深入讨论时持续推进，方案清楚时及时收束。

用户补充要求：不一次列出全部问题，每次提供一个 UI 作答；随后通过单题选择明确，**此要求适用于 App 的整个讨论过程，不限于生成交接**。

讨论需要创作者回答时，一次展示一张问题卡，包含当前问题、推荐选项与自由输入；回答后再依据答案推进下一问。普通事实说明和结果仍通过聊天正文呈现，不增加讨论阶段或专门模式。讨论答案用于澄清方案，沿用第一轮决定，不自动授权工程修改或正式记录交接。

### 文本资料与文件接入（Q9）

首版支持代码和文本资料，例如 Markdown、TXT、HTML、JS、CSS、JSON、SCD。图片、PDF 与音视频理解留到后续。

用户明确主要场景是 Runes 工程中 `grid.js`、`pattern.js` 这类不知道应放在哪里的源文件。创作者提供文件并明确要求接入当前工程后，由助手结合文件内容、工程入口与引用关系判断放置位置，完成必要适配与接线；创作者无需先掌握工程目录。正式采用应保留原作品的源码和行为，交代文件去向、必要适配与实际检查结果，延续已有任务撤回能力。

### 资料保留（Q10）

创作资料由 App 按工程保存副本，跨聊天、跨重启保留，由用户手动移除；采用后也保留资料原件。正式采用的文件进入工程，按既有工程规则管理和打包，参考资料留在 App 的工程专属资料区。

### 默认整理规则与补充规范（Q11）

“整理工程”作为一个编辑任务入口，采用 PNDS 默认整理规则，用户可用文字或指定文档补充规范。范围及保持作品行为的要求沿用第一轮决定。

## 第三轮已确认：资料同名冲突

工程已有文件与新资料同名但内容不同时，助手先说明差异与推荐，通过一张问题卡让创作者决定替换还是并存。其余可依据工程和资料判断的目录选择、文件放置及引用接线，由助手在明确的接入任务中直接完成。

## 收口状态

用户通过单题 UI 确认完整范围可以定稿，本轮设计访谈完成。讨论与逐题问答、讨论内手动交接、SCD 外部打开、文本资料接入及整理工程构成本轮设计结论，MCP 留到后续版本。随后用户确认统一助手工作流、必要原生边界及 #172 真实验收的测试接缝，授权发布 1.7.0 新任务；任务与依赖见正式补充规格，代码实施另行领取。

# v1.7.0-beta.2 演出角色与桌面池客设计讨论

状态：产品及 HTML A 原型已由用户确认，池主／池客与自动端口管理均纳入 v1.7.0-beta.2；本轮已转为正式规格与 GitHub #258／#259。本文保留逐轮决定及技术证据，正式规格见[beta.2 四项规格索引](./v1.7.0-beta.2-spec-index.md)。本轮不实施功能。

文件名保留原 v1.7.1 标记以维持已有评审链接；当前版本归属以本文件范围为准。

## 已确认的范围

- 功能纳入现有 PNDS App，作为 v1.7.0-beta.2 更新的一部分；自动管理端口与冲突避让同版交付，暂不考虑独立演奏端安装包。原 v1.7.1 安排已由 2026-11-03 的用户决定取代。
- 演出模式的左侧栏先提示选择「池主 / PNDS Host」或「池客 / PNDS Client」，再进入对应功能。角色属于演出模式，不新增第三个界面模式。
- 同一个 App 同一时刻仅担任一个演出角色，首版不支持同时主持本机演出并加入另一场演出。
- 每次进入演出模式都重新选择角色，不恢复上次角色，不自动启动或加入演出。是否保留其他偏好不由这条决定扩展推断。
- 池客首版用完整演出地址和最近连接加入，不纳入自动发现池主。最近连接以池主节点名为主，不用多个工程名代替池主；池主必须显式填写节点名，不采用电脑名回退。本地演出不因此要求填写 hub 地址或 token。
- 池客是通用 PNDS 演出参与入口，不是 Sensor Meter 专用功能；以 Sensor Meter 为首个验证工程，再核对其他符合连接约定的工程。
- 演奏页面在 PNDS 主窗口内显示，不额外打开系统浏览器。内嵌 WebView 的摄像头、权限与 Worker 推理必须先做真实双机验证，当前没有通过这一验收。
- 池客同时只加入一台池主的一场演出，显示一个演奏页面；换池主须先离开，创作模式已有的多个测试窗口保留。
- 网页数据按池主与工程隔离保存，退出或重启后可供下次手动加入使用；不自动加入，也不承诺恢复工程自身未保存的演奏状态。

当前实现步骤、状态表与验收矩阵已整理为[实施规格草案](./v1.7.1-performance-roles-spec.md)，刷新规则与自动端口管理的版本范围已确认；端口职责、技术验证与最终总览继续收敛。

领域词汇见根目录 [CONTEXT.md](../../CONTEXT.md)，已确认的角色关系见 [ADR-0014](../adr/0014-performance-roles.md)。performer / monitor 仍是工程页面角色；池客角色、页面打开和工程接纳是三个不同概念。

## 已确认的入口与交互

[独立 HTML](../prototypes/performance-roles-1.7.1.html) 以用户选定的 A 方案继续迭代：进入时用角色说明卡替代工程列表，选择后收拢为斜线角色按钮，侧栏显示对应功能。B 的常驻分段和 C 的职责预览只保留为历史比较记录，不再作为当前方案。

- 角色按钮默认只显示当前语言的角色名：中文「池主／池客」，英文「PNDS Host／PNDS Client」，不并列双语。
- 悬停或键盘聚焦时在按钮内提示目标角色；空闲首击显示「再次点击切换角色」，第二击提交。参考此前右下角斜线按钮，采用斜面露角、半幅确认与填满切换的变化，不用下拉菜单。
- 演出中拒绝切换，在同一个按钮内提示「请先退出当前演出，再切换角色」；不弹出框，不以切换操作自动关闭演出。加载、等待接纳、断线重连及退出清理同样禁止切换，直到明确取消／离开且资源清理完成。
- 池客侧栏聚焦地址、最近池主与当前连接；加入后沿用浮动显隐。底栏保留离开、刷新、设置，不显示池主音频引擎、投影与工程管理操作。
- 池客进入创作前离开本地演出，再进入本机创作首页；池主保留原有接续，返回演出重新选择角色。
- 本功能中的池客参加的是场地局域网内的本地演出，连接另一台池主不等于跨互联网演出。此前问题中的「远程演出」措辞已纠正，不能由该措辞推导 hub 或公网接入要求。

## 接入身份与重连的现状核对

- `nodeName` 是可编辑的名称，不是既有的安装级稳定 Host 标识；当前没有可直接复用的安装级 Host UUID。
- Rust 的 `SessionInner.generation` 是内部运行代；普通 `SessionSnapshot` 不公开该字段，只有本机 `CreationRuntime` IPC 携带 generation。前端 `session-store.runId` 是本窗口观察启动状态时自增的计数，不是网络端的演出身份。
- HTTP health 与工程 `__config.js` 目前只提供 manifest 的 projectId 等信息，不能区分同工程重启，也不能区分未更改 manifest.id 的工程副本。因此不能用 projectId、节点名或本地 runId 独自兑现 Q13。
- Sensor Meter、Template 及 players 模块在 Socket.IO connect 后自动重发 join，现行加入没有「用户确认的是哪个工程／哪次演出」条件。旧入口连接关闭后，同一地址重新上线仍可能触发旧页面自动加入。
- 既有 HTTPS gateway 在 Stop／替换时关闭 listener 和活动连接，但它是透明转发，不提供工程或运行身份门禁。**先自动加入，再提示工程已变化，不满足 Q13。** 正式接入方案必须在连接进入新工程前验证已确认的接入上下文。
- Sensor Meter 断线不停止媒体，也不阻止 emit；Template 与 Sensor Meter 的服务器重启恢复能力不同。Sensor Meter 的 registry 在内存，Template 可使用磁盘 SeatsStore；不能承诺 App 统一保证同一座位号码或音乐状态跨服务器重启恢复。
- 长期保存的 claim token 与一次演出的确认上下文承担不同职责。不能通过每次演出都换浏览器来源，顺带破坏工程已有的身份恢复；多个 Host／工程也不能共享混杂的本机存储范围。

事实来源为 `src-tauri/src/project/session.rs`、`src/store/session-store.ts`、当前 Sensor Meter 与 PNDS Template 源码。本段描述当前事实与新增要求，不表示接入身份协议已经实现。

接纳反馈的现有事实：创作测试窗口的 iframe onLoad 仅表示页面加载；可选 health performers 名册才表达工程已接受且仍在线的设备。`pndsTestClient` 是诊断标记，不是身份或授权凭据。`supportsPerformerUrl` 只承诺完整入口与同源资源／实时连接，不承诺名册或媒体能力。正式池客应复用这一事实区分，不以网络可达、HTTP 成功或页面加载次数猜测「已加入」。

### Q21 所指的工程兼容约定

工程侧的基础是现有[完整 performer URL 契约](../zh-CN/reference/runtime-contract.md#15-完整-performer-url-与外部入口138-冻结契约)与 [manifest 能力声明](../zh-CN/reference/manifest.md)，不是要求每个作品另做一套池主身份服务：

| 约定         | 工程应做到的事                                                                                                      | 原因                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 完整入口     | 对外二维码、复制地址和配置使用 Host 注入的 `PNDS_PERFORMER_URL`；页面角色用服务端注入值，不猜端口。                 | 入口可能经过转发，不能自行拼接或覆盖回局域网原端口。                                   |
| 同源资源     | performer 的脚本、样式、Worker 与本地模型跟随当前页面来源，例如 `/handpose-worker.js`。                             | 池客拟从本机回环入口提供页面，资源须能随该入口加载。                                   |
| 同源实时连接 | 使用当前来源建立 HTTP polling／WebSocket，例如 `io()`；不把 performer 连接写死为池主的 IP、协议和端口。             | 转发层才能完整管理接入上下文；硬编码地址会绕开它。monitor 的既有内部连接不属于此限制。 |
| 如实声明能力 | 已适配工程声明 `scoreServer.supportsPerformerUrl: true`；使用需安全上下文的 API 时继续按现有规则声明 `needsHttps`。 | 声明用于预检，不证明摄像头可用或工程已接纳；不能只加标记而不核对实际页面行为。         |

新增的稳定池主身份、演出身份、加入前校验、本机转发与网页存储隔离由 App 承担；具体协议和原生媒体方案仍待验证。作品继续使用原有音乐消息与加入策略。可选的接纳名册不升级为必需项，沿用 Q20；摄像头、麦克风、Worker 只按作品实际所需验收，也不要求所有作品使用传感器。

对已经遵循完整入口及同源连接的工程，适配可能只需核对声明和验证，不应预设需要重写。未声明只说明尚未声明能力，不能直接当作实际不兼容；Q21 已确认按声明与实际行为核对首版准入条件。不会因桌面池客方案而删除工程面向普通手机浏览器的 `needsHttps` 需求。

当前原型已更新两击刷新、App 分配端口后的地址与详情、旧工程端口冲突、工程需适配等交互。首击不重建原按钮或谱面，第二击才释放示例媒体状态并重新加载；未知接纳仍保持未知，检测工程变化时不自动加载新页面。模拟成功建立新确认上下文后会清除旧的变化场景，终止通知页切换角色回到目标角色的空闲页。这些内存行为不构成媒体、端口绑定或真实连接实现。现阶段仅余整体 UI／UX 核对与技术验收，不再追加底层实现问题让用户选择。

## 端口冲突核对与 Q26 建议（2026-11-03）

当前事实：`6868`／`6869` 是模板和官方工程的惯例，端口实际由 manifest 声明，平台无写死的默认值。[manifest 端口规则](../zh-CN/reference/manifest.md#端口)及 [runtime-contract §4](../zh-CN/reference/runtime-contract.md#4-http-与网络)明确规定工程监听声明端口、冲突即失败、不自动换端口或改 manifest。`preflight::check_ports_available` 用占用 PID、全接口与回环绑定检查发现冲突，但不为 Node 持续保留这些端口，不能宣称消除检查后被其他进程占用的竞态。

当前 App 的 `build_score_server_env` 不注入运行时 performer／monitor 端口，启动、health 目标／核对及网关上游都依赖 manifest 端口。Sensor Meter 的 `PNDS_PERFORMER_PORT`／`PNDS_MONITOR_PORT` 当前仅为其测试并行运行的覆盖，源码注明生产不设置；Template 与内置 Classic 仍读取 manifest。不能把这两个测试变量当成已发布的动态端口契约。

| 层次                         | 灵活端口建议                                                                           | 约束                                                                                                                         |
| ---------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Host 对池客的局域网入口      | 优先复用可用入口；冲突后选择可用端口并显示新的完整地址。                               | 最近连接中的旧地址不能凭空更新；入口变化必须可见，演出中不自动迁移。                                                         |
| 工程 performer／monitor 服务 | 对明确支持新运行端口契约的工程，实际端口由 App 与工程协调并核验，6868／6869 可作首选。 | 新增能力不能从 `supportsPerformerUrl` 推导；未适配工程继续按原端口运行，冲突仍明确失败。只改变外部入口不能解除内部端口冲突。 |
| 池客本机回环入口             | App 自动管理可用端口，乐手无需手填。                                                   | 必须同时兑现 Q23 的持久身份／存储隔离，不能把每次随机换 localhost 端口当作完整方案。                                         |

[Rust TcpListener](https://doc.rust-lang.org/std/net/struct.TcpListener.html#method.bind) 支持绑定端口 `0` 后由系统分配给实际 listener，drop 会关闭 socket。据此推断，正确分配须由实际服务持有监听器，或使用明确的交接／有界重试方案；先探测后释放再让子进程绑定并不具有保留保证。具体子进程协商方式在技术验证后固定，不在本轮冻结新环境变量。

浏览器 origin 包含端口，`localStorage` 按 origin 隔离；更换回环端口后无法直接访问旧来源下的 token，但旧数据不等于被删除。[MDN 同源策略](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) 支持这一约束。自动避让必须连同稳定来源／恢复方案验证；验证前不宣称 Q23 已由随机端口实现。手机浏览器入口的现有 origin 与 HTTPS 规则也不在本轮被静默修改。

Q26 纳入范围已确认：用户明确把池主／池客及自动管理端口、避让冲突一并移至 v1.7.0-beta.2。自动端口管理不再是待决定的版本范围。用户同时追问「由作品工程来选择端口？」；本轮澄清的建议是由 App 统一管理端口，工程遵守运行时分配并报告监听结果，不由每个作品自行寻找或切换端口。完整方案仍需最终总览与技术验证，上述分析尚未修改冻结运行契约。

### 端口职责的澄清

- App 拥有端口策略、分配与冲突避让，登记实际监听结果，并据此构造 health、monitor、转发上游和池客可见地址；演出中不自动迁移已发布端口。
- 已适配工程声明自己支持运行端口契约，按 App 提供的运行配置监听 performer／monitor，成功或失败都向 App 报告。工程不能自行改端口后让 App 和池客继续使用旧值。
- 未适配的旧工程仍走 manifest 固定端口兼容路径，冲突时明确提示。manifest 的既有端口不代表新方案由作品独立挑选实际运行端口，也不因为启用自动分配就被 App 写回修改。
- 底层可由操作系统为实际 listener 分配端口，再由 App 登记、核验和发布；监听器交接、子进程启动通道或有界重试属于实施细节。必须以真实绑定为准，不能以一次空闲探测代替监听成功。

流程为「App 管理分配 → 工程监听并报告 → App 核验并发布实际地址」。乐手仍只需使用池主显示的完整局域网连接地址。

# v1.7.0-beta.2 待处理文档规格

状态：产品方案已确认，供规格发布与后续实施使用；本轮不实施功能。2026-11-03。用户已确认将本项纳入 v1.7.0-beta.2，并确认长期工程说明的收录规则。本文将已确认讨论整理为可验收规格，不表示现有 App 已具有这些行为。

## Problem Statement

创作者常从 OpenProcessing 等外部平台取得代码或文字，希望先快速粘贴、命名和保存，再让 PNDS 创作助手根据当前任务将其放入合适的工程位置、调整依赖并接好入口。现有“创作资料”主要是不可变参考副本，不能直接承接主编辑器中的新建、编辑和重命名，也缺少接入成功后移出原文与跨重启撤回的完整工作流。

直接把这些内容当作已接入的工程文件，会提前把未整理代码混入运行、版本与分发范围；只复制一个文件又不足以证明入口、依赖、引用和检查均已处理。创作者需要清楚区分“暂存”“已接入”“已保存但尚未运行验证”，并在失败、冲突或后续编辑后保住原文和已有工程内容。

## Solution

在创作模式中，以“待处理文档”整体替换“创作资料”。创作者可在文件区新建条目，直接在主编辑器粘贴并保存，也可导入文本文件。每份已保存文档都是具有稳定身份的独立真实文件，能在 Finder 或外部编辑器访问；它在接入前仍属于工程私有创作数据。

PNDS 创作助手随请求获得已保存文档清单，结合任务按需读取。只有明确的工作任务才执行接入：源码进入合适的工程代码位置，需要长期维护的说明进入合适的工程文档，临时参考仍可留存。助手完成必要的入口、依赖和引用调整，按整次接入任务判断完成，提供真实结果及最近一次任务的持久恢复能力。日常保存、添加资料、讨论和单纯阅读都不触发自动接入。

## User Stories

1. As a project creator, I want a distinct Pending documents group, so that I can distinguish saved source material from files already integrated into the project.
2. As a project creator, I want the empty group to retain its creation action, so that I can start staging material without an existing document.
3. As a project creator, I want a new entry with an inline name and an empty main editor, so that I can paste external code without using a separate content dialog.
4. As a project creator, I want a new document to remain a draft until its first save, so that creating or cancelling an empty entry does not publish an unwanted file.
5. As a project creator, I want to save with the existing save control or keyboard shortcut, so that pending documents follow the editor workflow I already know.
6. As a project creator, I want drafts preserved while switching documents, so that navigation does not discard my pasted or edited content.
7. As a project creator, I want save, discard and cancel choices before leaving unsaved work, so that changing projects or quitting does not silently lose a draft.
8. As a project creator, I want saving a project version to handle pending drafts first, so that unsaved work is not mistaken for saved content even though pending documents are excluded from Git.
9. As a project creator, I want text import to copy material into the pending area, so that the external original remains unchanged.
10. As a project creator, I want to edit and rename pending documents without changing their identity, so that the assistant and previous references can still distinguish the same document.
11. As a project creator, I want confirmed deletion to remove only the pending copy and its draft, so that external originals and integrated project files remain intact.
12. As a project creator, I want Finder location and ordinary external editing, so that a saved pending document is a real accessible file.
13. As a project creator, I want the existing supported code and text types, including extensionless text, so that I can stage the same kinds of source material the editor already supports.
14. As a project creator, I want explicit limits and readable validation errors, so that oversized, invalid or unsupported content is not silently truncated or lost.
15. As a project creator, I want conflicting new names to require correction and imported names to offer an editable suggestion, so that one document cannot silently replace another.
16. As a project creator, I want external changes to refresh clean documents while preserving dirty drafts, so that external editing never overwrites my unsaved work.
17. As a project creator, I want each assistant request to include a saved-document catalog rather than every document body, so that the assistant can discover relevant material without sending unrelated text.
18. As a project creator, I want the assistant to read the current saved version when needed, so that stale summaries and historical excerpts do not substitute for actual source content.
19. As a project creator, I want adding, saving and discussing documents to remain separate from integration, so that those actions do not start a model request or modify project code unexpectedly.
20. As a project creator, I want the assistant to select relevant pending documents within my explicit Work task, so that I do not have to name every useful source individually.
21. As a project creator, I want source integration to include placement, entry wiring, dependencies and references, so that a copied file can actually participate in the intended project behavior.
22. As a project creator, I want the source algorithm and artistic intent preserved during integration, so that routine wiring does not redesign the sound, visuals or interaction.
23. As a project creator, I want relevant long-term project explanations incorporated into suitable project documentation, so that the project retains the knowledge needed for later maintenance.
24. As a project creator, I want temporary references and undecided notes to remain staged unless they are actually integrated, so that reading material does not consume it or add unnecessary project documents.
25. As a project creator, I want clarification when a document's use is ambiguous or integration would change artistic behavior, so that the assistant does not guess a consequential creative decision.
26. As a project creator, I want to save a dirty source before integration or cancel the action, so that the assistant works from the version I intend to use.
27. As a project creator, I want differing destination content shown before I choose replace, coexist or cancel, so that integration does not silently overwrite existing work.
28. As a project creator, I want an identical destination reused when appropriate, so that integration does not create redundant copies or claim ownership of unrelated existing content.
29. As a project creator, I want every selected source in one integration task to remain pending until the entire task is complete, so that partial success does not hide unfinished work.
30. As a project creator, I want failures to preserve all pending originals and report saved partial changes, so that I can continue or undo without guessing what happened.
31. As a project creator, I want failed checks distinguished from unavailable or blocked runtime checks, so that I can tell whether integration failed or has been saved without runtime verification.
32. As a project creator, I want completion results to show sources, destinations, actual modifications and verification status, so that I can review the outcome before relying on it.
33. As a project creator, I want the most recent successful integration task to remain recoverable after restart, so that completing a task does not remove the opportunity to undo it.
34. As a project creator, I want undo to cover the entire integration task and its references, so that restoring the original documents does not leave a partially disconnected project.
35. As a project creator, I want later project edits protected from integration undo, so that recovery cannot overwrite newer work.
36. As a project creator, I want a separate restore-originals action when full undo conflicts, so that I can recover source documents while preserving the current project files.
37. As a project creator, I want interrupted saves, migration and integration completion to recover from durable facts, so that a restart cannot invent an empty collection or an all-or-nothing success.
38. As a project creator, I want existing creation materials migrated with their names, content and historical identity, so that upgrading does not lose source material or its chat associations.
39. As a project creator, I want migration retries and a later empty pending area to remain idempotent, so that already handled legacy documents are not imported again.
40. As a project creator, I want old chats to retain the excerpts and versions actually read at the time, so that a renamed, edited or integrated document does not rewrite conversation history.
41. As a project creator, I want pending documents to travel with a complete project folder while remaining outside Git, the default performance bundle and runtime checks, so that staging remains portable without prematurely becoming production content.
42. As a project creator, I want clear guidance that switching a project version does not restore the private pending area, so that I use the explicit document recovery action when needed.
43. As a project creator, I want project identities and late replies isolated, so that another project's documents cannot appear in or modify my current project.
44. As a project creator, I want consistent Chinese and English controls with keyboard access and stable focus, so that the complete workflow is usable without relying on a mouse or a particular language.

## Implementation Decisions

- 本项纳入 v1.7.0-beta.2，仅面向可编辑文件夹工程。替换现有创作资料入口，不并列建立两套用于相同目的的资料系统；旧数据和旧聊天来源仍须迁移兼容。
- 文件区提供独立待处理文档分组及常驻新建入口。新建先产生稳定身份的草稿，行内命名并复用主文本编辑器；首次保存才创建独立真实文件，取消未填写的空白新建不产生磁盘文件。导入是复制来源的次要入口。
- 编辑对象明确区分普通工程文件与待处理文档身份。改名保留身份，文件名仅表示一层显示名而非任意目录路径；草稿、正文、保存失败、外部变化与离开操作沿用现有编辑协调流程。保存失败或冲突须阻止依赖该保存的接入或离开。
- 保留既有代码及文本类型，无扩展名按纯文本处理。单份正文上限 1 MiB，每工程最多 64 份，正文总字节数上限 8 MiB；新总量按正文计算，不沿用旧序列化记录大小的表述。无效编码、非文本内容、越限和不可读取应区分反馈并保护现有内容。
- 每份已保存正文为独立 UTF-8 文件，元数据仅记录稳定身份、名称、保存版本、状态及关联目标。正文、索引和恢复资料使用工程内私有创作数据边界，通过专用原生命令访问，不把私有路径伪装成普通工程文件。
- 原生操作绑定当前实际工程身份、文档身份和预期保存版本，复用可信目录、不可跟随符号链接、原子发布及失效身份检查。独立工程副本各自拥有文档；同一真实目录的别名共享其文档。文件与元数据发布须有可恢复次序，损坏、缺失或中断不能被当作空集合。
- 用户可编辑、重命名、确认删除及在 Finder 定位。删除只处理暂存副本和对应草稿。外部改名、删除或保存后同步当前事实；清洁缓冲可更新，脏缓冲及保存前版本复核保护用户内容。普通工程整理不改写或清空待处理原文。
- 每次助手请求准备时提供当前已保存文档的身份、名称及版本清单，不自动附带全部正文。助手按任务读取当前保存内容，接入须有确切版本及实际完整读取证据；文件名、摘要、历史片段和旧读取凭证不替代当前正文。
- 添加、保存、导入、讨论和单纯阅读不触发接入，也不授予写入权。已授权 Work 任务可自行发现并选择相关文档，不要求逐份点名；多个合理候选、用途不明或需要改变艺术行为时再询问。仅出现于清单不等于全部接入。
- 源码接入包括合适目标、必要目录、入口、依赖和引用调整，只改工程副本，保留待处理原文直到任务完成。算法、声音、视觉与交互意图保持原意，需要实质改变时询问。
- 与当前 Work 任务相关且应长期维护的工程说明，默认收录到工程根文档目录内的合适工程文档；优先更新已有合适文档，否则新建。内部设计说明不自动写入面向演出准备者和投影观众的工程根说明。临时问答、未定草稿、外部参考全文或用途不明资料可按需读取并保留；单凭“按此说明实施”不构成收录整份外部参考的理由。
- 接入源有草稿时提供保存并继续或取消；目标有草稿时先保护草稿。目标内容一致可复用，不同时展示实际差异并等待替换、并存或取消，确认后仍复核源版本、目标保存版和当前任务归属。先前答复不授权覆盖后来的内容。
- 同一工程同一时刻只有一个接入任务。恢复单位是包含接入的整次工作任务，覆盖本次创建或修改的全部工程文件与必要引用，而非只包含复制出的文件。取消执行不自动抹掉已保存修改。
- 整批选定接入源全部完成后才统一移出。显式完成步骤核对源版本、目标集合、必要引用及检查事实，助手一条“完成”回复或一次复制不能单独消费原文。实际检查失败或必要文件、依赖缺失时保留全部原文，报告部分修改并允许继续或撤回。
- 检查能力不支持或被当前运行占用时，必要文件与引用均已保存后可完成接入，但须标记“已接入，尚未完成运行验证”并说明原因。保存、检查和真实音画行为验收分别表达，不将当前仍运行的旧版本当作新保存内容的验证证据。
- 先持久化独立恢复记录和完成状态，再移出原文。保留最近一次成功接入任务的恢复记录，跨重启可用；新成功任务的恢复记录与原文移出均落盘后才替换上一份记录。不能依赖正常完成后会被清理的助手任务日志保存长期撤回能力。
- 整任务撤回前核对全部相关目标、保存版本及来源身份。后续修改或其他冲突阻止直接覆盖，并允许仅恢复原文、保留现有工程文件；恢复沿用原身份并保护暂存位置的已有内容。多文件恢复中断按持久记录继续或如实报告部分结果，不宣称已全部恢复。
- 旧资料迁移保留名称、正文原始 UTF-8 字节、原身份、内容版本及聊天关联，不自动规范化换行或 Unicode，同名文档分别保留。完整发布并校验独立文件与索引后才确认迁移完成，保留原数据作为恢复依据；重试不重复导入，后来空列表不触发重新迁移，损坏索引不静默回退旧记录。
- 历史聊天保留当时实际读取的内容、名称、身份和版本；当前文档或接入目标另行打开。编辑、改名、移出和恢复不把历史快照重解释为当前正文，也不恢复旧写入授权。
- 待处理正文、索引和恢复数据随完整工程目录迁移，接入前排除于 Git、默认演出工程包、普通助手文件工具和工程运行检查。接入后的目标按普通工程文件规则管理；Git 切回旧版本不自动重建私有待处理区。
- 延续类型安全原生命令、状态归属、持久化串行与中英文文案规则。正式帮助和开发规范在实际实现时同步更新，保持既有装机帮助路径与文档身份。

## Testing Decisions

用户已在本轮确认以下测试边界：以 App 公开操作／命令为主入口，观察真实工程、持久文件与受管进程／网络结果；界面补测可见工作流，媒体与声音保留实机验收。

- 采用一条主要验收接缝：从现有创作原生命令和受控助手任务入口驱动真实临时工程与私有文档存储，观察命令结果、磁盘内容、重新打开后的可见状态和接入／撤回结果。优先扩展现有入口，不为每个私有辅助函数建立新的测试接口。
- 好的测试验证创作者可观察的保存、冲突、接入、恢复和排除行为，并使用彼此不同的源内容、目标内容和后续修改证明保护边界；不以组件内部状态、调用次数或复制实现步骤代替结果断言。
- 现有先例包括私有资料原生命令对真实临时工程的保存／重启／身份隔离测试，材料接入任务的确切版本、显式冲突及受保护撤回测试，以及真实助手请求循环的受控接入重放。复用这些 fixture 与实际系统边界，仅在外部模型响应等边界使用替身。
- 在同一主要接缝覆盖新建首次保存与取消、文本导入保留外部源、编辑及重命名保留身份、确认删除不影响已接入文件、同名和全部容量边界、有效 Unicode 与非法文本，以及保存失败后原字节保留。
- 使用两个实际工程及相同 manifest 的独立副本验证归属；同一目录别名读取同一集合，工程切换或身份撤销后的迟到请求不得改写新工程。源和目标在确认、读取与发布之间变化时应保护较新的保存内容。
- 通过请求循环观察助手获得清单但未自动获得无关正文，验证保存不发起模型请求、讨论不授予接入权、当前完整正文才构成接入证据，以及临时参考不被误移出。受控源码 fixture 应实际加载接入后的入口和依赖，证明必要接线，而非只断言文件存在。
- 对新建目标、相同内容复用及不同内容冲突分别验收；替换、并存、取消和过期答复应产生各自可观察结果。长期工程说明应进入工程文档，外部参考全文与用途不明内容保持暂存或进入既有澄清流程。
- 验证多文档任务的整批完成、部分写入保留全部原文、真实检查失败、必要依赖缺失，以及检查不支持／运行占用时明确未验证的不同结果。不用一个成功写入断言整任务完成，也不以模拟检查成功宣称音画验收通过。
- 在文件发布、索引更新、迁移、整批完成、原文移出及多文件恢复的关键持久化边界中断后重新打开，验证旧数据或已确认结果可恢复，完成事实不被伪造，迁移不重复，空集合不复活已处理的旧资料。
- 验证最近一次成功接入的恢复信息跨正常任务日志退休及 App 重启仍存在；新成功任务替换旧恢复记录，失败任务不损毁上一份成功记录。整任务撤回应恢复全部受影响内容及待处理原文，后续编辑应阻止覆盖，原文单独恢复不改当前工程。
- 验证旧聊天快照在文档改名、编辑、接入、迁移和恢复后保持当时内容；打开当前文档或目标是独立操作，新请求重新读取当前保存版，历史引用不成为新写入许可。
- 以实际工程 Git、打包与运行检查入口证明待处理区及恢复资料被排除；接入后的普通目标按其原有规则进入版本与检查。完整目录复制保留待处理文档，Git 版本切换不重建它们。
- 前端仅补充主编辑器与原生命令接缝的可观察流程：新建后行内命名和粘贴、保存／放弃／取消、目标差异选择、保存及恢复失败后的重试、外部冲突、焦点和键盘操作、跨工程迟到回复。复用现有资料界面、编辑器草稿退出与文件同步测试习惯，不另建一套模拟业务存储。
- 完成标准为 `npm run check:all` 全绿。原生人工验收另覆盖中文／英文实际输入和编辑、Finder 外部编辑、真实模型的选择与接线质量、失败继续与恢复，以及有关工程的音画结果；自动化与替身不替代这些证据。

## Out of Scope

- 本次规格整理不实施功能、不提交代码、不发布 App 或工程；后续编码须由明确的实施任务启动。
- 图片、音频、压缩包、目录批量扫描，以及超出现有支持范围的二进制或富媒体文档管理。
- 自动运行粘贴代码、保存即调用模型、讨论即接入，或把待处理清单中的所有文档自动收录。
- 普通整理工程顺带清空待处理区，或无明确长期用途时把外部参考全文自动写入工程。
- 多层待处理目录管理、每次编辑的完整文档版本库、多个成功接入任务的无限恢复历史。
- 让 Git 版本、演出工程包或普通助手文件工具携带和管理私有待处理正文及恢复数据。
- 自动改变原有算法、声音、视觉或交互意图；现有明确创作任务以外的艺术重写。
- 将所有多文件写入伪装成不可中断的原子事务，或用保存成功代替真实模型、运行版本和现场音画验收。

## Further Notes

- 长期工程说明沿用已确认的默认位置：工程根 `docs/` 目录；具体目标优先复用已有合适文档。

- 确认来源为《查找创作资料用途》中的 Q1–Q21、2026-11-03 确认的长期工程说明收录修订，以及本轮将四项内容统一纳入 v1.7.0-beta.2 的明确指令；不再开展新一轮产品访谈。

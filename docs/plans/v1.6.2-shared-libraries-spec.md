# v1.6.2：单一较新共享库与作品兼容

规格基线：用户已确认。共享基础能力、Template、四个工具与三个作品的实现及实测已完成；工具正式发行输入、版本冻结和双架构发行验收仍待完成。当前证据见[验收复核](../acceptance/191-child-issue-closeout.md)，版本与完整顺序见 [#190 更新规划](https://github.com/xO-xN/PNDS-App/issues/190)。

GitHub Issue：[191](https://github.com/xO-xN/PNDS-App/issues/191)，标签 `ready-for-agent`。

## Problem Statement

创作者的工程、Template 与内置工具重复携带浏览器库和 Node 生产依赖，工程包较大，维护与升级分散。创作者希望 App 提供可离线引用的一套较新依赖，同时保留工程自带依赖的选择。模型并不广泛通用，应继续由需要它的工程提供。

共享库不能只省去文件而破坏现有作品。Inarticulate III、Inarticulate IV、ASBS 必须在本版 App 发行时可运行；库升级涉及页面加载、输入、OSC 与服务启动，静态 API 检查或 health 成功无法单独证明兼容。

## Solution

App 随发行固定提供浏览器库与选定 Node 生产依赖，每项只提供一个尽量新的、经过验证的版本。工程通过明确引用使用 App 保存的库，来源、版本与运行条件可读；模型、作品页面、谱面、音频与标准模块源码仍由工程维护。

先在隔离试验中验证新版库，必要时由用户更新三个作品，真实验收通过后冻结发行资源。正式采用共享新版写回工程引用并更新工程版本。共享工程包只分发引用，接收方缺指定资源时清楚失败；自包含工程继续使用自带依赖。App 更新与临时试验不会自动采用新引用。

## User Stories

1. As an 创作者, I want 在创作模式加入 App 共享包, so that 多个工程能够复用相同运行库。
2. As an 创作者, I want 共享资源仍由 App 保存, so that 加入引用不会复制一份重复资产。
3. As an 创作者, I want 看见库的用途与固定版本, so that 我知道工程依赖的运行条件。
4. As an 创作者, I want 每项只提供一个经过验证的较新版本, so that 发行资源和维护范围保持有限。
5. As an 创作者, I want 运行时从本机固定资源加载, so that 排练和演出不需要联网获取最新版。
6. As an 创作者, I want 保留工程自带依赖的方式, so that 特殊工程不被强迫采用同一实现。
7. As an 创作者, I want 模型由工程自己携带, so that 通用共享库不积累低频使用的模型资源。
8. As an 创作者, I want ml5 库和模型加载各自明确, so that 使用共享库仍能加载工程自己的模型。
9. As an 创作者, I want 浏览器库和 Node 依赖同版交付, so that 不需要等待另一版本才能完成接线。
10. As an 创作者, I want 共享 Node 包包含实际必要的生产依赖, so that 减少重复后仍能完整解析运行模块。
11. As an 创作者, I want 手机通过工程自己的服务取得共享浏览器资源, so that 本机资源目录不会成为手机不可访问的地址。
12. As an 创作者, I want HTTP 与可信 HTTPS 下的共享资源都可加载, so that 网络入口不会改变资源含义。
13. As an 创作者, I want 资源缺失时看到具体库与版本, so that 我能修正工程或使用合适的 App。
14. As an 创作者, I want 缺版本时不会静默替换, so that 演出不会突然使用未经验证的实现。
15. As an 创作者, I want 正式采用新版写回工程引用, so that 源工程准确描述实际依赖。
16. As an 创作者, I want 采用新版时更新工程版本, so that 分发版本与依赖变化对应。
17. As an 创作者, I want 安装新版 App 不自动改写我的工程, so that 创作内容仍由我决定。
18. As an 创作者, I want 临时试验不自动采用结果, so that 我可以先检查兼容性再更新源工程。
19. As an 创作者, I want 共享工程包只携带引用, so that 分发不重复携带 App 已提供的库。
20. As an 接收方, I want 安装与启动时检查共享运行条件, so that 不会收到虚假的可运行状态。
21. As an 演出操作者, I want 现有自包含工程继续运行, so that 本次能力不迫使旧工程立即迁移。
22. As an 创作者, I want Template 与内置工具真正使用共享库, so that 发行包的重复资源能够实际减少。
23. As an 创作者, I want 标准模块源码继续属于工程, so that 共享依赖不会替代可编辑接线和作品策略。
24. As an 创作者, I want Inarticulate III 使用新版后保持页面与双触点行为, so that 原有演奏方式可延续。
25. As an 创作者, I want Inarticulate IV 使用新版后保持读谱与时间行为, so that 声音链与画面仍可配合。
26. As an 创作者, I want ASBS 的运行依赖可接入共享库, so that 无需为它增加不使用的 p5 或 ml5。
27. As an 创作者, I want 作品谱面、预编译页面与声音资产仍随工程, so that 去重不会误删艺术内容。
28. As an 创作者, I want 三个作品失败后更新并重新验收, so that App 发行时它们都实际可运行。
29. As an 创作者, I want 打包安装后再验证三个作品, so that 源目录成功不掩盖分发缺失。
30. As an 维护者, I want 记录资源来源、固定依赖和完整性, so that 发行内容能够复现。
31. As an 维护者, I want 记录安装资源与 DMG 的真实体积变化, so that 原始文件估算不会被误当安装器增量。
32. As an 维护者, I want Apple Silicon 与 Intel 发行验证通过, so that 两种演出机器获得相同契约。

## Implementation Decisions

- 在已有工程工作流和类型安全命令边界增加共享资源目录、工程引用与解析；App 是库的提供方，工程声明使用，浏览器仍通过工程的同源服务加载。
- 首批库类别为 p5、ml5、Express、qrcode、Socket.IO／client、osc-min；实施前重核稳定候选并以兼容验收冻结确切版本。每个对外库只有一个选定版本，必要传递依赖按实际生产锁树保留，不人工抹平不兼容依赖。
- 模型不纳入共享目录，工程的模型及其完整性检查继续有效。标准模块复制、工程音频映射和作品内容的所有权不改变。
- 共享引用扩展运行与分发契约，明确资源标识、版本与接收方能力；保持自包含工程兼容，不能宣称旧 App 可执行它未支持的共享引用。
- 加入、正式采用与打包复用既有工程身份、来源保护、路径边界、版本冲突和原子保存原则。采用新版是工程内容变化；临时试验与 App 更新不自动更新引用。
- 共享包只分发引用，不提供将 App 共享库物化进包的选项；工程自带依赖继续随工程分发。缺失与不匹配不静默替换。
- 单较新版本替换旧共享版本共存及自动回退方案。三个目标作品必须适配并通过发行验收，失败由用户更新作品后重验，不以暂未迁移例外放行。
- p5 图片加载与输入、Express 监听错误、osc-min 加载与字节接口按实际使用适配；保持作品已有音乐、交互和画面政策。
- Template、内置工具与目标作品的维护仓库分别接线并通过自身检查，再发布固定工具产物进入 App；使用已有 App 与工程测试验收，不依赖后续 CLI。
- 所有实现保持 npm、双语／主题／逻辑方向与现有持久化模式；新模式在对应开发文档记录，稳定装机帮助资源接口保持。

## Testing Decisions

- 最高接缝是用户加入／采用共享包、打开工程、运行、打包并安装后的完整工作流。延伸已有工程打开、运行流程、文件保存与打包安装测试，避免给各 UI 按钮另造互不一致的校验。
- Rust 临时目录与实际 Node 加载验证引用、库版本、生产依赖闭包、只读来源、路径保护、磁盘冲突、重复操作、失败不假报成功；已有原子文件与 bundle staging 是 prior art。
- 浏览器资源通过工程 HTTP／HTTPS 同源入口实际加载，包含断公网冷加载与错误资源；只返回 HTTP 200 不等于 JS、模型或画面正确。
- 三作品按各自声明支持的模式实机验收页面、交互、声音链、刷新／关停及打包安装往返；III 双触点、IV 时间画面、ASBS 预编译页面与谱面分别验证。现有工程测试和 App 真实设备验收是 prior art。
- Template 与内置工具离线回归，保留模型在工程、标准模块与作品资源；共享能力不要求运行时 npm 安装或联网下载。
- 比较迁移前后的实际资源和双架构 DMG，记录新库与适配代码影响；压缩对照和源码扫描只作为线索。
- App 修改通过 `npm run check:all`，各工程通过所属仓库检查，真实结果单独记录；用户启动 App 开发服务器并回报实机操作。

## Out of Scope

- 多个旧共享版本共存、动态获取 latest、自动回退旧共享资源、自动采用未经确认的版本。
- 通用模型共享、自动替代 Max／Ableton、作品音频与谱面去重、艺术策略重写。
- 任意包市场、运行时 npm 安装、自动多文件接线或开放 shell。
- 依赖 v1.6.5 CLI 才允许本版验收，以及以静态或 health 成功代替真实作品可运行。

## Further Notes

本规格是单版本共享机制的交付目标，不代表已迁移。库的具体版本需测试后冻结；三作品在发行时可运行是硬门槛。版本按已确认顺序接续，UI／验收结果合流所属文档，不自动 commit 或发布 App。

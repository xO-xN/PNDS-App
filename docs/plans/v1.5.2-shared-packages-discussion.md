# v1.5.2：App 共享包讨论

状态：讨论中。用户指定以 v1.5.2 讨论本功能；尚未形成实施规格，不授权代码实现、commit 或发布。

## 已确认的方向

- 创作模式应提供加入 App 共享包的常规入口：用户建立使用引用，资源文件继续由 App 保存，不移动或复制到工程。
- 保留工程自带依赖的选择，以支持工程自己的版本需求。
- 首个具体来源是正在开发的 Mobile Sensor Meter：现有资产包含 ml5.js 1.4.0（含 TFJS）及 HandPose detector / landmark lite 模型，并有版本与 SHA256 来源记录。它目前属于该工具工程的资产，尚未加入当前 App 的内置工具注册表，也不是 App 公共依赖接口。
- 需要讨论 App 更新后旧工程试用新版依赖的机制，以及用几句话描述的外部 Skill 协助适配。
- 手机页面全屏不在本次讨论范围。

## 第一轮决定

- 版本安排：按第一轮推荐方案记录，v1.5.2 先交付共享包基础能力和简短外部适配 Skill；共享包的创作界面随 v1.6.0 接入。
- 首版资源范围继续讨论：用户提出同时考虑 p5.js、二维码等现有依赖，并精简内置工具与 Template 中的重复资产。
- 新版试用：用户下一次主动测试工程时自动尝试新版，可检测的错误触发回退；用户确认后才正式采用。演出使用上次确认的版本，App 更新本身不启动工程测试。具体检测范围与版本保留规则待定。
- 工程分发：引用 App 共享包的 `.pnds` 只携带引用，不携带这些依赖资源，不增加把 App 共享资源物化进包的选项。工程自带的依赖仍属于工程资产；接收方版本可用性规则待定。

## 第二轮待决定

- 调查实际 p5.js、二维码、Socket.IO 等依赖的归属与版本后，决定共享资源目录和 Node 服务端依赖是否纳入。
- App 发行与升级如何保留旧共享版本，保证另一台演出机及失败回退所需版本可用。
- 正式采用新版本是工程内容变化还是本机选择，是否写回工程并递增工程版本。
- Template 与内置工具精简到什么范围，第三方共享依赖与可编辑标准模块源码如何划界。

## 资源调查事实

- PNDS Template 携带浏览器资源 `public/libraries/p5.min.js`，文件头版本为 2.3.2。
- PNDS Template、Mobile Sensor Meter 与当前三项内置工具均使用 Node 侧 `qrcode` 生成二维码。二维码包可作为共享依赖候选；工程自身的二维码路由和地址接线仍是工程源码。
- Template、Mobile Sensor 与网络诊断工具还有 Express、Socket.IO 等 Node 依赖。若要精简这些重复依赖，需要明确将 Node 共享依赖纳入本版，而不仅提供浏览器静态资源。
- 第三方依赖精简不等于删除工程自己的页面、服务器接线、控制逻辑或可编辑标准模块。

## 现有规格的关系

[v1.6.0](./v1.6.0-creation-mode-spec.md) 与 [v1.6.1](./v1.6.1-modules-skills-spec.md) 规定的标准模块添加会复制源码到工程，并形成外部 agent 接线交接。App 共享包是新增的引用能力；本讨论尚未变更标准模块的源码所有权或发布范围。

领域术语见根目录 [CONTEXT.md](../../CONTEXT.md)。共享引用与工程自带依赖并存的决定见 [ADR-0010](../adr/0010-app-shared-packages.md)。后续按用户回答更新本记录。

# v1.7.0-beta.2：池主／池客与内嵌本地演出参与

## Problem Statement

乐手希望用自己的笔记本参加本地演出，直接在 PNDS App 查看谱面并按需使用摄像头、麦克风和模型推理，而不必为每场演出准备证书、场地 DNS 或另一套桌面软件。当前 App 面向工程主持，普通局域网 HTTP 谱面与 App 内嵌环境的媒体能力不能直接等同，用户也缺少明确的池主／池客入口。

演出现场还需要防止误操作：切角色不能意外停止演出；断网不能被误报为演出结束；地址复用、换工程或重启不能让旧页面自动加入未经确认的新演出。页面打开、工程接纳与媒体就绪必须分别表达。

## Solution

在现有演出模式的左侧栏先选择池主或池客。同一个 App 一次只承担一个角色，每次进入演出模式重新选择。池主运行本机工程并提供实际连接地址；池客填写或粘贴完整局域网地址，在 PNDS 主窗口内参加一场本地演出。

沿用用户已确认的 A 方案：选择角色后收拢为斜线按钮，空闲两次点击切换；演出或清理中只在按钮内说明先退出。池客保留同次演出的断线页面，新工程和新演出须明确确认；App 管理连接、资源与目标身份，工程继续拥有自身乐谱、加入策略和媒体控件。

## User Stories

1. As a performer, I want Host and Client roles inside the existing PNDS App, so that I can install one application for local performances.
2. As an operator, I want to choose a role in the performance sidebar, so that my responsibilities are clear before starting.
3. As an operator, I want to choose my role each time I enter Performance mode, so that an earlier role cannot silently resume a performance.
4. As an operator, I want one active role at a time, so that hosting and participation cannot interfere within the same App.
5. As a Chinese-speaking operator, I want role labels to show only 池主 or 池客, so that the interface stays concise.
6. As an English-speaking operator, I want role labels to show only PNDS Host or PNDS Client, so that the selected language remains consistent.
7. As an idle operator, I want the diagonal role button to reveal its target on hover or focus, so that I can understand the switch before committing.
8. As an idle operator, I want a second click to confirm a role switch, so that an accidental click cannot change my workspace.
9. As a keyboard user, I want Escape, an outside action or window blur to cancel an uncommitted confirmation, so that I remain in control of the switch.
10. As an operator using reduced motion, I want confirmation without an animation delay, so that the interface respects my system preference.
11. As a performer, I want an active or reconnecting performance to refuse role switching inside the same button, so that I cannot accidentally end my participation.
12. As an operator, I want loading and cleanup to remain locked until cancellation or release completes, so that a late result cannot recreate an abandoned connection.
13. As a PNDS Host operator, I want to explicitly set a node name before hosting, so that performers can recognize my Host.
14. As a local PNDS Host operator, I want hosting to work without hub credentials, so that a local performance needs little setup.
15. As a PNDS Client performer, I want to paste a complete LAN address, so that I can join without an invitation workflow or discovery service.
16. As a PNDS Client performer, I want recent connections to show Host node names, so that I can find a machine rather than guess from project names.
17. As a performer, I want recent Hosts to use stable identities, so that renamed Hosts remain recognizable and identical names do not merge different machines.
18. As a performer, I want to explicitly update a changed Host address after identity verification, so that an old address cannot silently select another machine.
19. As a performer, I want a reused address to show the different Host and preserve my original record, so that I can decide whether to join the new Host.
20. As a performer, I want the score embedded in the PNDS window, so that I do not need to manage an external browser.
21. As a PNDS Client performer, I want to join one Host and one performance at a time, so that my page, media and connection have a clear owner.
22. As a performer, I want compatible projects to provide their own score and input controls, so that the Client remains a general entry rather than a Sensor Meter utility.
23. As a performer, I want a truthful distinction between page loading and project acceptance, so that an open page is not presented as confirmed participation.
24. As a performer using a project without acceptance feedback, I want to open a compatible score with an unknown-acceptance status, so that optional roster support is not a barrier.
25. As a performer, I want ordinary network loss to preserve my score and the project’s reconnect behavior, so that a short interruption does not reset my performance.
26. As a performer, I want a verified project change to release the old page and media, so that it cannot continue collecting or join a different project.
27. As a performer, I want to explicitly confirm a new project before its page loads, so that the Host cannot move me into another performance without my choice.
28. As a performer, I want an explicit Host stop to end my participation, so that a later restart of the same project still requires a new join.
29. As a performer, I want an unreachable Host to remain an unknown connection outcome, so that an outage is not falsely described as an ended performance.
30. As a performer, I want a first refresh click to leave my score and media unchanged, so that I can cancel an accidental reload.
31. As a performer, I want a second refresh click to release and reload only my current page after rechecking its performance, so that refreshing cannot restart the Host or enter a new context.
32. As a performer, I want refresh to retain project web data without claiming to preserve unsaved musical state, so that I understand the recovery boundary.
33. As a performer, I want leaving to release page, proxy, Worker and media resources, so that my device stops participating when I leave.
34. As a PNDS Client performer, I want leaving to return to the connection page in the same role, so that I can choose another local performance without repeating role selection.
35. As a performer, I want persistent web data isolated by Host and project, so that another Host cannot receive my previous project’s recovery identity.
36. As a performer, I want a manual rejoin to reuse eligible saved project data after App restart, so that identity recovery is available without automatic participation.
37. As a PNDS Client performer entering Creation mode, I want participation cleaned up before the local creation home opens, so that a remote project is not mistaken for an editable local project.
38. As a creator, I want existing Host-to-Creation continuation and multiple performer test windows preserved, so that the new role does not regress my workflow.
39. As a performer, I want Host protocol upgrades and project adaptation issues explained separately, so that I can ask for the correct repair.
40. As a performer, I want camera permission denial and model readiness represented honestly, so that a loaded page is not mistaken for working media.
41. As a performer, I want actual connection addresses derived from verified runtime ports, so that automatic port fallback cannot leave a stale address on screen.
42. As a PNDS Client performer, I want only participation controls in my App chrome, so that local audio-engine or Host project controls cannot affect the wrong performance.

## Implementation Decisions

1. 此功能归属 v1.7.0-beta.2，HTML A 原型已由用户确认。保留演出／创作两种模式；角色属于演出模式，不增加第三种模式。
2. 池主／池客互斥，池客一次只参与一场演出、持有一个演奏页面。每次进入演出模式重新选角色，不持久化自动加入意图。节点名、最近连接和合格的工程网页数据分别持久化。
3. 使用既有浮动侧栏、底栏、系统字体与四主题。中文角色名只显示池主／池客，英文只显示 PNDS Host／PNDS Client；保持 RTL 逻辑布局与现有快捷键归属。
4. 斜线按钮默认显示当前角色，悬停或键盘聚焦提示目标；空闲首击仅原位提示再次点击，次击提交。未提交确认可取消，按钮在确认期间保留实例与焦点，减少动态效果时不等待动画。
5. 加载、待接纳、已参与、接纳未知但页面仍活动、断线重连及清理期间拒绝角色切换，只在按钮内提示先退出。不得以角色切换自动关停或弹出替代确认。清理失败保留事实和重试入口，不提前解锁。
6. 池主必须先显式设置节点名，不采用电脑名称回退。本地演出不要求 hub 地址或 token。保留池主既有选工程、音频、投影及启动能力。
7. 池客填写或粘贴池主显示的完整局域网地址；复制只是输入辅助，不增加独立邀请流程。可变端口必须出现在实际地址中，不承诺仅凭裸 IP 定位服务，不增加自动发现。
8. 池客主区内嵌工程 performer 页面，侧栏提供地址、最近池主和连接信息；底栏提供离开、刷新和设置，不出现本机工程管理、音频引擎或投影控制。具体传感器控件由工程提供。
9. 本地演出仍指场地局域网。池客连接另一台池主不构成跨互联网节点，不启动池主工程服务或 App 托管的 scsynth，也不隐式获得整场录制控制；池客输入可由池主主持的工程记录。
10. 新增 App 拥有的池客接入协调边界，统一管理目标身份、加入／取消／离开、页面、代理及异步结果归属。原生侧拥有网络、运行身份与资源生命周期；前端使用类型安全命令与事实事件，不读取谱面 DOM 猜测业务状态。
11. 稳定池主身份、工程身份、本次演出身份与工程座位／claim token 分别表达。名称、IP、前端本地运行计数或单独的 manifest 工程标识都不能代替前述接入身份。同工程停止后重启属于新演出，短时网络丢失不改变演出身份。
12. 最近连接按稳定池主身份组织，节点名仅用于显示。同名不同设备不合并，同一池主改名或换工程不新增记录。更新地址须核验目标身份；地址返回另一池主时保留原记录，用户明确选择后才保存新池主记录。
13. 每次进入工程前持有用户确认的接入上下文；Host 在页面资源、HTTP polling 和 WebSocket 进入工程之前验证该上下文仍对应当前运行。旧确认不能被后台发现的新工程／新演出静默覆盖，事后提醒不能替代加入前拦截。
14. Host 的 App 接入元信息仅公开参与所需的身份、名称、协议兼容及当前演出事实，能够表达池主在线但已结束演出；不得直接公开含绝对路径、日志或管理信息的本机运行快照。
15. 池客页面拟从仅绑定回环接口的受管来源获取页面、脚本、模型、Worker 及实时连接，App 转发至已确认的 Host。转发层保持工程音乐消息语义，不能成为任意目标的通用代理。
16. 内嵌工程页面使用低权限 WebView／frame，不获得创作文件写入、模型凭据或管理命令。网页来源可信、系统授权、WebView 媒体授权和模型就绪分别核实，不能用 App 外壳或能力声明代替实机证明。
17. 首版要求 Host 支持新接入协议；旧 Host 提示升级，不降级绕过身份门禁。工程须声明并实际遵循完整 performer URL、同源资源与实时连接约定；未声明先核对，实际不符合时说明具体适配项，不因此阻止池主按既有方式运行。
18. 完整 performer URL 能力不代表动态监听端口能力、摄像头能力或接纳名册。工程面向普通手机／浏览器的安全上下文需求保留，monitor 既有内部连接职责不被静默替换。
19. 页面 onLoad、HTTP 成功和其他设备在线均不能证明本池客已被接纳。只有工程反馈且能关联当前参与者时才显示实际接纳状态；可选反馈缺失或无法关联时允许打开兼容谱面，显示谱面已打开／工程未提供连接状态。
20. 普通断线保留同一页面、媒体意图及工程自身重连／媒体逻辑，不统一清除消息、重载或恢复音乐状态。无法核实的无响应只表示连接中断。
21. 核实换工程时先断开、销毁旧页并释放媒体，再提示演出变化；用户明确确认后才载入新页。Host 明确停止同样结束参与并释放资源；后来同工程重启也须明确加入。
22. 刷新独立采用按钮内两次点击：首击保留页面与媒体，取消不改变演出；次击释放旧页、重新核验并重载当前已确认的演出。演出变化仍需确认，无接纳反馈的工程刷新后仍为未知。刷新不重启 Host，不保证恢复页面未保存的演奏状态。
23. 主动离开、切入创作和实际退出 App 清理页面、连接、代理、Worker、媒体及迟到异步操作。清理完成后离开回池客连接页并保留角色／最近连接；终止通知页切角色必须进入目标角色空闲态，不携带旧错误或加入意图。
24. 网页存储按池主与工程隔离并持久保留，供下次手动加入；保存凭据不替代新演出的确认。回环端口变化不能任意改变来源而破坏恢复，隔离与稳定来源机制必须先验证。保存数据不保证座位、推子或服务器未持久化状态的统一恢复。
25. 池客进入创作先结束本地参与并进入本机创作首页；池主按既有非对称工程接续规则处理。创作测试窗口能力保留，返回演出模式结束测试并重新选择角色。
26. 自动端口管理由独立规格拥有：本功能只使用已核验的运行端口与公开入口，不再假设固定端口。三层入口与端口变化的网页恢复须共同验收，不能在两项规格中重复实现分配器。
27. 普通窗口隐藏、最小化和全屏沿用 App 既定行为，不将窗口隐藏或暂时失焦当作明确离开；工程媒体的可见性处理仍属工程与平台能力。
28. 持久化、状态 selector、命令桥、i18n 和原生生命周期遵循现有项目规范。近期记录保存失败如实反馈，不能把未落盘状态宣称为已保存。

## Testing Decisions

1. 用户已确认四项共用的测试原则：从 App 公开操作／命令进入，观察真实临时工程、文件、受管进程和 HTTP／WebSocket 的结果；只测试外部可见行为，不以私有字段、函数调用顺序或实现快照替代效果。
2. 本功能主接缝为公开的池客参与操作及状态事件，经受管接入协调边界连接真实 Host fixture，观察页面来源、网络路由、上下文拒绝与资源释放。新接缝集中在这一应用层边界，不在组件、代理和工程音乐协议各自建立旁路测试 API。
3. 优先复用既有 session 监督、真实网关／Node fixture、端口 lease、HTTP 与 Socket.IO 测试材料。补充公开加入、取消、离开及重试的端到端流程；不能因为已有内部 supervisor 测试，就声称完整加入流程已覆盖。
4. 用真实 TCP、HTTP polling 与 WebSocket 证明：旧上下文不能接入更换后的工程，同 manifest 标识的副本替换和同工程重启也被识别；不以只关闭旧连接或 UI 文案检查代替加入前门禁。
5. 区分网络故障、明确停止、工程变化、Host 身份复用、协议不兼容与工程需适配。验证保留原最近记录、明确确认前不载入、不发加入，并验证取消和迟到结果不会重建页面或连接。
6. 通过公开生命周期与真实资源观测验证加入中取消、快速重试、刷新、离开中切角色、切入创作和退出清理；清理失败不能解锁角色，运行结束不能遗留可用旧接入。
7. 持久化验收跨 App 重启、Host 改名、IP／入口端口变化和不同工程，检查数据隔离、手动重进、身份冲突以及旧数据不被错误发送给另一目标。端口变化场景与自动端口规格共用验收素材。
8. 少量界面测试通过现有命令桥与状态事件驱动可见界面，覆盖每次重选、双语单独标签、两击切换／刷新、取消、焦点、减少动态效果、活动锁定、未知接纳及创作接续。复用既有独立 performer 窗口和模式切换的测试习惯，避免复制状态机实现。
9. 用户确认的 HTML 只作为交互基线。正式签名／打包 App 在支持的 macOS 基线上进行双机验收：摄像头／麦克风首次授权、拒绝、停止、退出真实释放，Sensor Meter Worker／模型加载、首个推理、后台恢复，以及 polling／WS 和其他兼容工程。模拟媒体或浏览器页面打开不能替代这一关。
10. 完成标准包括新业务行为回归、仓库完整检查全绿以及上述原生验收证据；不能为通过原型而静默改用外部浏览器、提高系统基线或扩大页面权限。

## Out of Scope

- 独立演奏者安装包、第三种 App 模式、同 App 同时主持与参与，或池客同时参与多场演出。
- 自动发现、仅输入裸 IP 自动寻找可变端口、跨互联网连接、NAT 穿透、hub 配置与网络音频传输。
- 外部浏览器回退、统一传感器控制面板、为任意工程自动转换网页代码或绕过兼容协议。
- 用 App 统一解释乐谱消息、保证所有工程的座位或音乐状态跨服务器重启恢复。
- 自动启用媒体、自动加入新工程／新演出，或从页面加载推测已被接纳。
- 重新设计既有创作工作台、移除多测试窗口、改写池主的既定创作接续和手机 HTTPS 入口。
- 在此票重复实现端口分配器、演奏记录系统或待处理文档系统。

## Further Notes

- 用户已确认本次 chat 的 HTML A 原型，并确认本功能、演奏记录、自动端口管理和待处理文档全部纳入 v1.7.0-beta.2；原 v1.7.1 安排已被取代。
- 本规格承接池主／池客 ADR，并保留既有模式切换 ADR 的池主语义。原型中的 IP、端口、节点名及媒体状态均为合成演示，不是正式协议字段或实机验收结果。
- 运行端口由自动端口管理规格拥有；本票接入它提供的实际入口与生命周期。需要通过共同场景证明更换端口不会破坏池客身份隔离与恢复。
- 首先验证回环来源、低权限内嵌 WebView、媒体／Worker 和持久存储方案，再推进可发行实现。技术验证失败必须如实说明约束，不借此静默改变用户确认的产品行为。

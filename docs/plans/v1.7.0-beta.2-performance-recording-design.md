# v1.7.0-beta.2 演奏记录与叠加排练设计讨论

状态：用户已确认产品方案及录制 A 原型，并在本轮将四项范围统一纳入 v1.7.0-beta.2；后续实施以[正式规格](./v1.7.0-beta.2-performance-recording-spec.md)（GitHub #257）为准。本文保留逐轮决定和工程核查，历史待确认文字不覆盖最新整体确认；本轮不实施功能。

## 已确认的目标与边界

- 功能内置 PNDS App，纳入 v1.7.0-beta.2；功能所在模式已确认，具体布局仍待确认。
- 目标一：记录整场演出的演奏者信息、乐谱与指挥等必要信息，使演出结束后可回放。
- 目标二：作为创作流程，创作者使用自己的设备逐遍扮演不同演奏者，可选择相同或不同的乐谱选择序号，体验并录入各演奏者，最终形成包含全体演奏信息的一份记录。
- 保存演奏信息，回放时实时生成音频；不录制音频，不要求保存纯音频合成内部的随机状态，以简洁可靠为优先。
- 叠加过程不需要演出分支或冻结前遍乐谱。第一遍录演奏者 1；第二遍回放 1 并录 2，得到包含 1、2 的记录；第三遍回放 1、2 并录 3，得到包含三人的记录。每遍都能看到已有演奏者的演奏，声音按当遍内容生成。
- 已有信息被继承，不将回放内容重复追加。新叠加演奏引起的乐谱变化可以发生；本轮不据此加入分支、多个候选录次或局部编辑系统。
- 用户自行在设备上选择编号、判断准备状态和开始时机；App 不增加编号监控、准备确认或起录门槛。记录所需的演奏来源及编号变化由工程适配接口提供，不作为用户准备检查。
- 记录演奏者与乐谱选择序号分开：同一序号可有多个独立记录演奏者；同一物理设备新增叠加一遍也创建新的记录身份。仅明确重录指定演奏者才替换那一份演奏，不按序号或设备自动合并／覆盖。

领域词汇归根目录 [CONTEXT.md](../../CONTEXT.md)；已确认的记录边界归 [ADR-0015](../adr/0015-performance-recording-realtime-audio.md)。用户明确要求先确定完整方案，再开始实现。Q8 已确认允许整位演奏者替换，取消或失败保留旧内容；Q14 已确认可提前停止并保存本遍，未录后段视为未演奏，或明确放弃本遍保留原内容。

## START 对齐的解释与技术核查

用户已接受 Q11，因此 START 及其他实际生效的指挥变化属于记录内容。录制按钮与作品 START 是两个动作，记录时间与乐谱进度也不同；准备等待、作品暂停仍占用记录时间，定位倒退也不倒退记录时间。

以 runes 为例，第一遍记录时间 0 秒开始录制，5 秒按作品 START。后续每遍先恢复记录初态，从记录 0 秒开始，自动在第 5 秒执行同一 START，重放其后的暂停和定位。创作者不再次手动 START；START 前五秒的准备等待也保留。第三轮已确认锁定新的手动指挥操作，防止改变这一共同时间基准。

2026-11-03 早期对 `../runes-pnds` 的只读复核（以下 monitor 自主推进／POST 机制属于当时版本，已被后续 server 管理方案替代）：

- `public/monitor.js:452` 以本地 `millis()` 推进乐谱进度；`public/monitor.js:759` 的播放切换会发布明确的播放状态，到曲终后再次开始还会先归零。回放应恢复明确的播放／暂停／定位状态，而非再次调用依赖当前状态的 toggle。
- `public/monitor.js:254`、`:669`、`:873` 表明开始／暂停立即发布，定位合并发布，播放期间另有心跳，后台隐藏时不发心跳。应捕获全部实际生效的变化；完整接纳的 POST 状态也可表达这些变化，不能笼统排除状态记录。
- `server.js:345` 接受最后收到的 POST，没有发布者与回放主权门。monitor 又不回读 server 状态；仅往 server 注入回放状态会被 monitor 自主推进及发布覆盖，只禁用可见按钮也不够。
- `public/performer.js:163`、`audio/controller.js:166`、`:191` 各自外推进度，音频有更新超时释放。因此回放驱动仍须维持状态同步和存活，不能仅发送稀疏指挥事件。

该版本的适配推论：恢复已保存的 composition 与初始 transport，捕获带共同记录时间和顺序的生效变化；回放时让页面、server 和音频服从同一个时间驱动，暂停原 monitor 的自主推进与发布，并持续同步有效状态。这些同步心跳不重复加入演奏内容。现行 server 已接管 composition 与 transport，不能把旧接线建议原样套用；共同记录时间、保存生效指挥变化及单一回放时间驱动的产品原则不变。

## 同序号多演奏者（本轮明确）

用户明确要求：Runes 中一个乐谱选择序号可能由多个演奏者演奏，创作者一人用同一设备逐遍录制这种情况也必须正确回放。记录身份不以编号、设备或瞬时 socketId 作为唯一主键。

示例：第一遍设备选择序号 3，录为演奏者 A；第二遍同一设备仍选序号 3，回放 A 并新增演奏者 B；第三遍选序号 5，新增 C。最终同时存在 A→3、B→3、C→5。重录 A 时 B 保留，即使它们都选 3。

原型以 A、B、C 表示记录演奏者，另列“乐谱序号”；新增 `scene=shared` 的 runes 样例。原型只呈现身份分离及合并／替换的内存行为，真实多来源发声必须在适配完成后验收。

本轮现行 `../runes-pnds` 源码核查（只读，未运行工程）：

- `server.js:98` 校验乐谱 number 为 1–9，`:123` 的入场不独占编号；`:137` 将完整输入按 `context.socketId` 交给音频，`:143`、`:160` 按独立来源保留触点，不按 number 去重。
- `audio/controller.js:192` 的声音键包含来源 socketId、乐谱元素与种子等信息，`:245` 释放指定来源。同序号不同来源可独立建立声音；`public/monitor.js:362` 遍历全部触点，按各自 number 找到锚点。
- `test/instrument.test.js:139` 已有十二个来源同时使用 `number:1` 的声音节点用例。当前声音节点上限为十二，包含释放尾音；它属于工程原有音乐／资源政策，不是记录演奏者数量上限，录制器不隐式修改它。本轮仅阅读该测试，没有据此声称录制已实现或声音已验收。
- `server.js:43` 以 `createScoreSession()` 管理 composition 与 transport，`public/monitor.js:569` 通过 `scoreLink.command()` 发指挥；此前 monitor 自主生成、POST 和心跳的核查已属历史版本。

实现要求与必须验收的行为：新增叠加生成新的记录演奏者；各记录演奏者回放为独立工程运行来源，不能复用同一物理设备的来源键而互相覆盖；只有明确重录目标才替换对应身份；重连按工程提供的恢复信息归回本遍原身份，不能把“重连”误作“新增叠加”；同编号多来源、同设备连续两遍同编号、只重录其中一位及断线释放不影响另一位，均须覆盖真实接口和声音验收。

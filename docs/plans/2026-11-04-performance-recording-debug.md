# 创作模式演奏记录：诊断与逐轮决定

日期：2026-11-04（Asia/Shanghai）。状态：Q1–Q6 及整体实施范围均已确认，工作区实现已更新；原生声音验收待用户完成。全量检查与真实工程回归结果单独核对，不以本设计记录替代运行证据。

## 用户报告与事实

1. 演奏记录弹窗只能切换记录，无法删除；希望采用“记录列表 → 记录详情 → 返回列表管理”。
2. Runes 的 11:23:50 AM、3:08 记录仅第一遍有触点与声音，后两遍录制及回放均无有效演奏。
3. 希望复用同一虚拟演奏者窗口，自行更换工程编号；每轮可以一人或多人演奏，按轮新增或覆盖，无需管理演奏者序号。

当前 `PerformanceRecording.tsx` 直接混排 Select、录制、回放、叠录及单个演奏者重录；原生命令没有删除能力。“删除”属于需要新增的管理功能。现有规格已要求同设备连续叠录，但仅接纳一个现场来源；多人同轮叠录及整轮重录需要修订领域模型与适配协议，不能只隐藏演奏者列表。

### 最小反馈环及对照

临时诊断脚本在 `/tmp/pnds-recording-admission-repro.cjs` 与 `/tmp/pnds-recording-admission-controls.cjs`，通过生产 adapter 的 `handle()` 请求入口执行，不启动 dev server、不改产品源码。

```sh
node /tmp/pnds-recording-admission-repro.cjs "$PWD/src-tauri/resources/performance-recording/adapter.cjs"
node /tmp/pnds-recording-admission-controls.cjs "$PWD/src-tauri/resources/performance-recording/adapter.cjs"
```

最小复现：注册旧来源 → 普通首录并停止、旧来源仍在线 → 开始叠录 → 注册新来源 → 输入一次触点 → 停止并检查事件。红色断言要求新来源获准并采集触点，实际得到 `admitted=false`、`captured=false`、`touches=0`，命令退出码为 1。

在检验前按顺序列出的假设为：开始叠录已锁定旧来源；多窗口时最近注册者与实际操作设备不同；输入自身无效；触点已采集但回放丢失。原 JSON 排除了最后一项作为后两遍缺失的主因，单变量对照如下：

| 仅改变的条件                       | 观察                           |
| ---------------------------------- | ------------------------------ |
| 新来源在开始叠录后注册             | 被拒绝，无触点                 |
| 将同一新来源的注册提前至开始叠录前 | 被接纳，触点进入事件流         |
| 沿用同一来源，在第二轮改变工程编号 | 被接纳，保存新编号及触点       |
| A 注册、B 注册、A 换号后开始叠录   | 仍只接纳 B；换号不改变注册顺序 |

App 自带、Runes 自带、III 自带的三份生产 adapter 结果一致。诊断时的 adapter 在开始叠录时绑定最近注册的在线来源，`mappedId` 拒绝其他来源；Runes 有效输入入口先检查 `admitted`，因此拒绝同时阻止触点显示、发声与采集。该失效路径已复现，原记录未保存当时的窗口加入顺序，不能据此宣称重建了用户的完整操作过程。上述验证没有覆盖实际扬声器输出。

### 实施后的同场景回归

新 App 通过 `livePassId` 使用多人轮次路径，旧 `livePerformerId` 请求保留旧控制器兼容语义。原最小复现仅将请求改为新的 `livePassId` 后，在相同“旧来源在线 → 开始叠录 → 新来源加入”顺序下得到 `admitted=true`、`captured=true`、`touches=1`，命令退出码为 0；两来源均属于新轮次。临时绿色重放为 `/tmp/pnds-recording-pass-repro.cjs`。

留存自动化入口为 `node --test src-tauri/resources/performance-recording/adapter.test.cjs`，并由 Rust recording 测试调度。原生公开控制的实际 Runes 回归还覆盖第一轮、第二轮起录后加入另一来源、同号多人输入、第三轮复用设备换号、落盘轮次归属及实际 monitor 广播回放，避免仅验证 helper 而未验证 App 接线。实际声音仍由用户验收。

## 已确认的产品决定

- **Q1：以整轮管理和重录。** 每轮自动收录当次实际参与的全部演奏端，可一人或多人。叠加保留其他轮；重录整体替换所选轮，包括原轮内本次没有参与者的旧演奏。不做单人替换或时间片段覆盖。
- **Q2：自动保存与导出分开。** 停止／正常完成录制自动保存到 App；列表提供删除和导出，导出不是保留记录的必要步骤。
- **Q3：删除两层都支持。** 列表可删除整份记录；详情可删除其中某轮。删除轮次只移除该轮演奏，保留其他轮、共同起始状态、指挥过程和总时长。
- **Q4：复用设备，用户自行切工程编号。** 同一个虚拟演奏者窗口可反复使用，同号也可叠录；App 自动隔离每轮记录身份并接纳多人，不增加设备选择、编号跟踪或强制新窗口。App 不自动轮换工程编号，工程自身的入场与编号规则仍有效。
- **Q5：旧内容作为一轮保留。** 完整保留旧文件，现有全部演奏作为一轮“已有内容”；之后新录按新轮次管理。不猜测旧文件中每遍的分组。

领域定义见根目录 [CONTEXT.md](../../CONTEXT.md)，替换粒度的修订见 [ADR-0016](../adr/0016-recording-pass-as-management-unit.md)。

## 已整体确认的实施方案（Q6）

1. **列表**展示各份演奏记录，提供新录制、进入详情、删除和导入／导出。新录制明确创建另一份记录，不随当前选择含混改变含义。
2. **详情**提供整份回放、叠加新一轮、轮次列表、整轮重录及删除某轮。轮次可包含多人，不展示需要用户管理的演奏者 ID。录制完成返回该份记录的详情。
3. **输入**每轮接受所有按工程规则接纳的现场来源，并为各来源保留独立身份；回放来源不再次采集，普通首录、连续复用同设备、新窗口加入、多人同时演奏均进入同一规则。纯回放仍只由记录驱动。
4. **共同时间**沿用首轮确定的初态、指挥过程及总时长；新增、重录和删除轮次不改变这些公共信息。整轮提前停止保留已录部分，剩余时间没有该轮演奏；取消／保存失败保留上一完成版。删除最后一轮可留下同一时间框架的空记录，之后仍能录入新一轮；修改时长／指挥过程则新建记录。
5. **操作期间导航**返回列表或收起弹窗不中断当前操作，底栏继续显示状态；活动记录返回详情可停止／放弃。当前操作期间禁止删除该份记录及其轮次，避免删除尚在使用的数据。
6. **兼容**旧记录以一轮“已有内容”载入并保留原文件；已缺失的触点不伪造补全。新数据明确保存轮次归属与公共指挥信息。协议、格式版本和工程接线由实现验证确定；不让旧适配器把多人叠录悄悄降级为只采一个来源。

用户以“是，按此修复并实现”整体确认第 1–6 项。实施同步 App、实际 Runes／III 适配接缝与对应契约，保留工程自身音乐规则。

## 修复验收

- 同一设备连续三轮，同号／换号均有实时触点及可回放事件，回放来源不重复采集。
- 开始叠录前或之后加入新来源均可正常录制，不依赖窗口注册先后顺序。
- 两个或多个来源同轮录制，各自独立发声与显示；下一轮可改为一人。
- 整轮重录同时移除目标轮所有旧参与者，其他轮不受影响；放弃或保存失败保留旧完成版。
- 删除整份记录及单轮、删除首轮／最后一轮、自动保存与导入／导出、旧记录兼容均覆盖回归。
- 首录前已有持续触点，删除或重录所属轮次后不再恢复其旧触点；公共乐谱与指挥过程保留。
- 返回列表／收起面板不中断；当前操作不能误删；UI 文案全量双语。
- 原生快照携带工程路径与记录 ID；旧操作事件和状态恢复回执以任意顺序迟到，都不能把活动记录归到新工程。错误适配器回传其他轮的身份事件必须拒绝，旧完成版保持原样。
- 产品改动完成必须 `npm run check:all` 全绿，实际声音由用户启动 dev server 并实机验收。

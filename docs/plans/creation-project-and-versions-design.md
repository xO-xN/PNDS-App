# 新建工程、版本与 GitHub 的创作体验

产品方案和 HTML 原型已确认，纳入 v1.7.0-beta.4。本文保留创作工作台的用户流程和验收结果。实施见[正式规格](./v1.7.0-beta.4-creator-project-versions-spec.md)与 [#339](https://github.com/xO-xN/PNDS-App/issues/339)。[交互原型](../prototypes/creation-project-versions.html)

## 新建工程

创作首页和工程菜单共用一张表单。创作者填写「工程名称」，确认「保存位置」。位置记住上次选择，表单预览新建的文件夹。工程名可以使用中文。本地文件夹名和 GitHub 仓库名分别生成，均可修改。

GitHub 摘要始终可见，例如 `GitHub · 公开 · @mira/river-pnds`。默认使用已连接的个人账号，仓库默认为公开。折叠的「高级选项」可选择有权限的组织、修改本地文件夹和远端仓库名称、填写作者和简介、调整提交身份，或选择「私有」和「暂不上传」。新工程的初始提交和后续版本默认使用占位邮箱，创作者可主动填写 GitHub 的 `noreply` 邮箱。

| 表单状态                       | 主按钮              | 提交结果                                                       |
| ------------------------------ | ------------------- | -------------------------------------------------------------- |
| 已授权，选择公开               | 创建并公开到 GitHub | 创建本地工程、建立公开仓库并上传初始工程版本                   |
| 已授权，选择私有               | 创建并上传到 GitHub | 创建本地工程、建立私有仓库并上传初始工程版本                   |
| 选择暂不上传                   | 创建本地工程        | 创建本地工程和初始版本，打开工作台                             |
| 需要连接账号                   | 连接 GitHub         | 浏览器授权后回到原表单，核对实际目标再提交。可「先在本机创建」 |
| 已登录，目标仍需安装或批准权限 | 继续授权            | 浏览器完成授权后回到原表单，可继续提交或先在本机创建           |

「创建并公开到 GitHub」一次确认所显示的目标和初始工程版本。PNDS 先创建本地 Blank 和独立工程身份，再从官方 `xO-xN/PNDS-Template` 创建普通工程仓库、核验、上传并绑定。GitHub 显示 `Generated from` 来源，仓库默认分支的工程内容与已确认的本地版本一致。是否加入公开工程目录由创作者另行决定。[GitHub 模板建仓](https://docs.github.com/en/rest/repos/repos#create-a-repository-using-a-template)

本地创建成功后即可进入工作台。GitHub 步骤失败时显示「工程已创建，GitHub 上传未完成」，提供「继续上传」。继续操作指向原先确认的仓库、可见性和初始版本，即使后来保存了新版本或切换了路线。仓库已创建时沿用原仓库。建仓或推送响应丢失时先查明结果。同名仓库身份不明确时，显示候选和处理选项，由创作者明确选择。仓库名确实已被占用时给出可编辑的建议。组织限制公开时，可改为私有、换目标或先在本机创作。目标或可见性有变化时，重新展示结果供创作者确认。

选择「暂不上传」的工程可在版本页点「上传到 GitHub」。沿用仓库设置，提交前展示目标、可见性和**当前路线将上传的已保存历史**。历史中早先保存、后来删除的文件和原有的提交邮箱仍可被看到。已有仓库从「管理」绑定，沿用空仓或共享历史检查。从官方模板创建的目标仓库沿用模板来源、快照核验和历史保留规则。[模板核验与历史保留](../adr/0019-creator-github-template.md)

## 保存与浏览版本

「版本历史」位于中栏的「PNDS 创作助手」旁。「保存当前版本」位于版本历史内，先保存工程文件的编辑草稿，再按现有收录规则记录工程版本。页面提供默认版本名，保存后留在版本历史。成功提示和历史条目都提供「重命名」。`⌘S` 保存当前文件或文档。磁盘冲突需要处理后再记录工程版本。未开启自动备份时，保存只发生在本机。

进入「版本历史」时，左栏切换为「比较文件」，提供变更／全部、路径筛选和目录展开，历史中已删除的文件也可查看。中间上方是按父版本关系连线的版本树，单路线显示为一列，分叉显示在实际父版本处。版本名称、时间、当前版本和查看中的版本分别可辨认。下方始终显示所选文件的代码差异，支持逐行与左右对照，默认比较父版本和选中版本，也可与当前已保存文件比较。选择版本或文件只改变查看状态。「打开当前文件」进入编辑器并保留原有草稿。

「切换到这条路线」打开该路线的最新版本，之后沿它保存。「从此版本继续」打开选中的旧版本，下次保存建立新路线，原路线及其版本仍可访问。

有未记录的修改时，优先提供「保存后切换」和「取消」。「放弃修改」在次要入口，需要明确确认。工程运行中提示「停止运行并切换」，切换后保持停止。未完成的助手任务、外部暂存和冲突按现有保护处理。[版本切换规则](../adr/0011-creator-git-version-navigation.md)

## GitHub 状态与管理

版本页用一行展示当前工作区所在路线的 GitHub 状态。历史条目的选中状态只影响详情。状态行按情况给一个主要动作，并保留「管理」入口。新建时首次上传中断的状态指向工程原有的创建操作。

| 当前情况                    | 状态示例                      | 主要操作               |
| --------------------------- | ----------------------------- | ---------------------- |
| 仅在本机                    | 仅在本机                      | 上传到 GitHub          |
| 新建时首次上传中断          | 工程已创建，GitHub 上传未完成 | 继续上传               |
| 当前路线有待备份版本        | 有 2 个版本尚未备份           | 备份到 GitHub          |
| 当前路线最新版本已备份      | 当前路线已备份                | —                      |
| 自动备份因离线等待          | 已保存到本机，待备份          | 联网后按此路线设置恢复 |
| GitHub 有可直接应用的新版本 | GitHub 有新版本               | 从 GitHub 更新         |
| 两边各有新版本              | 本机与 GitHub 各有新版本      | 查看处理方法           |
| 远端分支被删除              | GitHub 上的路线已删除         | 确认重建               |
| 写权限丢失                  | 需要 GitHub 授权              | 重新授权               |
| 可见性变更                  | 仓库已改为公开                | 确认后继续             |
| 升级后待确认                | 自动备份已暂停                | 查看此路线设置         |

离线时，远端信息标为上次检查结果。停在历史版本时，可切回某条路线或保存成新路线后再进行日常备份。手动备份上传当前路线已保存的历史，草稿和未记录修改留在本机。新路线首次备份由创作者主动发起，公开时显示目标和范围。自动备份默认关闭，在该路线完成首次备份后才可单独开启。新建时上传初始版本可计入该路线的首次备份。离线待备份记录对应原工程、仓库和路线，打开原路线且联网后按授权范围恢复。

「管理」提供仓库链接、可见性、刷新、绑定已有仓库、解绑、换仓和当前路线的自动备份设置。账号连接和退出位于全局「设置 → GitHub 账号」。「从 GitHub 打开工程」位于工程选择器，沿用来源仓库，默认手动备份。仓库可见性在 GitHub 修改。PNDS 发现变更后暂停自动备份，显示新可见性，等创作者确认后继续。换账号时保留原目标，等待重新授权或明确换仓。解绑、换仓须明确确认，旧目标的待传任务随原绑定解除。[GitHub 仓库可见性](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)

「从 GitHub 更新」由创作者发起。仅在工作区满足保护条件、远端是当前路线的直接延续时应用。双方各有新版本时，使用外部 Git 工具处理，再回到 PNDS。远端删除了曾备份的路线时暂停自动备份，重建前需要确认。[同步边界](../adr/0018-creator-github-backup.md)

## 已有工程迁移

升级保留本地工程、版本、路线、仓库绑定和旧待传记录。旧版只记录工程级开关，升级时将旧自动备份迁为「已暂停」。创作者可手动备份，或为已完成首次备份的路线重新开启自动备份。无法核实该路线曾完成首次备份时，先由创作者确认一次手动备份。远端已包含目标版本时，核对结果即可。待传记录留在原目标和路线，升级本身只更新本地设置。未绑定工程显示「仅在本机」，直到创作者主动上传或绑定。

## 场景验收

下表是实施后的预期结果。自动化覆盖表单、工作台交互、真实临时 Git 历史和中断恢复。macOS 实机核对界面、键盘、系统浏览器授权和真实 GitHub 操作。真实建仓使用专用测试仓库。

| 场景                  | 前置条件与操作                                                                                                                     | 可观察结果                                                                                                                                                                                                                                           |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 01 默认公开           | 从创作首页和工程菜单分别打开新建表单。个人账号已授权，保持高级选项折叠并提交                                                       | 提交前可见本机路径、目标仓库和「公开」。工作台打开。本地工程有独立身份和初始版本，远端公开并显示官方模板来源。默认分支内容等于已确认的初始版本，原本地提交仍可访问，重开后沿用同一绑定。仓库为普通工程仓库，自动备份关闭。加入公开目录由作者另行选择 |
| 02 私有与仅本机       | 分别在高级选项选「私有」和「暂不上传」，折叠后提交                                                                                 | 摘要、按钮和实际结果一致。私有仓从官方模板建立，默认分支内容等于已确认的初始版本，重开后沿用同一绑定。仅本机路径创建可编辑工程及初始版本，GitHub 无建仓请求，也无待上传任务                                                                          |
| 03 首次连接和授权     | 未登录，或已登录但目标缺安装权限。填表后分别完成授权、取消授权及选择先在本机创建                                                   | 回到原表单时保留填写内容。成功后显示实际目标，用户提交才建仓。取消后可继续填写或在本机创建                                                                                                                                                           |
| 04 名称、位置与组织   | 用中文工程名。分别模拟本地目录重名、GitHub 仓库重名、本机目录不可写、取消旧工作区的离开确认、组织禁止公开                          | 工程名保留，本地与远端名称可独立修改。本地创建未完成时，旧工作区和已有目录保留，GitHub 无建仓请求。远端重名可调整仓库名。组织拒绝时可选私有、换目标或留在本机                                                                                        |
| 05 提交身份           | 全局已有个人邮箱。保持默认身份新建公开工程并再保存一个版本。另测明确填写 `noreply`                                                 | 默认初始和后续提交的作者及提交者使用占位邮箱。主动填写的 `noreply` 用于对应工程                                                                                                                                                                      |
| 06 首次上传中断       | 分别在建仓前、建仓后响应丢失、已确认建仓但推送未完成、推送已收到但本地未记账时断网或退出。在本机再保存两个版本，切换路线后继续上传 | 本地仍可创作。恢复查明原操作状态，复用可核实的仓库，只完成原先确认的初始版本。推送已完成时补齐状态。后存的版本、草稿及原历史保留，回到原路线后仍可通过普通快进备份后续版本                                                                           |
| 07 目标变更与模板核验 | 首次上传待完成时切换账号、改变可见性、加入远端提交，或改用模板来源或快照不匹配的仓库                                               | 状态说明变更并提供处理入口。目标或可见性变化需核对后继续。无法确认同名仓库属于原操作时等待创作者选择。快照不符或远端已有额外提交时保留双方历史                                                                                                       |
| 08 本机工程后来上传   | 暂不上传后保存多个版本，其中一个包含后来删除的文件。选择首次公开上传                                                               | 确认显示仓库、公开性、当前路线、所含历史及提交身份。GitHub 可核对该路线已保存的历史，包括早先存在的文件。其他路线、编辑草稿和私人创作资源留在本机                                                                                                    |
| 09 本机保存和重命名   | 修改文件，先按 `⌘S`，再从「版本历史」点「保存当前版本」。另测无可记录改动及磁盘冲突                                                | `⌘S` 保存当前文件。记录工程版本后历史才增加一条。保存后留在版本历史，可从提示或历史更名。无改动或冲突时未创建版本，冲突可继续处理                                                                                                                    |
| 10 比较、切换与分叉   | 在 A→B→C 中选择 A，从左栏筛选并切换比较文件，再选「从此版本继续」，修改后保存 D，随后切回原路线                                    | 左栏显示「比较文件」，上方版本树与下方代码差异同时可见。切文件只更新差异，查看 A 时当前仍是 C。保存 D 后树按父版本连出 A→D 与 A→B→C。切回原路线后沿 C 继续保存                                                                                       |
| 11 切换保护           | 有草稿、未记录修改、运行中或未完成助手任务时分别尝试切换                                                                           | 有修改时可保存后切换、取消或明确放弃。取消保留草稿。运行中的切换先停止，切完仍停止。助手任务及外部暂存按现有保护处理                                                                                                                                 |
| 12 手动备份与管理     | 初始版本已公开。保存新版本，查看状态行，再点「备份到 GitHub」                                                                      | 点击前远端仍是初始版本。状态行对应实际工作区路线，点击后 GitHub 可核对该路线的新历史。仓库管理、账号设置和克隆分别可从对应入口打开                                                                                                                   |
| 13 按路线自动备份     | 为已完成首次备份的主路线开启自动备份，断网保存，再从旧版本另开实验路线。联网后切回主路线                                           | 主路线显示待备份，回到原路线后可续传。实验路线默认在本机保存，需手动完成首次备份后才可开启自动备份                                                                                                                                                   |
| 14 可见性和权限变化   | 私有仓有待自动备份的版本，在 GitHub 改为公开。另测公开改私有、退出原账号及撤销写权限                                               | PNDS 发现变更后暂停自动备份，显示新状态。确认新可见性或恢复原目标授权前，待传版本留在本机                                                                                                                                                            |
| 15 更新、冲突和删除   | 分别构造远端单独领先、本机有草稿、双方各有新版本及远端分支被删除                                                                   | 用户主动发起且满足保护条件时才更新。草稿阻止更新并提供处理入口。双方各有新版本时给出外部处理方法。远端分支须明确确认后才重建                                                                                                                         |
| 16 升级、换仓与克隆   | 准备旧自动备份开启且有待传记录的工程、仅本机工程，以及可克隆的公开和私有仓库。升级后测试换仓、解绑和克隆                           | 工程身份、历史、原绑定和待传记录保留。旧自动备份显示暂停，升级过程无自动推送。换仓和解绑须确认，旧队列不转移。克隆沿用来源和可见性，默认手动备份                                                                                                     |

实施验收须通过 `npm run check:all`。真实 GitHub 验收使用已配置的 GitHub App 和「仅选定仓库」的安装，确认设备授权后能从其他账号的官方模板创建公开和私有仓库、访问并推送新仓，同时验证组织权限失败反馈。GitHub 提供较窄的仓库创建权限，已有安装需由所有者批准新增权限。[GitHub App 权限](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)

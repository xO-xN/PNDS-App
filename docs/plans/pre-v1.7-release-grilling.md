## 第一轮已确认

- **v1.7.0 助手可以修改代码**：根据创作者要求修改工程文件代码；复杂任务，例如需要生成或修改大量文件，应提示交给外部编程 agent。范围不局限于结构化配置。哪些任务适合内置完成、修改确认、失败恢复和测试调用方式尚待决定。
- **v1.6.0 先完成已规划工作**：完成功能后，用户在最终阶段与 agent 手动调整 UI/UX。用户接受按后续讨论修改、增加或减少 v1.6.0、v1.6.1、v1.7.0 尚未完成的 Issue；具体改票尚未确定。
- **重新打开 UI/UX 决策**：实现与原定 prototype 存在用户观察到的不一致，用户还有新想法。末期可以调整布局、信息层级、按钮位置和操作步骤；模式接续、草稿保存与运行生命周期继续以现有契约为基线，若需要改变则单独决定。原型“已定稿”不阻止本轮修订。
- **共享包安排在 v1.6.x**：应在某个 v1.6.x 补充版本交付，使 v1.7.0 开始工作时已有一定能力。原讨论将其安排在 v1.5.2 的归属已过期；具体 v1.6.x 编号和首版资源范围待定。
- **按能力验收安排版本**：允许按依赖增加 v1.6.x 中间版本，每版主要新增范围提前冻结。需要形成有限、可验收的 v1.7.0 开工条件；当前没有指定发布日期。

此前共享包已确认的引用、自带依赖并存、试用新版与工程包分发方向继续见[共享包讨论](./v1.5.2-shared-packages-discussion.md)，本轮只撤销过期版本归属，不重新默许其他方案。

## 第二轮已确认

- **单文件修改上限**：用户明确“每次交流只允许一个文件的修改，如果超过一个文件就是复杂任务”。助手可以读取相关工程事实，但修改范围只允许一个文件；需要修改第二个文件的任务交给外部 agent。一次交流与后续执行任务如何对应、编译产物和记录如何计数，以及单文件任务的其他承接条件仍待明确。
- **任务授权与结果审查**：接受将用户明确的修改请求视为本次任务授权，范围明确时直接执行，结束后展示实际变化、验证结果和撤销入口；扩大范围时重新确认。用户随后提出按钮触发工作流的想法，是否通过按钮提交执行、修改与检查是否分开触发继续讨论。
- **助手可调用标准检查与受控测试**：接受内置助手取得实际测试结果，而非只给出测试步骤；用户关心复杂度与时长，提出按按钮开始工作流。自动执行哪些检查、运行与编译条件尚未定稿。
- **共享包集中一个版本交付**：用户不接受先交浏览器资源、再另发 Node 依赖共享的分版方案。浏览器资源与选定的 Node 依赖共享放在同一个 v1.6.x；具体资源清单、版本兼容与失败行为继续收敛。

## 第三轮已确认

- **按钮提交执行**：普通聊天用于讨论和定位；助手说明目标文件和改法，用户点击“执行修改”提交本次单文件修改。点击“运行检查”独立执行选定检查，提供进度、结果与停止入口。聊天和保存不自动触发完整测试；按钮作为执行授权，不追加重复确认。
- **交接先询问**：判断任务复杂后，先向用户说明并询问是否交接外部 agent；确认前不直接生成或写入正式交接。交接的具体呈现和拒绝后的行为仍待决定。
- **共享版本明确**：工程引用明确的共享包版本；App 更新保留旧工程所需版本；接收方缺指定版本时清晰提示并阻止相关运行，不静默替换。主动测试时试用新版、用户确认后采用、检测失败回退的原决定继续有效。
- **自动运行检查不与活动运行并发**：首版需要新启动工程的自动检查遇 App 活动运行时要求先关闭，静态检查仍可执行；助手不自动停止已有演出。并发运行与额外隔离不属于首版承诺。
- **版本骨架获确认**：按下表细化验收范围；多人自动测试、交互录放、OSC 观测和自动音频分析保留为后续候选，不作为 v1.7.0 开工门槛。

## 第四轮已确认与未决

- **v1.6.3 首批模板**：空白工程与 PNDS Classic。两者都能离线创建，随后由用户手动启动，不要求另外安装 npm 依赖。Classic 保留现有 Template 完整示例，但新工程具有独立身份，排除模板运行缓存，更新文档与客户端身份。
- **v1.6.5 检查音频范围**：默认 None，用户明确选择时可执行 Internal；External 首版继续通过 App 手动测试。Internal 自动检查证明启动、就绪和清理，不声称证明声音内容或演奏体验。工程不支持 None 时说明未执行，不自动改变声明或换模式。
- **交接交付形式**：用户同意后，将目标、相关文件、已知问题和验收要求写入创作交接单，并提供可复制任务说明，由创作者交给外部 agent。首版不要求 App 对接特定外部 agent 的执行引擎。
- **共享首批清单未确认**：用户要求先核查 HandPose 是否包含在 ml5.js 文件内、全部共享资源体积和 App 安装包增量，以及 Inarticulate III／IV、All Sentient Being Sounds 能否使用这些共享资源运行。调查完成前，Q15 保持未决，不能把候选清单当作已批准的发行资产。
- **临时副本检查未确认**：用户要求评估由内置助手还是外部 agent 承担更可靠。建议把复制、启动、检查、关停和报告作为确定性的 App／CLI 服务，内置助手和外部 agent 均调用同一服务；临时副本策略及其实际可靠性尚未验收。

Q15 的当轮事实核查见[共享包体积与作品兼容记录](./shared-packages-size-and-compatibility.md)：HandPose 权重在独立文件；原基础候选内容约 24.60 MiB，补三作品现有精确版本后的原候选约 31.20 MiB。第五轮已改变版本与模型范围，这些体积不再代表当前发行目标；最终 DMG 净变化尚未发行构建测量。ASBS 的谱面 PNG 和预编译 dist 仍属于作品内容。

## 第五轮已确认

- **单一较新版本**：App 每项共享库只打包一个较新版本，尽可能新；先尝试 Inarticulate III／IV、ASBS 对当前稳定新版 p5 等依赖的支持，其他包按兼容情况评估版本。III／IV 不再以 App 保留 p5 1.10.0 为默认路线，先验证升级；ASBS 本身不使用 p5，仅核对相关 Node 依赖。
- **模型归工程**：模型不作为通用共享包资源，使用它的工程自行携带。ml5 JS 与模型文件分开；内置 Mobile Sensor Meter 自带的模型仍随该工具进入 App，不能把退出共享区当作安装包减少同等体积。
- **替换旧版本保留方案**：第三轮的 App 保留旧共享版本方向已被本轮替换，原自动回退旧共享版本不能继续作为承诺。工程自带依赖的既有选择保留；升级失败、旧引用失效和版本采用记录仍待细化。
- **临时副本检查确认**：Q18 获用户确认。复制、启动、检查、超时与取消清理、报告由确定性的 App／CLI 服务完成，内置助手与外部 agent 共用；不要求 LLM 自行管理进程。v1.6.5 先验证该服务，再由 v1.7.0 按钮调用。原工程不变、结果对应副本输入和活动运行拒绝等行为仍需要实际验收。

截至本轮官方 npm 查询，稳定候选为 p5 2.3.4、ml5 1.4.0、Express 5.3.0、qrcode 1.5.4、socket.io／socket.io-client 4.8.4、osc-min 2.1.2。这是调研快照，不是已验收或最终发行清单。正式发行前重核，并固定经过验证的具体版本与锁树；运行保持本地固定资源加载。

静态核查已发现 III／IV 的旧 `preload()` 图片加载需要验证 2.x 的加载流程，III 的双触点与 IV 的时间画面需实机回归；新版 Express 的监听错误回调及 osc-min 的 ESM／DataView 接口需要接线适配。尚未改写作品或执行迁移试验，不能把静态核查当作兼容通过。

## 第六轮已确认

- **三作品是发行硬门槛**：Inarticulate III、Inarticulate IV、ASBS 均纳入新版依赖验证；兼容失败时用户会更新作品，保证 App 发行时可运行。不能把未迁移的工程作为不阻塞发行的例外；仍保留一般工程可以自带依赖的能力，但它不替代本次三个目标作品的验收承诺。
- **正式采用写回工程**：正式采用的共享版本写入工程引用，相应更新工程版本并随 `.pnds` 分发；临时副本试验只形成结果，由用户决定采用后更新源工程。App 发行固定经过验证的具体版本，安装新 App 不自动改写工程引用。
- **已有单文件执行单位**：一次点击“执行修改”只改一个已有文本文件，包含源码、manifest、README、SCD。编译产物与检查报告属于独立检查动作；新建、删除、重命名及跨文件改写交给外部 agent，并先询问用户是否交接。

## 第七轮已确认

- **真实发行验收**：三作品按各自声明支持的模式完成 App 页面、交互、声音链、刷新／关停与 `.pnds` 打包安装后的运行验收。v1.6.2 复用当时已有 App／工程测试，不以服务启动代替作品可运行，也不等待 v1.6.5 CLI。
- **只新增上下快捷键**：v1.6.3 首版 Cmd+Opt+↑／↓ 用于演出模式主窗口选卡，到列表边界停止；monitor 持焦仍执行并显示侧栏，不自动加载。确认弹层和启动／关停期间禁止导航。左右键暂不添加；创作模式及 performer、投影、帮助窗口保留各自操作。
- **失败后用户决定**：检查失败保留修改并显示原因，提供撤销或下一次修改方案；再次修改仍需点击执行，不自动连续修复。跨文件问题先询问交接，用户拒绝后保持现状并可继续讨论。
- **正式开发顺序**：v1.6.0–v1.6.5 完成各自范围与验收后开始 v1.7.0 正式开发，助手方案研究可以提前。

## 后续分工的事实依据

- 静态 CLI 检查可复用现有 manifest、路径和依赖校验。当前 `preflight_project` 会先清理遗留进程，不能作为纯读取入口。None smoke 可复用 Node、health 与关停基础，但当前 App 启动流程共享运行状态、偏好和进程记录；独立测试需要自己的运行归属。真实 Internal 无界面测试仍会占用音频设备，不能当成静态检查或无声测试。
- p5.js、ml5.js 与 HandPose 模型属于浏览器静态资源；现有 Template 和内置工具的二维码生成使用 Node 侧 `qrcode`。只共享浏览器库与模型不能消除 Node 依赖的重复；Express、Socket.IO 的现有锁定版本也有差异。
- Mobile Sensor Meter 已进入内置工具注册表；共享包旧讨论中的未注册描述已经过时。

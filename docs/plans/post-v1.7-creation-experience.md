# 1.7.0 之后的创作体验构想

本轮讨论面向既定 1.7.0 及前序版本完成后的界面细调。创作体验以 AI 沟通为主：内置助手深入讨论创作意图、完善方案、辅助已有单文件的局部修改，复杂设计形成创作交接单，由外部编程 agent 实现。后续按用户提供的版本进展继续修订；本文不改变既定版本的交付范围，也不表示以下能力已经实现。

## 已确认方向

2026-10-15 用户明确了上述定位，并确认以下方向：

- 小段代码差异在相关回复下展开，完整文件进入更大的阅读区；保留讨论理由与继续提问的入口。代码区服务于理解 AI 修改和手动调整局部参数。
- 外部交接前后对比是核心体验，允许为此补充比较基线的记录能力。这是新增能力要求，不能仅靠移动现有控件实现。
- 实时工程画面常驻右侧，宽度可调，支持手动展开与还原；查看代码时保留工程画面，不自动缩小或挤走预览。
- 用户确认写入创作交接单时，记录当时已保存的工程内容作为该次交接的比较基线；重复复制任务不重置基线。已保存但尚未提交到 Git 的修改属于当时的工程内容，不能用 Git HEAD 直接替代。
- 返回核对时展示相对交接基线的工程整体变化，优先呈现任务中提到的文件；统一称为“交接后的变化”，不将期间的所有修改自动归因于外部 agent。
- 将用户主动触发的“记录版本（Git 提交）”纳入 1.7.0 之后的方案：明确文件范围与提交说明，用户确认后创建本地提交。保存文件、助手修改和生成交接单均不自动提交；这一确认是未来产品能力的设计决定。

## 布局方向与待验证尺寸

主工作区采用左右并列：左侧为创作对话及按需展开的代码、交接单，右侧常驻实时 monitor。扣除紧凑导航后，先以约 60% 对话、40% monitor 为默认比例，并提供调整宽度的方式。文件树按需展开，控制台保留为抽屉。

打开代码差异、完整文件或交接单均保留 monitor。放大与还原仅改变布局，沿用同一个运行页面，保留其交互状态。测试配置与启动、停止、刷新等动作靠近 monitor；performer 测试窗口管理按需展开。未运行时保留明确的启动入口，不用过往画面冒充实时结果。

“实时查看”表示观察正在运行的工程，不意味着保存代码后自动应用。保存、页面刷新、重启及编译继续分别表达；画面旁提示保存版修改是否仍待刷新或重启。

主窗口当前最小尺寸为 1000 × 700。右侧常驻、可调宽及手动展开／还原已确认；默认比例、最小可读宽度及窄窗口细节需在后续原型中验证，不以本轮比例示意替代验收。

## 代码阅读与局部编辑候选

优先考虑行号、语法着色、括号匹配、自动与选区缩进、稳定的撤销／重做历史、查找替换与跳行、快速打开文件，以及选中代码向助手提问。已有查找、保存、原生撤销继续沿用；差异、单文件撤销与确定性检查已有前序规划，重点是入口和状态衔接。

“本次改动”展示实际执行前后的只读记录；“当前文件”用于编辑草稿。后续手动或外部修改不能被旧撤销覆盖。选区问答需明确文件、行范围、版本及保存状态；读取未保存选区的授权与交互尚待决定，不隐式扩大现有磁盘读取规则。

## 交接比较尚待决定的边界

- 确认交接时仍有未保存草稿的提示与处理，以及交接单写入与基线记录的失败处理。
- 工程整体比较的具体排除范围，以及新建、删除、重命名、二进制资源如何呈现；本地展示变化与向 AI 提供内容分别定义范围。
- 无 Git 工程的基线保存机制、保存位置、保留期限与清理方式。
- 多次交接及任务修订时如何管理各自的基线，如何呈现交叉修改和已有来源证据。
- 返回核对时如何展示当前证据、未覆盖内容及用户验收，而不自动宣称任务完成。

## Git 融入创作流程

2026-10-15 用户确认将主动创建本地提交纳入 1.7.0 之后的设计；既定 v1.6.3 仍只交付只读 Git。以下入口与布局为交互建议，无 Git 工程的启用、提交细节及历史恢复范围尚待确认。

- 工程标题附近以紧凑入口显示分支和变化数量；点击进入主工作区内的“改动与版本”，右侧 monitor 继续保留。
- 差异视图明确显示比较对象：本次助手修改、交接基线或选定 Git 提交。交接比较始终对应当时保存版工程，外部提交不会重置它；没有 Git 时仍能使用创作对话与交接比较。
- 将流程组织为“理解实际改动 → 手动核对运行效果／执行适用检查 → 按需记录版本”。AI 可解释差异、起草提交说明；检查结果与用户对作品效果的判断分别呈现。
- 已确认增加用户主动触发的“记录版本（Git 提交）”：提交前明确文件范围与说明，确认后创建本地提交。保存文件、助手改码和生成交接单均不自动触发提交；草稿、磁盘、提交和运行内容继续分别表达。
- 首轮建议聚焦查看历史、比较差异和本地提交；分支切换、合并与远程同步继续由外部工具处理。无 Git 工程是否提供主动启用入口，以及恢复旧内容的范围和保护方式，留待相关能力确认后细化。

例如，外部 agent 在一次交接期间提交了三次，Git 工作区可能已经没有未提交修改，但“交接后的变化”仍应展示相对交接基线的完整结果。用户也可能先保存参数调整、尚未刷新运行画面；记录 Git 提交不代表画面已经应用这些调整。

当前待确认的问题：

- 无 Git 工程是否提供“启用版本记录”的主动入口，以及首次记录前如何展示文件范围。
- 提交是否先以完整文件为选择单位，以及未保存草稿、外部已暂存内容和工程位于父仓库内时如何明确提交对象。
- 历史内容是否先支持读取单个已有文本文件到编辑草稿，由用户核对后保存；新建、删除、重命名、二进制文件和整个工程的恢复另行定义范围。

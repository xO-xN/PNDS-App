## 本轮扩容范围

“较为完善”以可重复使用的完整创作流程定义：新建工程并自动记录初始版本 → 与助手讨论想法 → 附加代码片段 → 在讨论内调整参数或代码 → 按工程能力临时预演 → 明确应用已有单文件修改 → 查看实际差异和手动测试 → 确认复杂任务与交接基线 → 外部 agent 实现 → 返回比较整体变化并核对效果 → 手动记录版本，必要时载入单文件历史继续编辑。已有工程也可使用该流程；没有 Git 不阻断聊天、编辑、交接和交接比较。

## 对话、代码与实时画面

创作以 AI 沟通为主。内置助手深入讨论创作意图、完善方案，辅助已有单文件的局部修改；复杂任务确认后形成创作交接单，由外部编程 agent 接续。代码区服务于理解实际修改和局部调参，不因扩容获得任意 shell 或跨文件自主编程权限。

主工作区左右并列：左侧为创作对话及按需打开的代码、交接单、比较和版本视图，右侧常驻实时 monitor。文件树按需展开，控制台沿用编辑区下方 dock。小段实际差异在相关回复下展开，完整文件进入更大的阅读区，保留讨论与返回入口。打开代码、交接或历史不自动挤走 monitor；手动展开与还原使用同一个运行页面，保留其交互状态。

本版提供宽度调整和键盘可达的相应操作。约 60% 对话、40% monitor 只作为原型起点；默认比例、最小可读宽度和当前最小窗口 1000 × 700 下的可用性在本版实机验证，不把示意数值当作最终验收。测试配置与启动、停止、刷新等动作靠近 monitor；performer 测试窗口管理按需展开。未运行时显示明确启动入口，不用过往画面冒充实时结果。

右侧常驻 monitor 用于观察正在运行的工程；临时预演另有明确标记和结束入口。“修改建议”“临时预演”“文件草稿”“磁盘保存”“运行内容”“Git 版本”和“已执行差异”分别表达。保存、页面刷新、重启、编译、检查及版本记录保持独立操作，并提示保存版修改是否待刷新或重启。

### 讨论内调参、直接编辑代码与预演

助手根据当前创作意图及实际读取的工程内容，按需提供合适控件和作用说明；用户也可要求把某个可调内容呈现为控件。连续数值可用 fader，非数字内容可用合适的选项或直接代码编辑，不强制每条回复显示控件，也不按画面／声音或固定工程类型划定预演范围。App 核对参数来源、目标文件与版本、当前值和工程限制；模型推测的试调范围须明确为建议。真实模型在不同工程中是否适时选参属于交付验收，固定原型回复不能证明该能力。

同一修改建议卡提供“参数／代码”两种入口，编辑同一份待应用建议。用户可以直接改文字、条件、表达式或函数内容；完整文件编辑器仍用于查看上下文与较长编辑。参数和代码只有在绑定准确时才双向同步；手写代码使绑定失效时保留原文、停用受影响控件并说明原因，不能通过切回参数界面重写用户代码。建议的调整不会自动修改文件草稿、保存版或历史执行记录。

实际工程适配支持时，调参可立即进入临时预演；代码输入不逐键执行，并结束旧预演，用户明确点击“预演修改”后才尝试当前内容。预演能力由参数绑定、运行状态和工程支持共同决定；不支持时解释原因，仍可明确应用后手动测试。预演不注入任意模型生成的 JavaScript，不暗中启动或重启工程、音频或服务；涉及多文件适配的复杂工作进入创作交接单。结束预演恢复临时覆盖前的参数状态，不承诺倒退工程时间或完整运行状态；恢复失败须明确尚未恢复，不自动重启。预演失败不能冒充成功；具体受限接口和恢复行为在实现中审查。

用户点击“应用到工程”只将当前最终建议写入一个已有文本文件，并沿用目标身份、保存版本、已有草稿与适用内容校验保护。冲突时保留建议，要求明确处理后重试。成功后展示实际保存前后文本；该次差异保持只读且不被后续调参或手写代码改写。继续修改形成新的待应用内容，下一次成功应用产生新的记录。应用不自动刷新、重启、检查或 Git 提交；原预演在这次明确应用后重新核验仍有效时可保留临时标记，采用保存版仍需手动刷新／重启。外部或未经核验的来源变化使旧预演失效，不能因此把保存版标为正式运行已采用。

上述流程为已确认的交付范围；参数绑定、工程适配和模型选参效果仍须真实实现与验证。逐项验收见 [#172 创作工作流验收](../acceptance/172-v1.7.0-creation-workflows.md)。

## 基础编辑与显式片段附件

本版补齐行号、基本语法着色、括号匹配、自动与选区缩进、稳定的撤销／重做、当前文件查找替换、跳行和工程内快速打开文件。基本着色覆盖 SuperCollider、JavaScript、TypeScript、JSON、HTML、CSS 与 Markdown；不承诺通用语言服务器、补全、调试器或完整 IDE。已有保存、冲突处理、查找和适用的撤销能力直接复用，避免两套草稿或保存入口。

“修改建议”的参数／代码入口用于调整待应用内容，“本次改动”展示实际执行前后的只读记录，“当前文件”用于编辑当前草稿。沿用 #207 的版本证据和生命周期，不将界面调整扩大为所有助手差异的永久存档；后续手动或外部修改不能被旧撤销覆盖。

用户可选中代码并主动附加给助手，包括尚未保存的片段。输入区展示文件、行范围、片段及未保存标记，可在发送前移除；用户发送后才成为上下文，不自动读取其他草稿。显式片段是新的输入能力，仍遵守工程／模型服务授权、读取开关、预算和聊天历史过滤，不获得额外磁盘写入权。读取开关关闭时禁止发送附件及从历史重新发送，保留附件与输入并提示启用读取或移除附件，不提供绕过该开关的单次发送例外。切换工程或恢复历史不能恢复旧授权或把片段发送给其他工程。

## 交接基线与返回比较

用户确认写入创作交接单时，记录当时已保存的工程内容作为该次交接的比较基线；重复复制任务不重置基线。已保存但未提交到 Git 的修改属于当时工程内容，Git HEAD 不能替代基线。没有 Git 仍可捕获与比较，重启后能找到任务所对应的基线。

写交接单时发现未保存内容，显示未保存文件列表，提供“先保存再交接”和“仅按保存版交接”两个选择；优先建议先保存，不自动保存草稿，基线始终对应实际保存内容。任务写入和基线捕获失败必须明确反馈，不能把没有可用基线的任务呈现为已完成可比较交接。

返回核对时显示整个工程相对基线的变化，优先呈现任务提及的文件。统一称为“交接后的变化”，不把期间所有修改自动归因于外部 agent；外部 agent 的 Git 提交不重置此比较。代码文本提供实际差异；音频、模型等二进制资源按 Q16 只记录识别变化所需的指纹、大小等信息，展示变化摘要，不保存可恢复的资源副本。明确排除项与超限内容，不把未覆盖范围表示为“没有变化”。本地比较与向 AI 发送内容分别遵守对应范围和授权。

基线的存储、保留与清理、多次任务关联、并发变化、捕获失败和超限处理在实施任务中形成可审查方案。返回比较展示证据与未验证内容，不因文本差异存在或自动检查通过就宣称艺术效果完成。

## 本地版本记录与历史

通过 App 新建的工程必须建立标准本地 Git 仓库，并自动记录一个初始版本；这是自动提交的明确例外，后续修改始终由用户手动记录。App 提供所需 Git 能力，覆盖 macOS arm64／x86_64，不要求另行安装开发工具。初始化与初始提交属于创建成功条件，失败须明确原因并可重试，不能把缺少初始记录的工程标为完整创建成功。新工程不继承模板维护者的 Git 历史或署名。

Q15 已确认：已有无 Git 工程提供“启用本地版本记录”入口，由用户主动触发，预览文件范围后初始化并记录初始版本。单纯打开已有工程不自动建仓；已有仓库及其历史保留。位于父仓库或其他 Git 工作区的目录必须说明实际范围，不能静默嵌套或提交父工程。

Q17 已确认：新建工程沿用创作者名称作为本地提交署名，允许修改；邮箱选填，缺省使用明确标示的本机占位地址。已有仓库保留现有身份，缺失时再设置，不要求登录 GitHub，也不改全局 Git 配置。

版本入口显示分支与变化数量，打开后可查看历史时间、提交说明、变化文件与标识，并查看选定版本的内容和差异。记录版本时由用户选择完整文件，预览已保存内容的变化并确认说明；不提供逐行或逐块提交。草稿单独提示且不自动保存；保存文件、助手修改和交接均不自动提交。AI 可以依据实际差异起草说明，是否记录仍由用户决定。

Q18 已确认：Git 默认纳入代码、配置、文档和普通资源，默认排除依赖缓存、已识别敏感项，以及大音频、视频和模型资源；用户可以主动纳入大资源。提交预览显示资源体积与历史增长影响，不承诺无限制存档。已有仓库已经跟踪的大资源不静默取消跟踪，用户必须看见其实际状态；新 ignore 规则也不能被当作已取消跟踪的证据。具体大小阈值与提示行为在实施任务中统一，交接基线的 Q16 资源摘要规则与 Git 纳入范围分别表达。

历史恢复仅将单个现存文本文件的历史内容载入编辑草稿，由用户核对后保存。已有草稿须先处理，保存沿用磁盘版本冲突和适用内容校验；不自动刷新、重启、提交或回退 Git 历史。新建、删除、重命名、二进制文件及整个工程的历史恢复不属于该能力。

外部已暂存内容、并发磁盘变化和仓库身份必须在提交前检查，确保实际记录与用户预览一致。分支切换、合并、远程同步及 GitHub 管理继续由外部工具处理。标准本地 Git 可供外部 agent 接续历史；已有 `.pnds` 打包规则排除任意深度的 `.git*`，版本历史不随演出包分发。

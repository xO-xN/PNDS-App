# v1.7.0-beta.2 自动运行端口管理与冲突避让规格

## Problem Statement

演出机器上的 TCP 端口可能已被其他软件使用。当前 PNDS App 要求工程监听 manifest 声明的 performer／monitor 端口，惯例为 6868／6869；启动前发现冲突就失败。操作者必须理解端口归属、修改工程或处理占用进程，才能继续演出。池主／池客增加局域网接入入口与池客本机回环入口后，只更换外部地址仍不能解除工程内部服务的冲突。

一次“端口空闲”检查也不能保证稍后启动的工程仍能绑定它。若 App 显示预选数字、工程实际监听另一端口，health、monitor、二维码与转发可能各自指向不同服务，甚至误连其他进程。反复更换池客回环端口还会改变网页 origin，使之前保存的 claim token 等数据无法按原来源读取。

用户已确认把自动管理端口与冲突避让纳入 v1.7.0-beta.2，并确认由 App 负责管理，工程遵守运行配置并报告结果。本规格记录这项已确认功能的行为与验收要求，不表示现行平台契约已经支持动态端口，也不表示 HTML 原型执行过真实绑定。

## Solution

App 统一管理池主对池客的局域网入口、工程 performer／monitor 服务以及池客本机回环入口。对明确适配新运行端口契约的工程，App 自动处理可用端口与启动期间的占用冲突，以真实监听结果核验运行，并发布完整实际地址。操作者不需要为普通池客接入手填本机代理端口、修改 manifest 或结束其他软件。

池主入口优先复用可用的既有入口，发生冲突后自动避让，并清楚显示新的完整地址。实际端口确定后，在这次运行中保持不变。池客本地端口由 App 管理，同时兑现按池主与工程隔离、退出或重启后仍可恢复网页数据的要求；不能以每次随机更换 localhost 端口代替完整方案。

未适配的工程保持 manifest 固定端口兼容路径，冲突时明确失败并说明限制，不被 App 静默修改。自动避让不会抢占其他进程，也不会将旧连接悄悄转入另一工程或新演出。

## User Stories

1. As a PNDS Host operator, I want the App to manage runtime ports, so that I can prepare a performance without editing project configuration.
2. As a PNDS Host operator, I want an adapted project to start when its preferred performer port is occupied, so that another application does not unnecessarily block my performance.
3. As a PNDS Host operator, I want an adapted project to avoid an occupied monitor port, so that both required project services can become usable together.
4. As a PNDS Host operator, I want the App to reuse an available Host entry address, so that performers can continue using a familiar address when possible.
5. As a PNDS Host operator, I want a changed Host entry address to be clearly displayed, so that I can give performers the correct connection address.
6. As a PNDS Client user, I want to enter the complete address displayed by the Host, so that I can connect without guessing a port.
7. As a PNDS Client user, I want the App to manage its loopback entry automatically, so that I do not need to configure a local proxy port.
8. As a PNDS Client user, I want my saved webpage data to remain available after a local port conflict is avoided, so that returning to the same Host and project does not silently lose my recovery credentials.
9. As a PNDS Client user, I want different Hosts and projects to retain isolated webpage data, so that one connection cannot inherit another connection's credentials.
10. As a PNDS Client user, I want a reused network address to be checked against the expected Host, so that an old address cannot silently connect me to another Host.
11. As a PNDS Client user, I want my confirmation to remain bound to one performance, so that port reuse cannot automatically join me to a newly started performance.
12. As a PNDS Host operator, I want connection addresses to reflect actual bound listeners, so that I do not share an address that the App merely hoped to use.
13. As a PNDS Host operator, I want project readiness and entry readiness to be reported accurately, so that a working local performance is not confused with a working external entry.
14. As a PNDS Host operator, I want a successful HTTP response from an unrelated process to be rejected, so that port reuse cannot make the wrong service appear ready.
15. As a PNDS Host operator, I want health checks and the monitor to use the actual project ports, so that the interface observes the project that is really running.
16. As a PNDS Client user, I want HTTP resources, polling and WebSocket connections to reach the same confirmed performance, so that the score remains usable after automatic port allocation.
17. As a PNDS Host operator, I want runtime ports to remain stable during a performance, so that the App does not interrupt connected performers by migrating listeners.
18. As a PNDS Host operator, I want startup races to be handled within a bounded period, so that an occupied port cannot leave the App waiting indefinitely.
19. As a PNDS Host operator, I want a partial startup failure to release resources owned by that attempt, so that retrying does not collide with abandoned listeners.
20. As a PNDS Host operator, I want cancellation during startup to prevent late address publication, so that a cancelled attempt cannot reappear as a usable performance.
21. As a PNDS Host operator, I want stopping or replacing a project to revoke its forwarding target, so that old traffic cannot reach the replacement project.
22. As a PNDS Host operator, I want a retry to use only its own allocation and health results, so that delayed replies from a failed attempt cannot corrupt the new run.
23. As a PNDS Host operator, I want legacy projects to keep their declared fixed ports, so that existing project behavior is preserved until they are explicitly adapted.
24. As a PNDS Host operator, I want a legacy port conflict to explain why automatic avoidance is unavailable, so that I can distinguish a project compatibility limit from an App failure.
25. As a project creator, I want an explicit runtime-port capability contract, so that supporting a complete performer URL is not mistaken for supporting dynamic service ports.
26. As a project creator, I want the App to provide the runtime assignment and accept a binding result, so that my project follows one allocation authority instead of inventing its own port policy.
27. As a project creator, I want binding failures and incompatible runtime reports to remain visible, so that an incorrect adapter cannot be accepted as a successful performance.
28. As a PNDS operator, I want occupied ports to be avoided without terminating their owners, so that preparing a performance does not stop unrelated software.
29. As a PNDS operator, I want port diagnostics to distinguish the running allocation from the selected project's manifest, so that I do not mistake a pending project for the service holding a port.
30. As a PNDS operator, I want automatic allocation to preserve existing HTTPS and browser entry rules, so that avoiding a conflict does not silently change security or recovery behavior.
31. As a PNDS operator, I want allocation and cleanup failures to provide an actionable retry result, so that I can recover without the App falsely reporting completion.
32. As a PNDS maintainer, I want real listener and lifecycle tests, so that availability probes and simulated UI states cannot be mistaken for proof that automatic port management works.

## Implementation Decisions

1. **范围与归属。** 本功能随池主／池客进入 v1.7.0-beta.2。端口策略、分配、冲突避让、实际结果登记及地址发布由 App 负责；已适配工程按 App 提供的运行配置监听并报告成功或失败。操作系统可以为实际监听器分配端口，但这不把策略和发布职责转交给工程。

2. **分开管理三层端口。** 池主局域网接入入口面向池客；工程 performer／monitor 端口承载工程服务；池客回环入口只服务本机演奏页面。三者分别记录监听地址、实际端口、所有者和生命周期，不因数字相同而混为同一服务。改变池主外部入口不视为解决工程内部端口冲突。

3. **新增显式适配能力。** 工程必须明确声明并实际遵守可识别版本的运行端口契约，才进入自动分配路径。supportsPerformerUrl 只表达既有完整入口兼容能力，不能推出动态监听、工程接纳、名册或媒体能力。新能力声明的具体名称、结构及版本编码在技术验证后固定；不把测试环境变量提升为已发布平台接口。

4. **旧工程保留固定兼容。** 未声明新能力的工程继续使用 manifest 声明端口，保持现行两个服务、端口合法性和互异要求；冲突明确失败，不自动改端口或写回 manifest。已声明但无法识别或没有遵守新契约时，不在未告知的情况下按另一套含义启动。说明应区分“工程未适配运行端口”与“池主接入协议不兼容”。

5. **最小协议语义。** 新契约至少表达：工程是否支持及支持版本；本次启动的归属；App 提供的服务角色与端口安排；实际监听成功结果或明确失败；就绪后可核验的实际服务信息。必须存在能让 App 在第一次 health 请求前定位 performer 服务的启动结果通道，不能要求 App 向尚未知晓的端口查询端口。具体进程通信方式、字段名及监听器交接机制经 PoC 后确定。

6. **真实绑定是分配依据。** 空闲检查只是诊断，不是端口保留。App 必须以真实服务持有的监听器及可核验的绑定结果登记分配。允许技术验证后采用持有并交接监听器、明确协商绑定或受 App 控制的有界重新分配等机制；不得把“探测后释放，再让子进程绑定”写成无竞态保证。工程不得自行寻找或切换端口后继续让 App 使用旧值。

7. **启动期间有界处理冲突。** 对适配工程，首选端口在检查后被占用，或两项服务仅一项成功时，由 App 在启动期限内协调清理和重新分配。每次尝试须有明确归属，部分成功的监听器不能成为遗留占用。达到期限或无法确认清理时给出失败与重试入口，不无限循环，也不把失败隐去。

8. **预检与最终启动一致。** 预检仍验证工程声明、依赖、端口值和兼容能力，但不因适配工程的首选端口占用而沿用旧固定路径直接判死。每次真正启动重新核验当次能力与运行配置；较早的空闲或兼容结果不能替代启动阶段的绑定和校验。旧工程仍保持固定端口冲突规则。

9. **以当次实际值驱动所有消费者。** health 的目标及返回端口核对、monitor 地址、网关上游、完整 performer URL、二维码、当前运行快照及端口归属诊断，都取同一受管运行的实际结果。适配路径中 manifest 端口可参与首选策略，但不是已应用值；旧路径中实际值仍必须与 manifest 一致。选择其他工程、修改 manifest 或更改下一次启动设置不能重标当前运行。

10. **就绪必须核验。** 工程的成功报告不能独自使演出就绪。App 仍核对健康状态、工程身份、音频模式、实际端口和运行归属，并保持既有音频就绪条件。HTTP 200、页面载入或端口能连接不能证明正确工程已经就绪。端口归属核验不得把第三方同端口服务当成本次工程。

11. **区分演出与入口就绪。** 工程已经就绪与池主接入入口已经绑定、能够正确转发是不同事实。准备阶段可以如实显示状态和已确认的实际地址，只有相应校验通过才标记可加入。入口运行中故障须如实报告，不因改变端口或回退协议掩盖故障，也不把它自动解释为本地音频或工程已经停止。

12. **地址发布与复用。** 池主入口优先复用仍可用的既有入口；发生启动冲突后，在允许的自动分配路径内避让，并显示含实际协议、主机与端口的完整地址。最近连接中的旧地址不会凭空更新，纯 IP 也不携带新端口；本规格不引入自动发现或独立邀请机制。不得把演示端口数字固定为平台约定。

13. **本次运行不迁移。** 一旦发布本次入口或服务分配，不在演出中自动换端口、改 origin 或把连接转往另一监听器。运行中端口／接口故障按相应生命周期报告，由明确重启或重新加入恢复；新一次启动可重新分配，但不能沿用旧演出确认。

14. **复用地址不复用授权。** Host 接入与池客转发必须核验稳定池主身份及已确认的演出上下文。端口被回收、同工程重新开始、换工程或地址指向另一池主，均不能令旧 HTTP 请求、polling 或 WebSocket 自动进入新演出。撤销与校验发生在请求进入工程之前，不靠事后改文案弥补。

15. **生命周期与异步归属。** 绑定、启动报告、health、入口探测及地址发布都归属于各自受管资源及当次运行。停止、取消、替换或失败后，迟到成功不能重新发布旧地址，迟到失败不能覆盖新运行。工程停止时先撤销其转发目标；如果池主控制入口继续用于报告“池主在线／演出已结束”，必须明确其独立生命周期，不能继续转发到旧工程或把入口存在误报为工程仍运行。

16. **资源清理。** 启动失败及停止路径清理所属监听器、活动连接、转发目标、子进程和待完成操作，只有确认结果后才发布完成状态。不能确认终止的资源保留归属并阻止被当作可安全复用。池客退出后不保留仍可向工程发送请求的转发连接；网页数据的保留与网络资源的释放分别处理。

17. **持久网页数据约束。** 池客按池主与工程隔离并保存网页数据，退出或 App 重启后下次手动加入可使用既存数据。端口属于 origin，因此不能把随机更换回环端口视为满足这项要求。稳定来源、存储分区及占用后的恢复方式须在支持的 macOS 基线上共同验证；未证明前不宣称自动避让与存储恢复同时完成。保留数据不等于自动加入，也不保证恢复工程未保存的音乐状态。

18. **保留现有浏览器与 HTTPS 边界。** 池客新增入口的自动避让不等于静默修改普通浏览器／手机入口、可信 HTTPS 固定配置或证书规则。现有完整 performer URL 仍是对外地址依据，已配置可信 HTTPS 的失败、协议与 origin 语义必须明确保留或在相应契约中显式扩展；不能为了绕过冲突降级 HTTP、误报安全上下文或承诺跨 origin 迁移手机 token。

19. **不抢占、不增加并行演出。** 自动分配不能停止、抢占或重配其他进程，也不自动调用释放端口操作。现有显式释放仍需核验占用者身份与受管归属，不能用于绕过受管运行关停。本功能不取消单个受管工程运行约束，不因有空闲端口就启动第二场池主演出。

20. **界面显示真实状态。** 池主地址、端口详情、启动失败及兼容提示使用同一份运行事实。端口检查区分当前已应用结果与所选工程的 manifest 目标；无分配、准备中、实际绑定、入口故障和旧工程冲突不能都显示成“可用”。反馈沿用已核对的 HTML 交互与现有双语文案、类型安全命令、状态持久化及无障碍规则。

## Testing Decisions

用户已在本轮确认以下测试边界：以 App 公开操作／命令为主入口，观察真实工程、持久文件与受管进程／网络结果；界面补测可见工作流，媒体与声音保留实机验收。

- **优先使用一条最高层接缝。** 主验收通过受管运行的公开启动入口，在临时工程上完成 start → 真实绑定与 health／ready → 实际地址的 HTTP／polling／WebSocket 访问 → stop／retry。断言外部请求、运行快照、可观察状态和最终资源释放，不以私有分配函数调用次数、内部容器形状或模拟“空闲”作为成功标准。
- **复用现有材料，补齐完整工作流。** 现有 session 测试已经使用 mock App、真实 health responder、真实入口与公开 stop 检验就绪、失败、运行代次和清理；网关测试已有真实 TCP／HTTP／升级连接及 Socket.IO 形状。主验收应把这些材料放到真实公开启动流程下，而不是只装入内部状态后宣称覆盖启动协商。需要新增 fixture 时放在该工作流边界，避免为每项私有函数再造一套接缝。
- **进程与端口由 fixture 自己拥有。** 复用本地 Node fixture 的就绪诊断、有限输出、期限及异常清理规则。测试端口 lease 仅协调参与的测试，不能证明没有外部显式绑定；生产竞态用受控占用者和可同步的绑定阶段重现。不得操作用户已有服务，也不得靠重跑整条失败测试或降低并行度制造通过。

| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 无冲突启动         | 适配工程的两项真实服务与入口正常就绪；地址、health、monitor、网关和诊断使用一致的实际分配。                                                                |
| 首选端口占用       | 分别占用工程 performer、monitor、池主入口及池客回环首选端口；允许自动分配的路径避让，占用者继续存活且未收到停止信号。                                      |
| 检查后抢占         | 在空闲检查与最终绑定之间由 fixture 占用端口；App 有界处理或明确失败，不把预检通过当成监听成功。                                                            |
| 部分绑定与耗尽     | 一个服务成功、另一个失败以及可用分配无法完成；所属资源先清理，失败明确，下一次重试不被遗留监听器阻挡。                                                     |
| 实际结果核验       | 工程忽略分配、返回错误角色／端口／运行归属、报告失败、非法结果或提前退出；不能进入 ready 或发布可加入入口。                                                |
| 健康证据           | 正确端口上返回 starting、error、错误工程身份、错误音频模式或不匹配端口；第三方 HTTP 200 也不能被接纳为本次工程。                                           |
| 完整转发           | 从发布入口请求 HTML、脚本、Worker／模型样例路径及查询参数，执行 polling 和真实 WebSocket 升级／数据往返；请求进入实际 performer 上游而非 manifest 旧端口。 |
| monitor 与既有入口 | monitor 使用实际内部服务端口；手机／二维码完整 URL、可信 HTTPS 网关及各音频模式保持明确契约，不被自动分配错误改写。                                        |
| 旧工程兼容         | 没有新能力声明时固定端口运行；占用明确失败、manifest 字节不变；supportsPerformerUrl 单独为真不会启用动态分配。                                             |
| 能力不兼容         | 不认识的协议或虚假适配与“未提供连接名册”分别处理；缺名册不影响端口协议成功，也不据此宣称工程已接纳池客。                                                   |
| 取消与交错         | 在分配、绑定、工程启动、报告及入口探测阶段取消或停止；迟到结果不发布地址，不恢复转发，不影响随后启动。                                                     |
| 替换与地址复用     | 停旧工程再启动新工程，或同工程重启使用相同端口；旧上下文的 HTTP、polling 和 WS 均不能进入新演出。                                                          |
| 清理与重试         | 成功 stop、启动失败、异常退出及清理失败均观察资源归属；应释放端口可重新绑定，应终止连接确实关闭，未确认清理不能报告完成。                                  |
| 独立入口寿命       | 工程停止后允许继续存在的池主控制入口仅报告相应状态，没有残留工程转发；显式结束其所有者时真实释放监听器。                                                   |
| 状态与诊断         | 已运行 A、另选 B 或编辑下一次配置时，当前地址和占用归属仍指 A 的实际结果；UI 只通过类型安全边界控制回复时序。                                              |
| origin 与存储      | 池客退出／重开／App 重启以及首选端口被占用后的避让，仍能手动恢复同一池主／工程数据；不同池主或工程隔离，旧确认不自动恢复。                                 |
| 运行期稳定         | 已发布端口发生故障时不自动迁移、不静默降级或重连新演出；当前本地运行与入口故障状态分别如实呈现。                                                           |

默认并行的 `npm run check:all` 全绿是实现完成条件；新增业务逻辑随实现带测试。两台真实设备、支持的 macOS 基线、正式打包权限、局域网地址可达性、媒体与存储行为单独验收。自动化 HTTP 成功不能替代这些结果，HTML 内存演示也不构成端口绑定证据。本次只写规格，不据此执行生产实现或宣称测试已通过。

## Out of Scope

- 独立池客软件、自动发现池主、纯 IP 自动推断端口、独立邀请系统及公网接入服务。
- 同一 App 并行主持和参与、同时运行多场池主演出，或改变创作模式已有的多测试窗口规则。
- 自动停止或抢占其他进程、修改系统端口策略、防火墙、路由器、DNS 服务或要求主 App 提权。
- 无声明地让任意旧工程动态换端口、自动改写工程源码或 manifest，以及由工程自行选择并切换已发布端口。
- 演出中无感迁移监听器、跨演出复用加入授权、绕过池主身份核验或改变工程音乐消息协议。
- 把 supportsPerformerUrl、健康可达或页面载入当成新能力、媒体支持或工程接纳证明。
- 保证普通手机浏览器跨 origin 迁移 claim token，或保证恢复工程未持久化的座位、推子与声音状态。
- 在本规格中提前冻结未经 PoC 证实的端口区间、环境变量、公开字段、进程通道、监听器交接或 WebView 存储机制。
- 本轮实施生产功能、发布版本、提交代码，或在四份规格之外额外拆解实施工单。

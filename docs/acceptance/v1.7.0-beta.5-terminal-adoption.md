## 独立新实例中的阻断故障

运行 `node scripts/verify-project-terminal-wasm.mjs`，每个场景使用新 `WebAssembly.Instance` 和公开 `Ghostty.createTerminal(40, 12, { scrollbackLimit: 128 })`；没有先前释放、没有共享 heap、没有 Canvas、没有 PTY 或网络。每次写入同一行并观察公开 `getScrollbackLength()`。

| 语料              | 完成行数 | 已观察最大历史行数 | 结果                                        |
| ----------------- | -------: | -----------------: | ------------------------------------------- |
| `line ascii`      |   10,000 |              2,316 | 没有 trap；超过请求的 128 行                |
| `中文 é`          |    1,677 |              1,666 | `RuntimeError: memory access out of bounds` |
| `👋🏽 👩🏽‍💻 👨‍👩‍👧‍👦 é 中文` |    1,267 |              1,256 | `RuntimeError: memory access out of bounds` |

两个执行者在本机 arm64 对相同实际 WASM 独立复现上述结果。行数为成功完成的写入数；下一次写入触发 trap。历史探针采用“请求 128 行、允许超量 0 行”的严格测试约束，未假定未经证实的页粒度允许超量；这不是父规格要求精确 128 行。上游把该值传给 Ghostty 的 `max_scrollback`，可能存在最小页面开销，实际有限上界仍未建立。将来修复 trap 后仍需测出并记录真实界限，不能把不再崩溃直接等同于历史已合格。**故障疑似涉及字素/历史页回收，但未完成根因证明。**

另外独立复现了共享实例的 `create → write('👋🏽') → free → create → write('Hello')` 越界。每个会话使用独立 WASM 实例的短语料重建可通过，却不消除上述单次会话长输出故障。

纯黑、隐藏无条件绘制、复制宽字符和本地 WASM loader 已有小范围 wrapper 修补及真实 WASM 回归。没有以插入清空历史指令、截断 Unicode 或重新启动 CLI 的办法掩盖采用缺陷。

## 发布的 next 候选补查

另从 npm 解包了 `ghostty-web@0.4.0-next.21.g640db46`（gitHead `640db4617c69a73ccebce437cebc598c7f73cdb7`，WASM SHA-256 `794191ccd9f469ed0d49ebcb3e6b326d64279b91752b71ad80a3d89ff1f26416`），未将它采用为生产依赖。可以用相同工具加 `--candidate-root <解包后的 package 目录>` 重现。

它在同一公开 API 的 ASCII/CJK/复杂 emoji 各 10,000 行探针中没有 trap，因此不能把稳定版缺陷外推为全部 Web 路线均不可行。但更长的固定 Unicode 语料发现持续 WASM 线性内存增长。80 × 24，`scrollbackLimit: 2000`，每 64 行调用公开 `update()` / `getViewport()` / `markClean()`：

| 成功输出行数 | WASM 线性内存字节 | 当前历史行数 |
| -----------: | ----------------: | -----------: |
|       10,000 |        45,940,736 |        1,142 |
|       20,000 |        81,592,320 |        1,129 |
|       50,000 |       188,547,072 |        1,090 |
|      100,000 |       366,804,992 |        1,025 |

相同新实例、相同有限 Unicode 语料，没有不断引入新字符。两个执行者独立复现；补充按 64/256 行批写仍有同一增长趋势，不能用“传输分片太小”解释并放行。这里测的是 WASM 已分配线性内存，并非已证明的特定对象泄漏或 App RSS；真实分配器根因仍待核对。它尚未证明所要求的受控资源开销，因此不以仅 10,000 行不崩溃作采用结论，也不为绕过问题清空历史或重启会话。

## 宿主与其他证据

真实静态 WKWebView/PTY 短语料 fixture 在本机 aarch64 通过。报告位于执行时的临时目录 `pnds-real-terminal-mgJV6e/result.json`（工具会在每次执行时输出新的目录，不能把该临时路径当作长期工程接口）。生产 CSP 保留，`script-src` 仅新增 `'wasm-unsafe-eval'`。工程实际位置含中文和空格。

该次通过的类别：真实 PTY UTF-8、surface 的默认/ANSI/RGB 纯黑、alternate screen、bracketed paste、合成 composition 抑制、DSR 回写、resize、暂停绘制时继续消费输出、EOF/显式结束/重复释放，以及 24 次独立 heap 的 emoji 短语料重建。alternate screen、配色与 DSR 的部分输入由 fixture 直接写入 production surface，不冒充实际 Agent TUI 端到端验收。

该次工具读数：surface/WASM/PTY 首次建立 50 ms，暂停绘制时 printf 输出可读 33 ms，24 次重建共 323 ms，resize 后为 65 列。这些是单次短 fixture 的读数，没有空闲/隐藏 CPU/RSS、高输出延迟或音频基线对比，不能代替产品性能验收。物理 IME、目标 CLI、其他资源开销及双架构发布运行尚未执行，不计通过。

- 正常回归使用真实 WASM 验证默认/ANSI/RGB 纯黑、UTF-8 跨字节分片与 Unicode 选区、隐藏无条件 rAF 暂停、12 次独立 heap 的短语料重建，以及旧会话字节拒绝、原生清理失败保留 surface、setup 失败清理原生会话。Canvas 在该测试中被模拟，不算 WebKit 验收。
- 静态原生 fixture 前端实测构建出独立本地 WASM 423,036 字节；短语料 fixture JS 约 139 kB，随 fixture 验证逻辑变化。不是 App/DMG 包增量或最终工作台首开结果。
- 既有主 App 前端基线为 3,854,757 字节 / 55 文件；当前尚无资格把 fixture 文件之和当作完整集成 App 的增量。
- 未完成 arm64/x86_64 发布包运行、真实付费 Agent 交接修改、音频/monitor 并行负载；不声明 beta.5 可交付。

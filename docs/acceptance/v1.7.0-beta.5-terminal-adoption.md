## 未修改稳定包的历史故障

最初对未修改 `0.4.0` 发布包的对照探针中，每个场景使用新 `WebAssembly.Instance` 和公开 `Ghostty.createTerminal(40, 12, { scrollbackLimit: 128 })`（128 是字节预算，不是行数）；没有先前释放、没有共享 heap、没有 Canvas、没有 PTY 或网络。每次写入同一行并观察公开 `getScrollbackLength()`。

| 语料              | 完成行数 | 已观察最大历史行数 | 结果                                        |
| ----------------- | -------: | -----------------: | ------------------------------------------- |
| `line ascii`      |   10,000 |              2,316 | 没有 trap；历史行数仅为观测值               |
| `中文 é`          |    1,677 |              1,666 | `RuntimeError: memory access out of bounds` |
| `👋🏽 👩🏽‍💻 👨‍👩‍👧‍👦 é 中文` |    1,267 |              1,256 | `RuntimeError: memory access out of bounds` |

两个执行者在本机 arm64 对相同实际 WASM 独立复现上述结果。行数为成功完成的写入数；下一次写入触发 trap。原探针一度把 `scrollbackLimit` 当成行数，这个严格 128 行判断已撤销；核心接收的是带最小页面开销的字节预算。真正的越界故障与该误读分别记录，不能用行数超量本身判定规格违反。后续源码对照、局部修补与正确字节预算的验证见下文；当前默认探针已改为加载修补资产并使用 1 MiB 预算，不再执行旧的 128 行断言。

另外独立复现了共享实例的 `create → write('👋🏽') → free → create → write('Hello')` 越界。每个会话使用独立 WASM 实例的短语料重建可通过，却不消除上述单次会话长输出故障。

纯黑、隐藏无条件绘制、复制宽字符和本地 WASM loader 已有小范围 wrapper 修补及真实 WASM 回归。没有以插入清空历史指令、截断 Unicode 或重新启动 CLI 的办法掩盖采用缺陷。

## 发布的 next 候选补查

对照阶段另从 npm 解包了 `ghostty-web@0.4.0-next.21.g640db46`（gitHead `640db4617c69a73ccebce437cebc598c7f73cdb7`，WASM SHA-256 `794191ccd9f469ed0d49ebcb3e6b326d64279b91752b71ad80a3d89ff1f26416`），其未修补 WASM 未被采用。当前固定的是这个 wrapper 加下述显式修改 WASM；可用工具的 `--candidate-root <解包后的 package 目录>` 选择未修改发布资产作对照，当前探针的字节预算与历史记录分别表达。

它在同一公开 API 的 ASCII/CJK/复杂 emoji 各 10,000 行探针中没有 trap，因此不能把稳定版缺陷外推为全部 Web 路线均不可行。但更长的固定 Unicode 语料发现持续 WASM 线性内存增长。80 × 24，`scrollbackLimit: 2000`，每 64 行调用公开 `update()` / `getViewport()` / `markClean()`：

| 成功输出行数 | WASM 线性内存字节 | 当前历史行数 |
| -----------: | ----------------: | -----------: |
|       10,000 |        45,940,736 |        1,142 |
|       20,000 |        81,592,320 |        1,129 |
|       50,000 |       188,547,072 |        1,090 |
|      100,000 |       366,804,992 |        1,025 |

相同新实例、相同有限 Unicode 语料，没有不断引入新字符。两个执行者独立复现；补充按 64/256 行批写仍有同一增长趋势，不能用“传输分片太小”解释并放行。这里测的是 WASM 已分配线性内存，并非已证明的特定对象泄漏或 App RSS；真实分配器根因仍待核对。它尚未证明所要求的受控资源开销，因此不以仅 10,000 行不崩溃作采用结论，也不为绕过问题清空历史或重启会话。

## 当前显式修补资产

wrapper 固定为已发布 `ghostty-web@0.4.0-next.21.g640db46`，源码提交 `640db4617c69a73ccebce437cebc598c7f73cdb7`。App／fixture／回归测试统一加载 `src/assets/project-terminal/ghostty-vt.wasm`，而不是静默替换 npm 包内的 WASM。修改资产为 **424,058 字节**，SHA-256 `9658ac9534e8cf702c72bcbb371de3f36d50f060695216f4fc1f5b4c4823b543`。

固定 Ghostty 核心提交上的局部源码修补保留被回收页的实际 capacity，并在 WASM ReleaseSmall 两条页初始化路径清零复用存储。前者修复增长页被当作标准容量回收的所有权失配；后者修复“native mmap 保证零初始化、WASM 复用块并不保证”的平台假设。没有替换 renderer、删除终端状态或清空历史。完整源补丁、原版权通知、构建 SHA 和复现命令保存在 `vendor/ghostty-web/`。

使用官方 Zig 0.15.2、`wasm32-freestanding`、ReleaseSmall 构建；只应用上游 API patch 的对照产物与 npm 发布 WASM 字节一致（SHA `794191cc…6416`），确认补丁比较没有混入编译器差异。PNDS 修改增加 119 字节。

原 wrapper 把 `scrollback` 误注释为行数；核心 `max_scrollback` 实际是字节预算，另有最小页及活动／字素存储。产品 surface 使用 **1 MiB 字节预算**。旧严格 128 行探针不是这个契约，也不是父规格要求；已从当前资格判断中移除。

当前 `node scripts/verify-project-terminal-wasm.mjs` 对**仓库内同一修改资产**完成：

- ASCII、CJK、组合重音、肤色 emoji、复杂 ZWJ 五套语料 × 40／80／132 列，每组 100,000 行；1 MiB 预算；真实 `update`／`getViewport`／字素读取／`markClean`，全部完成，50k→100k 的已分配 WASM 容量增长均为 0。
- 1／2／4 MiB 预算下，已有 5k 行复杂输出后反复缩至 20×5、扩至 132×36、再到 40×12 和 80×24，继续写入／render／free，全部完成。
- 同一个 WASM 实例 30 轮和独立实例 30 轮的写入／resize／render／free 全部完成；同实例后期容量保持平台。

原生与主执行者另对修改 SHA 独立复现 15 组长输出和两种 30 轮生命周期；它们使用的早期 2000 字节小预算与当前产品 1 MiB 分开记录，不把任一值误作行数。当前产品预算的探针也已独立通过。探针使用独立受管 Node 子进程和 60 秒真实期限，避免将同步 resize 卡死伪装成等待。

这些是 WASM 已分配容量和 VT 生命周期证据，不等于 App RSS、物理输入法、实际 Agent TUI、双架构发布或音频共存验收。修补资产的真实 WKWebView 短语料验证与交互验收将在实际运行后追加。

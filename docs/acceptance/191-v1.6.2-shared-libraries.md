## 共享工程选卡性能修复（2026-10-14）

用户实测后确认延迟主要发生在 1.6.2 共享工程；DNS 问题交给另一个 agent，此次只修改共享资源解析与相关测试／文档。原实现每次选卡重新解析 catalog 并逐库读取、计算 SHA-256，多个 Node 引用重复校验相同生产闭包。

现在一次解析对相同路径／长度／预期哈希的记录去重。App 选卡、采用和启动使用仅驻留本进程的成功校验缓存；每次仍检查所有必要文件的可读性、目录边界、预期哈希和文件身份／纳秒 mtime／ctime。首次与变化后的资源完整计算 SHA-256；catalog 变化、资源替换／损坏或失败使缓存失效。打包／安装仍执行新一轮完整内容校验。具体模式见 [开发说明](../developer/shared-libraries.md)。

使用实际 Mobile Sensor Meter 0.4.0 的四个确切引用，在相同 macOS arm64 debug 环境调用公开 `resolve_at`：

| 指标                 |      修复前 |    修复后 |
| -------------------- | ----------: | --------: |
| 本进程首次完整解析   | 1,918.55 ms | 918.06 ms |
| 随后三次解析的中位数 | 1,778.84 ms | 100.81 ms |

重复解析耗时约降低 94%。这里测量共享资源解析阶段，不包含端口检查、偏好读取等其它选卡步骤，也不代替原生 UI 手测。首次解析仍承担完整内容校验。

正常回归新增八项：同长度损坏并恢复旧 mtime、删除与原子替换、catalog 改写并恢复旧 mtime、确切版本变化、目录重定向越界、目录内链接更换目标、资源根替换、重叠记录的冲突哈希。缓存以声明路径作为键，并保存当前真实目标，避免内部链接反复重定向留下旧目标记录。实际资源性能复验为显式忽略的 `repeated_shipped_shared_project_resolution_is_faster_after_full_verification`，在原实现上已失败、修复后通过。
